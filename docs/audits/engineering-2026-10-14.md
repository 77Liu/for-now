**1. 错误登录可以拖住其他账户的正常认证**

`login()` 在 `repository.update()` 内验证密码，并在失败时等待 250ms。JSON 认证仓库使用一条全局 Promise 队列；PostgreSQL 认证仓库则在调用这个 mutator 前取得数据库级认证 advisory lock。等待时间因此被所有账户共同承担。现有限流按“IP + 用户名”组合记账，更换用户名就会进入不同桶。

证据链：[登录与延迟](../../src/modules/auth/index.mjs#L197-L215)、[JSON 全局写队列](../../src/shared/persistence/auth-repository.mjs#L20-L40)、[PostgreSQL 认证事务锁](../../src/shared/persistence/postgres-runtime.mjs#L441-L460)。仓库提供的 Nginx 配置也没有为登录入口设置请求速率限制；线上是否存在额外防护未检查。

隔离复现采用真实认证服务和 JSON 仓库适配器，数据文件位于临时目录。正常登录单次耗时 **21ms**；先提交同一来源、六个不同不存在用户名的登录请求，再从另一来源提交正确登录，后者耗时 **1581ms**。六个错误请求均返回 401，未触发 429。此测量证明队列阻塞机制，不代表线上延迟基线。

后果是匿名请求可以低成本阻塞正常登录，以及同样依赖认证写事务的注册、退出和账户管理。PostgreSQL 等待者还会占用认证连接池连接，具备扩大影响的条件；这一部分通过代码确认，未进行真实数据库攻击压测。

整改应把密码计算和失败延迟移出全局写事务，登录成功后用短事务重新校验密码版本、账户状态及会话版本，再创建会话。采用全局、来源 IP、账户等互补限流，并为等待队列和限流缓存设置容量及过期回收。单纯删除认证锁会引入竞争，必须同步收紧事务边界。

验收应覆盖：一个来源轮换用户名失败登录时，另一账户仍能正常登录和退出；失败延迟不持有认证写锁；密码修改与并发登录不能签发基于旧密码的有效会话。JSON 和 PostgreSQL 两种后端都应验证。

**2. 一个账户恢复异常会让所有账户无法访问服务**

启动恢复串行遍历全部账户。每个账户要依次恢复业务数据、模型设置、AI 用量、审计、附件清理及后台任务；任意一步抛错都会结束整轮恢复。HTTP 服务直到整个恢复过程成功后才开始监听，所以单个账户的局部故障会阻止全站启动。

证据链：[账户恢复步骤](../../src/app/account-lifecycle.mjs#L55-L62)、[逐账户恢复](../../src/app/account-lifecycle.mjs#L147-L149)、[恢复完成后才监听端口](../../src/app/server-lifecycle.mjs#L133-L155)。

隔离复现调用真实账户生命周期和服务生命周期实现，注入三个虚构账户 A、B、C，在 B 的用量恢复步骤抛出异常。结果是 **服务未启动，C 的恢复完全没有执行**。生产监督配置会尝试重启，但确定性的账户故障不会因此消失。

现有 [account-lifecycle 回归测试](../../scripts/account-lifecycle-regression.mjs#L252-L274) 明确要求 B 失败后停止恢复。这说明问题已经进入验收契约，需要调整故障隔离目标，不能只补一个 try/catch 后继续返回成功。

整改应区分数据库、schema、全局认证等基础设施故障与特定账户的数据故障。基础设施故障继续阻断全局就绪；账户故障应保留原数据，将该账户标记为恢复失败、限制其读写并发出告警，健康账户继续提供服务。恢复过程应支持幂等重试；账户数量增长后，再采用受限并发或按需恢复。

验收应覆盖：A、C 可以登录和记录；B 收到明确的恢复状态；B 的数据不被默认空值覆盖；重试恢复 B 不重复执行已完成的外部副作用；全局数据库故障仍不能被误报为就绪。

**3. PostgreSQL 仍承载整份文档读写，扩容基础没有建立**

一次业务更新先读取该账户完整 store，规范化并复制，再映射为全部数据库对象；提交时删除该账户在六张 store 表中的数据，再批量插回。业务操作只改变一个对象，也走相同路径。读取 store 同样对六张表执行账户范围全量查询。

证据链：[完整读取及提交](../../src/shared/persistence/postgres-runtime.mjs#L279-L324)、[全量查询与清除实现](../../src/shared/persistence/postgres-objects.mjs#L48-L84)、[同步快照仍完整读取 store](../../src/shared/persistence/postgres-runtime.mjs#L362-L374)。

用真实映射和 SQL 生成函数、记录 SQL 调用的测试替身验证了写入工作量：

| 虚构账户记录数 | 改动记录数 | 账户范围 DELETE 语句数 | 重新插入的业务对象数 | INSERT 参数合计字节数 |
| --- | --- | --- | --- | --- |
| 100 | 1 | 6 | 100 | 39,646 B |
| 1,000 | 1 | 6 | 1,000 | 398,746 B |

以上是本地函数实测的生成结果，不是 PostgreSQL 吞吐或 WAL 实测。它直接证明一次小修改的工作量随账户历史数据增长。数据库事务可以回滚，不能据此断言数据必然丢失；已经确定的问题是读写放大、锁占用及内存复制成本。

同步接口会进一步放大读取成本：[无变化的长轮询](../../src/http/sync.mjs#L78-L84) 在等待前后各读一次完整快照。响应数据缩小并没有消除服务器读取全部历史的成本。此外，[应用实例锁](../../src/shared/persistence/postgres-runtime.mjs#L510-L517) 明确拒绝同库第二个应用实例，当前调度和全局配额不能直接水平扩展。

整改应从高频路径切入：任务状态、通知已读、单条记录编辑改为按资源 ID 和版本执行增量 SQL；关联、附件引用、幂等回执和同步事件随同一事务原子提交。同步游标、操作回执应能独立查询，空轮询不再重建 store。随后逐域迁移列表查询及持久化逻辑，保留数据迁移与回滚证据。

多实例应在持久任务领取、租约、重试幂等及跨实例配额完成后再开放，不能直接删除现有实例锁。验收应度量：单条修改影响的行数、SQL 调用、锁等待、WAL、内存和延迟随历史规模的变化；并确认重启、并发修改和任务重放下的数据一致性。

**4. 100 条之后的思绪没有连续浏览入口**

路由投影最多恢复五页，每页二十条，第五页强制将下一页标识置空。前端也在累计达到 100 条时拒绝继续加载，并把合并后的列表裁剪到 100 条。这同时限制了无筛选列表和结果超过 100 条的筛选列表。

证据链：[路由投影截断](../../src/app/startup-projections.mjs#L618-L650)、[前端加载限制](../../public/frontend/features/thoughts/operations.mjs#L101-L135)、[底层游标分页](../../src/modules/thoughts/index.mjs#L186-L245)。

隔离复现构造 121 条虚构思绪，第五页返回 **100 条且 nextId 为空**；请求第六页得到与第五页完全相同的结果。底层分页函数仍可继续返回接下来的二十条，说明数据并未删除，缺陷在页面访问链路。更精确的搜索或已知 ID 详情可能仍能访问旧记录，不能把问题描述为历史数据永久丢失。

整改应保持游标可继续推进，使用分页窗口或虚拟列表限制渲染数量；页面恢复保存当前位置及必要游标，避免靠“反复取前 N 页”恢复位置。只有服务端确认没有后续数据，才显示已经到底。

验收应从页面连续浏览超过 100 条数据，验证最后一条可达、无重复遗漏，且搜索、标签、排序、详情返回和刷新后的列表位置一致。现有投影测试的相关搜索用例只恢复到 29 条，未覆盖这个边界。

**5. AI 请求排队时，取消和超时不会结束等待**

`createRateGate()` 的等待队列只保存 resolve 回调，没有取消信号、截止时间或队列上限。AI 生成器在获取容量前预留调用额度，虽然自身设置了超时 AbortController，但 `gate.acquire()` 和场景级 acquire 都没有收到该 signal。因此请求必须排到容量，才能进入后续处理并结束。

证据链：[容量队列](../../src/shared/concurrency/index.mjs#L1-L2)、[超时与额度预留、容量等待](../../src/modules/ai/generation.mjs#L112-L148)、[后续供应商调用与释放](../../src/modules/ai/generation.mjs#L232-L257)。

隔离复现使用真实容量队列和生成器，供应商调用替换为本地函数。先占住唯一并发槽，再发起第二个请求：取消后观察 80ms，请求仍未结束，已预留额度也未释放；另一用例设置 20ms 超时，在开始后约 90ms 观察时仍未结束。两个用例都在主动释放前一个容量槽后才返回取消或超时错误。

复现还观察到后续 transport 收到了已取消 signal。真实 fetch 通常会据此拒绝请求，这不证明发生了外部收费；已确认的是等待不能及时结束、额度不能及时归还，以及失效请求还会进入后续容量和审计流程。

整改应实现 `acquire({ signal, deadline })`，取消或到期时原子移除等待项并拒绝 Promise；排队设定总量及账户限制，超限给出明确的可重试结果；获准后、写调用审计和开始预算阶段前再次检查取消状态。额度预留与释放必须覆盖所有未实际开始调用的退出路径。

验收应在真实队列饱和条件下证明：取消和超时能够自行返回，不依赖其他请求释放容量；未启动请求不进入 transport；额度恢复；队列项及事件监听器回收；正常请求不会被失效队列长期挡住。

**2026-10-14 补充：F3 的具体范围与并行能力**

补充代码核对时工作区提交为 `de90df`。与上文 `4ebc4b` 的隔离测量区分：以下是当前调用链的静态核对，未重新进行线上或数据库容量测试。

| 场景 | 为什么触发整份 store 提交 |
| --- | --- |
| 新建/编辑思绪、捕念、健康打卡、日记等 | 领域仓库最终调用共享 `repository.update()`，首次幂等创建走 `executeIdempotent()` 后提交 |
| 服务端保存日记草稿 | `saveDraft()` 改变 `journalDraft` 后提交账户 store；不是指每次键盘输入 |
| 一条通知已读或全部已读 | `backgroundAi.readNotification/readAllNotifications` 直接调用共享 `repository.update()` |
| AI任务入队、领取运行、保存结果/失败 | 各阶段分别提交 store，正常“创建→运行→结果保存”主链已有三次提交，其他后续动作可能更多 |
| 取消/重试任务、启动恢复任务 | 通过相同仓库更新任务及通知状态 |

代表调用方：[日记草稿](../../src/modules/journals/records.mjs#L215-L249)、[集合仓库对整份store的包装](../../src/app/content/resources.mjs#L54-L95)、[通知已读](../../src/app/background-ai.mjs#L565-L573)、[AI任务领取](../../src/app/background-ai.mjs#L163-L194)。

普通 `update()` 在 mutator 正常返回后无条件提交，没有先判断实际差量。因此“重复已读”等没有实际业务变化的调用也可能重写；抛错退出和命中幂等账本的 replay 不属于这个无条件提交分支。纯读取与同步 GET 读取完整 store，但不因此执行整份重写。

重写单位是**当前账户在六张 store 映射表内全部仍保存的数据**，不按本次功能、页面、日期或最近窗口缩小：

| 表 | 内容 |
| --- | --- |
| `store_objects` | 业务记录和嵌套子项，包括思绪、日记、健康、聊天、书笔记、小物元数据、摘录、AI任务、通知、用户模型、来源权限、摘要和回收站等 |
| `store_relations` | 上述对象的父子、来源、任务和结果等关系 |
| `store_attachment_refs` | 业务对象到附件的引用路径 |
| `store_fields` | 顶层字段、未拆为对象的JSON值，以及同步元数据等 |
| `resource_lifecycle` | 资源生命周期和删除/恢复等记录 |
| `idempotency_ledger` | 保留期内的幂等键、请求摘要及响应回执 |

SQL 删除带 `WHERE account_id = $1`，不是清空全表。图片/音频二进制及附件清单不随 store 的六表整体重建；提交另有附件引用校验和针对无引用 `missing_cleanup` 清单项的删除。账户登录凭据/会话在认证表，模型设置与AI用量在独立 document，系统/AI审计日志也不属于这六张表。修改设置不会顺带重写该账户全部思绪，但当前独立 document 适配器仍会重写被修改的那份 document。

重写体积取决于当前账户所有保留正文、嵌套对象、派生内容及回执，没有“最多100条”或“最近7天”这样的仓储上限。前述 398,746 B 是一千条简短虚构思绪的 INSERT 参数总量，不能当作真实账户大小、磁盘占用或数据库实际写入字节。真实账户规模本次没有查询。

当前具有并行能力：HTTP 可处理并发请求；不同账户的数据操作可通过连接池并行；同一账户写事务通过数据库 advisory lock 串行，读取使用一致快照。全站预算已有数据库行锁。限制是**多个完整应用进程共享同一数据库尚未具备完整协调能力**，不是 PostgreSQL 只能单连接，也不是设置的性能阈值。

禁止多实例有具体正确性依据：

1. [任务恢复](../../src/modules/tasks/index.mjs#L499-L517)没有工作进程租约与心跳，启动时会把已有 `running` 任务视为中断。移除应用锁后，B启动可能误判A仍在执行的任务。
2. [预算恢复](../../src/app/ai-budget-runtime.mjs#L218-L245)扫描全部遗留预留并结算或释放，没有先判断它是否属于其他存活实例。数据库行锁只能保证单次改动原子，不能证明该预留已经失去执行者。
3. 供应商QPS/并发容量门、[账户在途额度预留](../../src/modules/ai/usage.mjs#L332-L356)和流式在途去重仍有进程内状态。多个实例会各自计数，且另一个进程无法直接共享本进程的取消控制器或回答流。

因此只改端口、连接池大小、QPS或进程数不能解决；应用锁也没有现成配置开关。共享额度账本并非全部缺失，整改重点是补齐任务执行归属/租约、按失效租约恢复、共享或明确分配的容量与额度，以及取消/去重的跨进程协调。继续保持单实例时，可先独立完成按资源增量SQL和元数据读取优化，不必把多实例改造作为其前置。
