# UI/UX 优化标准作业流程

- SOP 编号：`SOP-UIUX-001`
- 版本：`1.0`
- 状态：生效
- 适用项目：此刻
- 适用范围：新页面、新流程、现有页面重构、组件统一、展示文案调整、响应式与可访问性优化
- 版本设计依据：对应开发分支中的 `knowledge/ui-ux-v0.4.0.md`

## 1. 目的

本 SOP 用于避免以下开发方式：

- 收到功能需求后直接增加按钮、表单和卡片；
- 只修改颜色、圆角和间距，未解决任务层级；
- 每个页面独立设计相同组件；
- 只设计正常状态，不设计空、加载、失败和恢复；
- 把研发术语、数据模型名称或实现说明直接展示给用户；
- 只检查页面能打开和没有溢出，就宣称 UI/UX 完成。

本 SOP 的目标是把每次 UI/UX 优化转化为一套可重复执行的过程：

`发现问题 → 收集证据 → 定义任务 → 重构信息架构 → 审计文案 → 设计流程 → 建立组件 → 制作原型 → 用户验证 → 实施交接 → 设计验收`

## 2. 适用时机

命中任一条件时必须执行本 SOP：

1. 新增用户可见页面或主要流程。
2. 在现有页面增加新的功能入口、字段、媒体类型或 AI 能力。
3. 用户反馈“找不到、看不懂、太复杂、像功能堆叠、没有设计”。
4. 相同组件在多个页面出现不同尺寸、颜色、交互或状态。
5. 页面切换、模板切换或状态切换出现明显位移和布局跳动。
6. 用户可见文字包含内部术语、供应商名称、实现说明或证明式说明。
7. 功能已经可用，但体验、视觉或内容质量未经过独立验收。
8. 版本规划包含 `UI` 或 `UX` 类型需求。

纯后端、无用户可见变化的任务不执行完整流程，但若改变等待、错误、权限或数据
可见性，仍需执行状态与文案审计。

## 3. 角色与职责

| 角色 | 职责 | 不可替代的决定 |
| --- | --- | --- |
| Owner | 确认产品目标、文化方向、范围和关键取舍 | 品牌方向、核心任务、用户权益和重大范围变化 |
| UI/UX 负责人 | 调研、审计、流程、视觉、原型和交接 | 设计方案完整性与规范一致性 |
| 产品/需求负责人 | 用户任务、优先级、验收标准和需求池 | 需求边界与版本归属 |
| 工程负责人 | 技术可行性、组件复用、状态契约和实现计划 | 技术实现与风险控制 |
| 测试负责人 | 用户旅程、视觉回归、异常与可访问性验证 | 验收证据是否充分 |
| 内容设计负责人 | 用户可见文案、术语、来源和错误语言 | 文案是否清楚、必要且符合产品语气 |

同一人可以承担多个角色，但每个阶段仍要按不同职责独立检查，不能因为“都是自己”
而跳过闸门。

## 4. 单一事实来源

执行前必须读取：

1. [产品定义](../knowledge/product-definition.md)
2. [文化内容与命名偏好](../knowledge/cultural-content-preferences.md)
3. [设计语言与哲学](../knowledge/design-language.md)
4. 当前开发分支中的 `knowledge/ui-ux-v0.4.0.md`
5. [用户旅程测试](../knowledge/user-journey-testing.md)
6. [指标口径](../knowledge/metrics.md)，仅在涉及趋势、状态和统计时读取

发生冲突时的优先级：

`用户本次明确要求 > 产品与文化单一事实来源 > UI/UX 版本规范 > 页面历史实现`

旧 UI 只提供功能和数据证据，不是新设计必须继承的视觉约束。

## 5. 输入与输出

### 5.1 最小输入

开始前必须具备：

- 需求池记录；
- 用户问题或期望；
- 当前页面或流程；
- 可运行页面、截图或源码；
- 相关业务与数据约束；
- 目标版本；
- 明确的非目标。

需求池中的“技术描述”必须使用以下结构：

```text
现状：用户现在看见什么、遇到什么问题。
优化预期：改完后用户应该怎样理解和完成任务。
技术方案：准备怎样调整页面、状态、组件和数据连接。
```

禁止只写“优化体验”“美化页面”“调整交互”“参考竞品”等无法验收的描述。

### 5.2 必须输出

一次完整 UI/UX 优化至少产生：

- 现状审计；
- 用户任务地图；
- 信息架构或页面职责；
- 文案审计表；
- 正常与异常流程；
- 低保真线框；
- 视觉规范或组件映射；
- 手机与桌面高保真稿；
- 可交互原型；
- 实施规格；
- 验收用例；
- 固定截图与测试证据；
- 设计决策记录。

只提供一张理想状态视觉图，不算完成。

## 6. 总流程与闸门

| 阶段 | 主要工作 | 必须产物 | 退出闸门 |
| --- | --- | --- | --- |
| S0 立项 | 明确问题、范围、版本和非目标 | 设计任务简报 | G0 问题成立 |
| S1 证据 | 截图、源码、用户反馈、数据和状态盘点 | 现状审计 | G1 证据充分 |
| S2 任务与架构 | 用户任务、页面职责、入口和层级 | 任务地图、信息架构 | G2 结构冻结 |
| S3 内容设计 | 审计标题、操作、状态、来源和技术术语 | 文案 inventory | G3 文案职责清楚 |
| S4 流程设计 | 正常、空、加载、失败、权限、冲突和恢复 | 流程图、状态矩阵 | G4 路径闭合 |
| S5 线框 | 建立移动优先的内容与操作层级 | 双端线框 | G5 层级通过 |
| S6 视觉与组件 | token、组件、状态和动效 | 视觉稿、组件清单 | G6 系统一致 |
| S7 原型验证 | 真实任务、可理解性、可达性和多端 | 原型与观察记录 | G7 用户可完成 |
| S8 实施交接 | 行为契约、数据、组件和测试要求 | 实施规格 | G8 可以开发 |
| S9 设计验收 | 对照原型、任务、状态和视觉基线 | 验收证据 | G9 可以关闭 |

任何闸门不通过，都退回最近一个能解决问题的阶段。不得在实现阶段通过局部 CSS
补丁掩盖信息架构或交互流程问题。

## 7. S0：立项

### 7.1 建立设计任务简报

使用以下模板：

```markdown
# UI/UX 任务简报

- 需求编号：
- 版本：
- 页面或流程：
- 用户：
- 使用情境：
- 用户要完成的任务：
- 当前问题：
- 期望结果：
- 业务约束：
- 数据约束：
- 技术约束：
- 非目标：
- 需要 Owner 决定：
- 计划证据：
```

### 7.2 判断问题类型

每个问题至少归入一类：

- 信息架构；
- 任务流程；
- 交互反馈；
- 内容设计；
- 视觉层级；
- 组件一致性；
- 响应式；
- 可访问性；
- 感知性能；
- 信任与数据边界。

如果一个问题同时属于多类，必须分别描述，不以“整体体验不好”代替。

### 7.3 G0：问题成立

进入下一阶段前确认：

- 问题能用用户行为描述；
- 不是只根据个人审美做判断；
- 范围和非目标明确；
- 需求已进入正确版本；
- UI、UX 类型标记正确；
- 当前阶段不误写为已实现。

## 8. S1：现状证据

### 8.1 采集页面证据

最少覆盖：

- Compact：320×700、390×844；
- Medium：768px 宽；
- Wide：1440×900；
- iOS 紧凑、标准和大屏；
- 竖屏与横屏；
- 键盘关闭与打开；
- 默认、空、加载、成功、失败和恢复。

截图必须使用真实渲染页面。内容可以使用隔离测试数据，但不能用纯设计占位图替代
产品状态。

### 8.2 盘点用户任务

按以下格式记录：

```text
用户角色 → 使用情境 → 用户目标 → 入口 → 操作路径 → 业务结果 → 恢复路径
```

示例：

```text
普通用户 → 突然想到一句话 → 保存捕念
→ 所见 / 念起 → 输入 → 保存
→ 列表出现记录且刷新后仍存在
→ 断网时保留草稿并在恢复后同步
```

不得只列“点击按钮、输入文字、点击保存”。

### 8.3 盘点界面内容

收集：

- 页面标题、眉题和副标题；
- 按钮、菜单和标签；
- placeholder；
- 空状态；
- 加载、成功、失败和冲突文案；
- tooltip 和 `aria-label`；
- 动态生成文字；
- 用户内容、来源和 AI 内容标签；
- 普通用户可见的技术或管理信息。

### 8.4 盘点视觉实现

收集：

- 颜色；
- 字体和字号；
- 间距；
- 圆角；
- 边框和阴影；
- 按钮与输入变体；
- 图标来源和尺寸；
- 页面模板；
- 响应式断点；
- 动效时长；
- 共享组件与页面专用组件。

统计结果只是发现漂移的线索。不能仅凭类名数量直接判定设计错误，必须结合真实
页面和任务判断。

### 8.5 G1：证据充分

必须回答：

- 用户第一眼看到什么；
- 首要任务是否明确；
- 用户在开始任务前要做多少判断；
- 页面有哪些不应给用户看的内容；
- 哪些相同组件发生了漂移；
- 哪些状态缺失；
- 手机、桌面和辅助功能分别有什么风险。

## 9. S2：用户任务与信息架构

### 9.1 先写任务，不先画页面

每个页面先完成一句话定义：

```text
用户来到这里，是为了 ________。
```

如果无法只填一个主要目标，检查是否需要：

- 拆成多个页面；
- 把低频能力后移；
- 使用详情或更多菜单；
- 调整导航归属；
- 删除不属于用户产品的管理能力。

### 9.2 页面职责表

```markdown
| 页面 | 首要任务 | 默认展示 | 按需展示 | 不应展示 |
| --- | --- | --- | --- | --- |
| 页面名 | 一句话 | 首层内容 | 更多或详情 | 管理/技术内容 |
```

### 9.3 导航约束

- 最多三级；
- 一级表示稳定生活场景；
- 二级表示内容类型或主要任务；
- 三级只处理当前对象；
- 不新增第四层常驻标签；
- 主任务在所属一级入口内不超过两次操作；
- 移动底栏与桌面侧栏名称一致；
- 返回、刷新和深链保留上下文。

### 9.4 用户与管理界面分离

将页面或能力标记为：

- 普通用户；
- 高级用户；
- Owner / 管理员；
- 开发测试。

架构、商业化、本地测试、供应商密钥、模型档位和底层计费默认属于 Owner 或开发
界面。不得仅通过视觉隐藏，必须有角色或构建边界。

### 9.5 G2：结构冻结

Owner 需要确认：

- 页面职责；
- 一级和二级导航；
- 普通用户可见范围；
- 首要任务；
- 需要删除、后移或拆分的功能；
- 旧链接兼容方式。

G2 通过前不进入高保真视觉设计。

## 10. S3：内容设计

### 10.1 建立文案 inventory

每条文案记录：

| 字段 | 说明 |
| --- | --- |
| 页面 | 所在页面 |
| 状态 | 默认、空、加载、错误等 |
| 当前文字 | 真实展示内容 |
| 职责 | 位置、任务、操作、状态、边界或来源 |
| 判断 | 保留、重写、删除、后移、仅管理端、待验证 |
| 新方向 | 不是最终文案时写表达目标 |
| 证据 | 截图、代码位置或用户反馈 |

### 10.2 删除证明式文案

以下内容不能因为“功能已经实现”而展示：

- “原音频与转写分层保存”；
- “需要时展开麦克风控制”；
- “内容时间线”；
- “最新在前”；
- 每条内容都重复出现的“用户原文”；
- “每周自动尝试，服务需运行”；
- API、ASR、OCR、Worker、Token、模型档位等内部术语。

该信息若有必要，移动到帮助、来源详情、高级设置或管理端。

### 10.3 页面标题检查

逐页检查：

- 导航是否已经说明位置；
- 眉题是否重复；
- 标语是否帮助当前任务；
- 诗意是否损害可理解性；
- 页面是否每次打开都要求用户重读无用文字；
- 标题是否把系统或助手置于用户之前。

### 10.4 错误文案

固定使用：

`发生了什么 + 数据是否安全 + 下一步`

禁止：

- 只有“失败”；
- 直接显示接口异常；
- 用供应商名代替用户结果；
- 让用户猜测是否需要重做；
- 成功与失败同时出现。

### 10.5 G3：文案职责清楚

通过条件：

- 页面每句话都有明确职责；
- 不存在开发证明式文字；
- 普通用户看不到管理端信息；
- 同一概念使用同一名称；
- 原文与 AI 内容在需要时可辨认；
- 空状态和错误有下一步。

## 11. S4：流程与状态设计

### 11.1 绘制主路径

每条流程至少包含：

- 入口；
- 开始；
- 输入；
- 校验；
- 提交；
- 本地保存；
- 服务端同步；
- 后台处理；
- 完成；
- 返回与再次进入。

### 11.2 补齐异常

至少检查：

- 空输入；
- 超长输入；
- 重复点击；
- 慢网；
- 断网；
- 登录过期；
- 权限拒绝；
- 上传中断；
- AI 失败；
- 版本冲突；
- 切换页面；
- 刷新；
- 前后台切换；
- 浏览器或应用被关闭；
- 多标签页；
- 多账户切换。

### 11.3 状态矩阵

```markdown
| 状态 | 用户看见什么 | 可以做什么 | 数据在哪里 | 下一状态 | 恢复方式 |
| --- | --- | --- | --- | --- | --- |
| 编辑中 | 草稿提示 | 继续、取消 | 内存/本地 | 已保存 | 自动恢复 |
```

统一使用：

- 编辑中；
- 已保存；
- 同步中；
- 处理中；
- 已完成；
- 需要处理；
- 失败。

### 11.4 G4：路径闭合

每条主路径必须：

- 有明确完成结果；
- 刷新后仍成立；
- 失败后不破坏数据；
- 能继续、重试或退出；
- 不因 AI 未完成阻塞原始内容；
- 不因连续点击产生重复对象或费用。

## 12. S5：线框设计

### 12.1 移动优先

先设计 390px，再检查 320px，之后扩展到 Medium 和 Wide。

移动线框必须体现：

- 首屏的主要任务；
- 底部导航和安全区；
- 键盘打开后的输入与主操作；
- 一手操作区域；
- 长文本换行；
- 状态信息位置；
- 滚动与返回。

### 12.2 内容优先级

线框只使用灰阶也应能看出：

1. 当前任务；
2. 用户内容；
3. 必要元信息；
4. 次要操作；
5. 系统状态。

若必须依赖颜色才能看出主次，线框不通过。

### 12.3 渐进披露

对每项默认隐藏内容记录：

- 为什么不是首层；
- 用户如何发现；
- 从哪里展开；
- 收起后是否保留；
- 是否记忆上次状态；
- 键盘和读屏如何进入。

### 12.4 G5：层级通过

使用 5 秒检查：

- 5 秒内能否指出页面用途；
- 5 秒内能否指出主操作；
- 5 秒内能否找到返回；
- 5 秒内能否判断当前是否已经保存；
- 5 秒内能否区分用户内容与 AI 内容。

任一失败，返回 S2 至 S4，不进入视觉润色。

## 13. S6：视觉系统与组件

### 13.1 先定义 token

至少定义：

- 语义颜色；
- 字体家族；
- 字号与行高；
- 间距；
- 内容宽度；
- 圆角；
- 边框；
- 阴影；
- 图标；
- 动效；
- z-index；
- 响应式断点。

页面不能自行新增未登记 token。

### 13.2 组件 inventory

至少覆盖：

- AppShell；
- PageHeader；
- PrimaryAction；
- IconButton；
- SegmentedControl；
- Field；
- Composer；
- MediaAttachment；
- RecordListItem；
- RecordDetail；
- SystemStatus；
- EmptyState；
- Dialog / Sheet；
- Menu；
- ChartFrame；
- Toast。

每个组件记录：

```markdown
- 名称：
- 职责：
- 允许变体：
- 尺寸：
- 内容槽位：
- 交互状态：
- 键盘行为：
- 读屏名称：
- 响应式规则：
- 使用页面：
- 禁止用法：
```

### 13.3 无漂移规则

- 同一组件在同一断点使用相同 DOM 结构和 token。
- 选中态不通过改变边框厚度或字号造成尺寸变化。
- loading、徽标和错误图标预留槽位。
- 文案变化使用稳定宽度或容器。
- 媒体加载前后保持宽高比。
- 模板切换时共享锚点位置差异不超过 1px。
- 内容自然增高不算漂移，共享控制区移动算失败。

### 13.4 视觉原则

- 内容先于控件；
- 页面区段默认无卡片；
- 禁止卡片嵌套；
- 卡片圆角不超过 8px；
- 不用胶囊承载普通文字按钮；
- 不用字符或 emoji 冒充通用图标；
- 使用统一线性图标；
- 浅色用于背景，不用于降低正文可读性；
- 不使用渐变球、光斑和无意义持续动画。

### 13.5 G6：系统一致

通过条件：

- 同类组件只有一套基础结构；
- 视觉 token 有来源；
- 页面没有局部新体系；
- 所有状态有对应样式；
- Compact、Medium 和 Wide 均有规则；
- 原型切换无明显漂移；
- 哲学原则已转化为具体界面行为。

## 14. S7：高保真与交互原型

### 14.1 原型必须覆盖

- 正常数据；
- 空数据；
- 长文本；
- 长标题；
- 多图；
- 音频；
- 加载；
- 错误；
- 权限拒绝；
- 冲突；
- 草稿恢复；
- 后台任务；
- 用户原文与 AI 内容并列；
- 320、390、768、1440px。

### 14.2 使用真实内容形状

可以脱敏，但必须保留真实长度、段落、图片比例、标签数量和时间格式。禁止使用
“标题标题标题”“Lorem ipsum”或统一高度假数据验证布局。

### 14.3 原型检查

- 所有按钮可操作；
- 动效方向与状态一致；
- 关闭后焦点返回；
- 返回后保留位置；
- 加载不会改变外框尺寸；
- 键盘不会遮挡主操作；
- 大字体不会截断；
- 无动效模式可完成相同任务。

### 14.4 G7：用户可完成

使用目标用户语言描述任务，不提示按钮位置。至少验证：

- 是否知道从哪里开始；
- 是否理解产品承诺；
- 是否能完成主任务；
- 是否知道内容是否保存；
- 是否能从失败中恢复；
- 是否能解释用户内容与 AI 内容的区别；
- 是否能返回原处。

记录犹豫、误触、回退和询问，不只记录任务最终是否完成。

## 15. 冷启动专项流程

冷启动必须执行以下顺序：

### 15.1 欢迎

- 首屏只显示品牌、一个产品承诺、主按钮和登录入口。
- 不显示功能矩阵、版本、供应商、价格和技术说明。
- 使用全幅环境背景，文字不放在卡片中。

### 15.2 产品介绍

最多三个画面：

1. 先留下；
2. 再看见；
3. 始终由你决定。

每页只包含短标题、两行以内正文、真实产品视觉对象、继续和跳过。

### 15.3 模式选择

- 快速认识：8 题，约 2 分钟；
- 更完整地认识：18 题，约 5 分钟；
- 不使用紧凑分段控件；
- 不自动开始；
- 说明没有标准答案且以后可修改。

### 15.4 逐题

- 一屏一题；
- 移动题目 24 至 28px；
- 桌面题目 28 至 32px；
- 最大正文宽度 620px；
- 中文每行约 18 至 28 字；
- 选项 16 至 18px；
- 答案按钮最小高 56px；
- 移动端四项单列；
- 进度显示为细进度线与 `3 / 8`；
- 顶部返回和底部稍后继续位置稳定。

### 15.5 切题

- 120ms 内显示选中；
- 180 至 240ms 后切到下一题；
- 前进向左，返回向右；
- 位移不超过 16px；
- 同时调整透明度；
- 减少动效时取消位移；
- 切换后焦点进入新题标题；
- 已选答案立即持久化；
- 共享锚点位置差异不超过 1px。

### 15.6 可选资料

- 必答题之后单独询问是否补充；
- 默认提供“先到这里”和“再补充一些”；
- 基本资料、兴趣、自我介绍和已有材料分步；
- 每一步都可跳过；
- 文件导入只在已有材料步骤出现。

### 15.7 初始理解

- 说明它是起点，不是人格结论；
- 先显示用户明确选择；
- 再显示暂时倾向；
- 显示不确定和矛盾；
- 提供修改与否定；
- 不生成类型、分数和标签徽章。

### 15.8 首次行动

只提供：

- 留下一句话；
- 记录现在的状态；
- 先去看看。

进入真实保存流程，不生成样例记录。

## 17. S8：实施交接

### 17.1 交接包

工程开始前必须提供：

- 需求编号和版本；
- 已批准原型；
- 页面与组件映射；
- token；
- 组件状态；
- 文案表；
- 响应式规则；
- 动效参数；
- 可访问性行为；
- API 与数据来源；
- 草稿、同步与后台任务契约；
- 测试选择器要求；
- 验收截图矩阵；
- 不应修改的业务规则。

### 17.2 技术边界

- 优先复用现有业务 API 和状态契约。
- UI 重构不改变用户原文、发生时间、来源、版本和权限语义。
- 视觉组件不得直接调用业务 API。
- 页面不得复制已有组件后局部改样式。
- 旧组件迁移要登记使用页面和删除条件。
- 数据迁移、权限、供应商和生产配置另走对应工程流程。

### 17.3 开发切片

按以下顺序拆分：

1. token 与基础组件；
2. 页面外壳与导航；
3. 一个完整核心流程；
4. 状态与异常；
5. 其他页面迁移；
6. 旧组件清理；
7. 视觉与用户旅程回归。

禁止先同时改完所有页面，再一次性测试。

### 17.4 G8：可以开发

- Owner 已批准结构与视觉方向；
- 所有关键状态有设计；
- 文案已经审计；
- 组件和 token 已定义；
- 手机和桌面都有规格；
- 技术负责人确认可实现；
- 验收用例可执行；
- 未决问题已记录，且不阻断当前切片。

## 18. S9：实施中设计 QA

### 18.1 每个切片检查

- 结构是否与批准原型一致；
- 是否复用了正确组件；
- 是否新增未登记 token；
- 文案是否来自批准清单；
- 状态是否齐全；
- 真实数据是否正常；
- 键盘、焦点和读屏是否可用；
- 多端是否稳定；
- 是否出现组件漂移；
- 是否破坏历史业务行为。

### 18.2 视觉比较

固定截图至少包括：

- 默认；
- 空；
- 长内容；
- 加载；
- 成功；
- 错误；
- 打开菜单；
- 打开键盘；
- 系统大字体；
- 减少动效；
- 320、390、768、1440px。

截图比较必须结合 DOM、业务结果和持久化验证。像素接近不能证明任务正确。

### 18.3 偏差处理

发现实现与设计不一致时：

1. 判断是实现错误、设计遗漏还是技术约束；
2. 不直接用页面专用 CSS 掩盖；
3. 若需改变规范，先更新知识和组件定义；
4. 记录影响页面；
5. 更新基线并重新评审；
6. 再修改实现。

## 19. G9：完成与关闭

UI/UX 任务只有同时具备以下证据才能关闭：

- 需求池状态和技术描述；
- 最终设计与原型；
- 正常、空、加载、失败和恢复截图；
- 手机、桌面和 iOS 证据；
- 真实用户任务结果；
- 刷新后持久化结果；
- 可访问性结果；
- 组件几何检查；
- 文案审计结果；
- 已知偏差和后续项；
- Owner 验收结论。

以下情况一律不能标记完成：

- 只有代码提交；
- 只有单元测试；
- 只有正常状态截图；
- 只有“没有横向滚动”；
- 只有设计稿，没有真实实现；
- 只有实现，没有设计对照；
- 关键异常被列为“以后优化”但未建独立需求。

## 20. 变更管理

### 20.1 设计过程中出现新功能

- 先判断是否属于当前用户任务；
- 属于当前任务且不扩大业务边界时，更新当前需求；
- 改变数据、权限、费用或产品范围时，新增需求并重新评审；
- 不在视觉稿中暗中加入未规划功能。

### 20.2 实施过程中发现旧设计不成立

- 保留证据；
- 回到对应阶段；
- 更新决策记录；
- 重新通过受影响闸门；
- 不以开发进度为由保留明显错误体验。

### 20.3 设计系统变化

任何 token 或基础组件变化都要：

- 说明原因；
- 列出影响页面；
- 更新组件样例；
- 更新视觉基线；
- 执行跨页面回归；
- 删除旧变体或登记退出时间。
