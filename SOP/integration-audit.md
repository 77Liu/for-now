# 集成审计与候选验收 SOP

- SOP 编号：`SOP-DEV-004`
- 版本：`1.0`
- 状态：生效
- 对应阶段：集成审计与验收
- 进入门禁：相关切片均通过 `G3`
- 退出门禁：`G4 候选已验收`

本 SOP 用于把一个或多个已完成切片按依赖顺序集成，并以固定对象验证完整用户
路径、公共契约、兼容性和恢复能力。生命周期定义以
[`knowledge/development-lifecycle.md`](../knowledge/development-lifecycle.md)
为准。

## 1. 角色

| 角色 | 责任 |
| --- | --- |
| 集成负责人 | 固定基线、控制顺序、解决冲突、维护候选 |
| 切片负责人 | 说明变更、证据、依赖和未覆盖项 |
| 独立审阅者 | 从目标和失败路径检查实际 diff 与候选 |
| Owner | 对范围变化、风险接受和关键体验作出决定 |

同一人兼任时，也要把集成、审查和决定分别记录。

## 2. 进入条件

- 本轮冻结范围和验收可查询；
- 相关切片有 `G3` 证据、明确提交/tree 和受影响旅程；
- 公共契约负责人、合并顺序和冲突处理方式已确定；
- 测试端口、数据库、账户、文件和外部服务相互隔离；
- 未完成或阻塞切片已明确排除，且不破坏主要目标；
- 集成工作区不包含来源不明的未提交改动。

## 3. 标准流程

### 步骤 0：固定集成基线

记录：

```text
本轮目标与范围：
集成分支 / 工作树：
起始完整 SHA：
计划接入的切片及 SHA：
排除项：
合并顺序：
共享契约负责人：
系统门命令：
```

先只读核对 `git status`、工作树、分支、标签和各切片提交，不清理其他现场。
再按 [`worktree-lifecycle.md`](worktree-lifecycle.md) 核对活跃工作树不超过
6 个；脏或不完善现场允许保留，已结束工作树进入 reviewer 分类。

### 步骤 1：核对切片交付

对每个切片检查：

- 需求/任务、代码、测试和证据可追溯；
- 实际修改与声明范围一致；
- 共享依赖和兼容要求已声明；
- `partial` / `blocked` 旅程有人工补验或明确排除；
- 没有把外部服务桩、模拟身份或缓存页面写成真实依赖通过；
- 未覆盖项不会使本轮目标失真。

不满足时退回切片，不在集成阶段静默补写结论。

### 步骤 2：按依赖串行集成

1. 先集成共享底座和契约。
2. 每次只接入一个切片或强依赖任务组。
3. 解决冲突时保留双方语义，不以“能合并”代替行为正确。
4. 每次集成后运行受影响专项和跨模块测试。
5. 公共契约变化时暂停后续切片，通知消费者并重新确认兼容。
6. 最终形成可重建的固定集成提交或 tree。

并行任务必须串行进入集成基线；不得让多个 Agent 同时写集成工作树。
已结束但尚未吸收的工作树由 reviewer 按工作树 SOP 审查；只合并仍有必要的
行为，合并后立即运行专项与影响测试，再归档或移除源工作树。
多 Agent 的角色总账、知识交接、通信和热点所有权按
[`multi-agent-orchestration.md`](multi-agent-orchestration.md) 执行；集成
负责人只接收绑定完整 SHA/tree、测试和未覆盖项的交付。

### 步骤 3：运行里程碑系统门

按 [`knowledge/system-testing.md`](../knowledge/system-testing.md) 执行：

- 影响矩阵命中的专项；
- `npm run test:system`；
- 涉及数据库时的 PostgreSQL stable 门；
- 适用的 Journey Daily、浏览器、恢复、真机或外部服务验证；
- 安全、依赖和制品检查。

每个结果绑定当前集成 SHA/tree、环境、命令和产物。测试过程中改动行为代码后，
旧结果失效并从受影响层级重跑。

### 步骤 4：独立审计

审计实际候选，而不是切片摘要：

- 主要目标和冻结范围是否完整；
- 跨模块用户路径是否闭合；
- 权限、账户隔离、隐私和敏感信息；
- 老数据、空数据、重复操作、并发、重启和恢复；
- API/schema/配置/依赖的消费者兼容；
- 日志、指标和审计是否足以判断发布后健康；
- 发布包是否可能夹带调试资产、测试数据或其他任务；
- 回滚代码与数据恢复是否分别成立。

发现阻断问题时退回 `G2/G3` 修复。任何行为修改都必须重新集成并重跑受影响
证据，不能在审计报告中直接“接受”。

### 步骤 5：固定候选清单

至少记录：

- 完整候选 SHA 和 tree；
- 基线、分支、暂存区、未提交与未跟踪文件；
- 版本元数据、依赖锁、Prompt/部署/原生版本；
- 可重建制品及摘要；
- 调试路由、日志、profile、截图和本地数据排除结果；
- 需求、任务、用户旅程和延期项；
- 系统门、真实依赖、恢复和人工补验；
- 当前生产基线及发布前仍需完成的配置和授权。

## 4. `G4 候选已验收`

- [ ] 所有纳入切片通过 `G3`；
- [ ] 合并顺序和公共契约影响有证据；
- [ ] 固定候选的完整路径和系统门通过；
- [ ] 独立审计无未关闭阻断项；
- [ ] 功能、兼容、权限、数据、恢复和可观测性结论明确；
- [ ] 候选 SHA/tree、环境和制品可追溯；
- [ ] 延期项不会破坏本轮主要目标；
- [ ] 发布准备缺口和人工事项已交接。
- [ ] 活跃工作树不超过 6 个；临时 reviewer 工作树已移除，保留现场均有负责人。

通过后状态为“候选已验收”，进入
[`release-and-observation.md`](release-and-observation.md)。这不等于 `G5`
最终 GO，也不授权任何远端或生产操作。

## 5. 证据失效与回退

| 变化 | 最低回退 |
| --- | --- |
| 单切片行为代码或测试变化 | `G3`，随后重新集成 |
| 公共契约、依赖锁、配置或迁移变化 | `G2`，重跑相关系统门 |
| 候选版本元数据或制品变化 | 重新固定候选并核对制品 |
| 只修改说明性文档 | 重跑链接、事实和候选一致性检查 |
| 生产配置或外部依赖状态变化 | 发布流程重新核对对应人工项 |

```markdown
- 独立审计发现及关闭：
- 真实依赖与恢复：
- 延期和未覆盖：
- 发布前人工事项：
- G4 结论：通过 / 退回 / NO-GO
```
