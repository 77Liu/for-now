# 多 Agent 协作协议

目标：一条集成主线、一个协调入口、按需隔离写任务。工作树只隔离文件现场，任务归属和接入由协调者负责。

## 角色与责任

- **协调者/主控**：唯一维护协调控制面、冻结全局状态、裁定范围/冲突/接入与回收；可把代码实现委托给主开发，但不得把控制面写入权隐含转交。主开发拥有被授权任务的代码集成写入权，不拥有全局状态裁定权。
- **开发 Agent/subagent**：在任务卡范围内实现、验证并交接；不自行扩大写集、改变共享契约或合入集成线。
- **验证/审查 Agent**：读取固定候选，报告证据与缺口；默认不写业务文件、不创建工作树。
- **monitor/需求管理**：跟进和提供需求事实；向唯一协调入口交接，不直接维护另一套开发队列或越过协调者派发实现。需求事实可以由需求管理维护，迭代、候选、发布和运行状态只能由协调者写入控制面。
- 角色不等于必须新开聊天或 Agent；串行、小改动、只读任务优先复用现场。跨聊天通信遵守用户已授权的接收方和范围。

## 派发前：判断行为依赖

协调者先读相关实现、调用方、测试与配置，回答：

1. 任务改变谁提供的数据或行为？谁消费它？包括前后端、测试、迁移和外部调用方。
2. 是否涉及公共入口、共享状态、schema、依赖、默认配置？
3. 两项任务各自完成后不兼容时，能局部调整还是推翻对方设计？
4. 是否确实需要同时写代码，且能给出独立验收和明确所有权？

判断依据是实际调用/数据流、共享不变量及反例，不仅是文件重叠。无法证明可独立交付时，先做短侦察或串行共享底座，不凭“不同文件”宣布无冲突。

共享依赖串行完成并验证后，独立完整切片再并行。没有并行写需求就不新建或保留工作树，单写者直接使用唯一 `develop` 工作树；确需独立提交/环境的并行写任务使用各自 feat 工作树。只读调查与审查共享读取即可。

工作树不是第二份主线。一个任务只能有一个活动写入位置；根目录 `develop` 与任意工作树不得同时写同一共享文件集。并行理由消失或任务完成后，协调者在本轮内完成交接和归档，工作树转为只读审计/恢复对象，不得继续开发。

主控掌握全局接入权。工作树可能落后于最新规则、`develop` 契约或其他已接入提交；开发 Agent 只提交自己的事实回执，不能自行认定可合入。主控在合入前负责核对规则基线、实际写集、依赖关系、冲突处理和必要验证，决定串行 merge/commit、选择性提取或归档放弃，确保并行成果在 `develop` 上高质量汇合。

## 工作树边界

每个写任务在开始前必须登记“允许写集、明确禁写集、共享文件负责人、接入顺序”。工作树只能写允许写集；共享契约、默认配置、构建/部署入口、`.gitignore` 和控制面等文件默认属于协调者的串行写集，功能工作树只能读取，除非任务卡明确转移唯一写入责任。发现越界或与另一活动写集重叠时，立即停止该任务写入并回报；协调者先拆分或串行整合，再允许继续。合入 `develop` 前按实际差分复核边界，边界不清或重叠未裁定不得合入。

## 任务下达协议

```text
任务：具体用户问题、做什么/不做什么
模式：只读调查 / 实现 / 验证 / 审查
基线：分支 + 起始 commit；规则来源及生效日期
负责人：唯一实现者；协调者
权限与写集：读写权限、允许文件/模块、禁止修改的共享范围
接口约定：输入、输出、错误、数据格式与共享不变量
依赖：已满足的前置、消费者、预定接入顺序
验收：行为结果、失败恢复、契约与专项验证
交接：差分/提交、实际测试、风险、未提交内容、建议接入方式
```

只读任务可省略写入字段的细节，但明确“无写权限”。当前任务、队列、候选与运行状态只登记在[唯一协调控制面](../knowledge/coordination-control-plane.md)，由协调者通过指定入口更新；有意义派发与结果追加到版本事件。链接的任务卡只承载契约、设计及事实证据，不另维护当前状态。不再复制角色知识账、资源账或另一张进度表；开发 Agent 交接的是事实回执，不是要求协调者照抄其本地状态。

## 事中：监督与契约变更

开发者发现必须改签名、schema、公共状态或越过写集时，先向协调者说明原因、消费者和最小方案；不得静默修改，也不为绕过限制造重复函数。
协调者只暂停受影响的写任务，保存检查点；串行修订共享契约并验证生产者/消费者，提交到 develop 后通知相关任务接收新基线。无关任务可继续。
能安全 merge/rebase 的既有工作树继续使用；只有旧方案已不适配时才归档并重开，不把“全部丢弃重做”设为默认流程。

## 接入与同步

### 开发者自查与主控接入审查

生效：2026-10-12。代码质量不能主要依靠运行暴露遗漏后补修；开发者自查和主控代码审查是明确责任，验证用于确认审查结论，不能替代审查。

1. **开发者完成编辑后先自查，再运行相关验证和交接。** 阅读实际差分及依赖实现，沿完整数据链核对生产者、转换/存储、读取/重建与真实消费者，确认输入输出形态、字段类型、身份/引用、业务顺序及适用失败恢复契约。查找已有实现并说明沿用或改变的依据；不能只检查新函数或自建夹具。
2. **主控作为接入者，合入前必须亲自、独立地仔细审查实际代码及相关调用方。** 跨聊天回复、开发者自查和其他审查者结论仅为审查输入，主控不得照抄结论或据此直接接入；必须自行读取当前候选实际差分、依赖实现和真实消费者，对照代码核实交接声明并形成自己的质量判断。核对真实返回形态、既有实现和接入后的消费者兼容。涉及数据库、持久化、脱敏或状态转换时，必须追到实际读取、重建、重新映射与消费环节；区分数据库返回顺序与业务顺序，核对转换是否保留所依赖的引用、匹配和状态语义。不得只阅读交付摘要或测试结果。
3. 自查和接入审查在既有交接回执中简要记录：检查的实际入口/消费者、关键契约、发现与处理、未确认边界。类型检查通过、自测通过或独立审查 GO，都不能替代具体代码契约审查；独立审查也不能转移开发者与主控的责任。不另建审查报告链或重复测试矩阵。
4. 发现实现或契约问题，主控拒绝接入并退回原开发者，在同一 feat 上修正；修改后重新审查差分并只补受影响验证。不能用改报告、放宽断言、忽略字段或连续线上试错代替修复。确需运行才能确认的环境问题，先明确静态审查已确认的契约与剩余未知，再执行最小验证；未知不能写成可用。

- 可独立验收的切片完成后尽早进入接入队列；未完成验收的半成品不因抢时间而合并。
- 协调者串行处理合并：核对写集/依赖 → 完成上述接入审查 → 在当前 develop 上组成实际候选 → 处理冲突并审查结果 → 相关验证 → 合入。
- 基线测试只证明原候选。接入时复用仍有效证据，补集成后受影响行为；有冲突或契约变化必须验证其结果。
- 正在开发的 Agent 不必等全部分支完成。只有 develop 新变化影响其契约/实现或接入验证时才安排同步；不要每个提交都广播全量重测。
- 从更新后的 develop 接收变化允许包含已集成的功能；它们已是公共基线。禁止从尚未集成的 feat 建立、merge、rebase 或 cherry-pick 出依赖 feat。
- 合入后通知相关任务新基线、变化边界和证据位置，完成交接并归档已结束工作树。

## Git 分支

| 分支 | 来源与归宿 | 写入责任 |
| --- | --- | --- |
| main | 接收完成发布的 release/hotfix；用标签和运行证据定位生产 | 协调/发布执行者，不直接开发功能 |
| develop | 唯一功能集成线；可从同一或不同提交切 feat | 协调者；共享底座串行写入 |
| feat/xxx | 从 develop 切出，验收后回 develop；业务、测试、构建和工具代码均在此完成 | 唯一开发负责人 |
| release/xxx | 从 develop 冻结；只承载候选引用和发布验证结果 | 唯一发布负责人 |
| preview/xxx | 只定位预览候选和预览部署对象，不产生开发提交 | 协调者/发布执行者 |
| hotfix/xxx | 只跟进生产热修候选和回流，不在其上直接写修复代码 | 协调者/热修负责人 |
| docs/xxx | 只承载文档提交，审查后回 develop | 文档负责人 |

五类受保护分支（main、release、preview、hotfix、docs）都不是普通开发起点；需要改代码时回到 develop 或从 develop 创建 feat。具体约束以[远程分支规则](../knowledge/remote-branch-policy.md)为准。
热修在发现影响生产的问题时立即处理；图中的开发早期案例不是限制热修发生时间的规则。
功能工作树只能从 develop 创建；release/hotfix 为上表定义的发布隔离例外，由协调者管理，均不得从未集成 feat 派生。
