# 功能切片开发 SOP

- SOP 编号：`SOP-DEV-003`
- 版本：`1.1`；生效：2026-10-12
- 状态：生效
- 对应阶段：小批开发与持续测试、审查
- 进入门禁：`G2 开发已就绪`
- 退出门禁：`G3 切片已完成`

本 SOP 适用于功能、缺陷、重构、测试和普通文档切片。生命周期以
[`knowledge/development-lifecycle.md`](../knowledge/development-lifecycle.md)
为准，代码与提交边界以
[`knowledge/engineering-rules.md`](../knowledge/engineering-rules.md) 为准。

## 1. 进入条件

开始实现前必须具备：

- 任务 ID、目标、范围和非目标；
- 起始提交或 tree、工作树及已有改动归属；
- 允许修改的模块、共享契约和文件所有权；
- 成功、失败、中断、恢复、权限、持久化及副作用验收；
- 受影响用户旅程、验证层级与实际命令；
- 风险预验证结果、外部依赖和授权边界；
- 提交、集成及需要升级报告的条件。

任一关键项缺失时退回
[`iteration-planning.md`](iteration-planning.md)，不得以实现过程代替规划。

## 2. 标准循环

```text
固定任务基线
→ 复现问题或建立失败断言
→ 完成最小纵向改动
→ 开发者沿完整数据链自查实际代码
→ 运行相关检查与旅程
→ 主控接入审查实际代码与契约
→ 修复并复验
→ 整理 G3 证据
```

### 步骤 0：固定任务现场

记录：

```text
任务 ID：
目标与验收：
分支 / 工作树：
起始 HEAD / tree：
已有未提交改动及归属：
允许修改：
禁止修改：
依赖和授权：
```

执行 `git status --short --branch` 并搜索现有实现、测试和相邻模式。不得回退、
格式化、移动或提交其他任务和用户的改动。

按[工作树生命周期](worktree-lifecycle.md)核对隔离理由、写集和回收条件；不按角色数量开树，不为腾名额丢弃现场。

使用多个 Agent 时，同时按
[`multi-agent-orchestration.md`](multi-agent-orchestration.md) 固定任务图、
角色知识、文件所有权、通信信封和交接条件。并行开发者必须使用隔离工作树，
reviewer 与思考秘书默认只读。

### 步骤 1：验证症状与关键依赖

- Bug 优先稳定复现或建立修复前失败的断言。
- 新能力先核对真实消费者与既有契约；已确认存在的不确定依赖才做必要预验证，不固定新增预检轮次。
- 可以用桩验证业务逻辑，但必须单列真实依赖缺口。
- 环境失败与业务失败分别记录，不因更换环境后通过就声称根因已修复。

验证失败且会改变方案时退回 `G2`；影响本轮目标或范围时退回 `G1`。

### 步骤 2：实现最小纵向路径

优先让一条用户路径完整成立，例如：

```text
用户操作 → HTTP / 领域逻辑 → 持久化
→ 页面结果 → 刷新或重启后仍成立
```

执行要求：

- 复用现有架构、组件、数据契约和错误表达；
- 共享 schema、API、认证、配置、入口和依赖锁由唯一负责人修改；
- 结构整理与行为变化的拆分及不可分割修复例外，统一按[工程规则](../knowledge/engineering-rules.md#34-模块与跨模块修改)执行；
- 不顺手处理无关问题；记录到需求池或后续任务；
- 用户输入、网络、文件、外部服务和持久化处理真实失败；
- UI/UX 变化同时执行 [`ui-ux-optimization.md`](ui-ux-optimization.md) 的
  适用阶段。

### 步骤 3：持续验证

每个可理解小批次完成后，先按[协作协议的自查要求](multi-agent-orchestration.md#开发者自查与主控接入审查)检查实际代码与完整数据链，再执行适用验证：

1. 运行语法/静态检查和领域专项；
2. 运行受影响的 Journey Smoke；
3. 检查业务结果、持久化、失败恢复和副作用；
4. 页面改动检查适用视口、键盘、控制台和网络；
5. 记录实际命令、对象、时间、结果和未覆盖项。

具体选择与层级以[测试影响矩阵](../knowledge/test-impact-matrix.md)为准；命令见[系统测试](../knowledge/system-testing.md)，旅程方法见[用户旅程](../knowledge/user-journey-testing.md)。普通切片不以无差别全量测试替代精准验收。

### 步骤 4：审查

主控按[协作协议的接入审查要求](multi-agent-orchestration.md#开发者自查与主控接入审查)审查实际差分、依赖与真实消费者，核对目标/非目标、写集、权限、隐私、费用、失败恢复和兼容边界。高风险切片使用独立审查视角，责任仍由开发者和主控承担；发现问题退回实现、重新自查并补相关验证。

### 步骤 5：处理范围变化

开发中发现新信息时：

- 不影响当前目标：记录候选需求，当前切片不扩范围；
- 在当前边界内必要：更新任务契约、验收和测试后继续；
- 改变公共契约、主要目标、安全或数据正确性：暂停并退回 `G1/G2`；
- 无法安全完成：缩小范围或标记阻塞，保留现场和恢复条件。

### 步骤 6：形成检查点与提交

- 连续工作按工程规则形成可恢复检查点。
- 按[本地提交规则](../knowledge/commit-and-release-rules.md)组织原子提交，不另设文件或行数提交触发线。
- 只暂存本任务文件；提交权限、门禁和命名按工程规则执行。
- 本地提交不推进发布状态，也不授权 push、tag、Release、部署或生产写入。

## 3. `G3 切片已完成`

全部满足才能通过：

- [ ] 任务目标和逐条验收已满足；
- [ ] 成功路径和关键失败/恢复路径有实际证据；
- [ ] 受影响旅程及本次验证层级已记录；
- [ ] 相关检查通过，无未解释的跳过或弱化断言；
- [ ] 实际 diff 已审查，无越界或无关改动；
- [ ] 共享契约、数据、权限、隐私和费用影响已处理；
- [ ] 工作区、提交或 tree 可精确恢复；
- [ ] 工作树符合生命周期约定；本切片有明确接入或归档去向，分支保留；
- [ ] 未覆盖项、剩余风险和后续条件已明确；
- [ ] 交付状态写为“待集成”，没有误报已发布。

## 4. 交付模板

```markdown
## 切片交付
- 任务 ID：
- 起始 / 结束 SHA 或 tree：
- 实际改动：
- 用户结果：
- 受影响旅程：
- 实际验证：
- 审查结论：
- 未覆盖与风险：
- 公共契约 / 合并顺序：
- 工作区与提交状态：
- 下一状态：待集成 / 阻塞
```

通过后交给 [`integration-audit.md`](integration-audit.md)。阻塞时保留当前 HEAD、
工作区、失败证据、已尝试方案和解除条件。

## 5. 禁止事项

- 未通过 `G2` 就开始大范围实现；
- 用代码存在、按钮可见或接口 200 代替用户结果；
- 为通过而删除测试、吞错、放宽阈值或无限重试；
- 在多个并行任务中修改同一共享契约；
- 把本地验证、提交或 Preview 体验写成生产完成；
- 在热修中混入普通功能，或在普通切片中绕过热修止损流程。
