# 发布与观察 SOP

- SOP 编号：`SOP-DEV-005`
- 版本：`1.0`
- 状态：生效
- 对应阶段：上线与观察
- 进入门禁：`G4 候选已验收`
- 决策门禁：`G5 最终 GO`
- 退出门禁：`G6 发布已关闭`

本 SOP 是发布阶段的操作入口。双轮检查、人工确认、证据失效、Git/Gitee、
部署和观察的完整规则以
[`knowledge/pre-launch-confirmation.md`](../knowledge/pre-launch-confirmation.md)
为准；逐项阻断检查以
[`knowledge/development-release-checklist.md`](../knowledge/development-release-checklist.md)
为准。本文只规定阶段交接与执行顺序，不复制详细检查项。

## 1. 进入条件

- 集成候选已通过 `G4`，完整 SHA/tree 固定；
- 当前生产版本、数据写源、服务和已知风险明确；
- 发布记录已建立，目标、范围、非目标和回滚责任明确；
- 真实依赖、迁移、备份、恢复、费用和设备授权边界明确；
- 工作区其他改动不会进入候选。

任何条件不满足时停止推进，不使用浮动分支名或“最新代码”代替发布对象。

## 2. 标准流程

```text
G4 候选已验收
→ 第一轮实现完整性检查
→ 人工配置与风险预确认
→ 冻结发布候选
→ 第二轮独立发布审计
→ 文档与发行说明同步
→ G5 Owner 最终 GO
→ Git / Gitee 发布
→ 生产部署与冒烟
→ 观察
→ G6 发布关闭
```

### 步骤 0：建立发布记录

使用 `reports/pre-launch-YYYY-MM-DD-<name>.md`，记录：

- 发布目标、范围、非目标和验收；
- 生产基线、候选 SHA、风险等级和责任人；
- 数据、API、认证、附件、AI、第三方和部署影响；
- 测试、人工验收、迁移、回滚和观察条件；
- 已知未提交改动及归属。

### 步骤 1：完成第一轮检查

按发布流程重新读取规则、映射验收、执行测试和详细清单。第一轮允许修复问题，
但任何行为、依赖、迁移或部署脚本变化都会使 `G4` 相关证据失效，必须退回
开发/集成流程重新形成候选。

### 步骤 2：人工介入与预确认

向 Owner 提交脱敏清单：

- 范围、时间、维护窗口和允许中断；
- 隐私、运营、费用、邀请和风险接受；
- 生产身份、环境、认证、云服务、证书、备份和设备；
- 未执行项目、剩余风险、责任人和补验条件。

预确认只授权进入第二轮审计，不授权 push、tag、Release、部署或生产写入。

### 步骤 3：冻结并执行第二轮

- 从固定候选和干净环境重新建立判断；
- 核对版本、依赖、制品、调试资产、配置存在性和延期项；
- 重跑 Release 门及已授权的真实依赖、恢复和真机验证；
- 从失败角度复查权限、数据、回滚、资源和可观测性；
- 第二轮发现行为问题时返回第一轮，并重新经过 `G4`。

### 步骤 4：执行 `G5 最终 GO`

Owner 决策前必须提供：

- 候选完整 SHA、生产基线和变更范围；
- 两轮检查与 Release 门结果；
- 人工配置、备份恢复和回滚证据；
- 中文发行说明、目标标签和上一发行版；
- 未执行项目及已接受风险；
- 准备执行的具体远端和生产动作。

同时按 [`worktree-lifecycle.md`](worktree-lifecycle.md) 确认活跃工作树不超过
6 个，发布候选工作树干净且唯一，其他保留现场不会进入制品。

只有 Owner 对本次具体动作明确授权，`G5` 才通过。历史授权、模糊“继续”、
本地提交或测试通过均不能替代。

### 步骤 5：Git、Gitee 与生产发布

严格按发布流程和 `deploy/README.md` 执行：

1. 核对并 push 指定提交；
2. 创建不可变标签及同标签 Gitee Release；
3. 核对 Release URL、完整目标 SHA、比较基线和固定栏目；
4. 发布前只读核对生产、备份、磁盘、告警和配置；
5. 部署指定 SHA，不在活动 release 中临时修代码；
6. 验证 `/readyz`、运行版本、静态资源和关键用户路径；
7. 失败时按预定触发条件停止、回滚或恢复。

### 步骤 6：观察

观察窗口和信号按风险制定。低流量产品必须主动执行关键路径，不能只看进程：

- 健康、错误率、P95、重启、CPU、内存、磁盘；
- 核心创建/读取/编辑/恢复及账户隔离；
- 数据、附件、任务、AI、第三方和费用异常；
- 日志、告警、备份和回滚路径；
- 用户可见回归与移动端关键入口。

出现生产异常时进入 [`hotfix.md`](hotfix.md)，保留当前发布对象和观察证据。

### 步骤 7：执行 `G6 发布已关闭`

- [ ] 远端分支、标签、Gitee Release 和运行 SHA 一致；
- [ ] 生产冒烟和适用真实依赖通过；
- [ ] 观察达到退出条件，无未处置阻断信号；
- [ ] 最终结论为继续运行、已回滚或修复后重新观察；
- [ ] 发布记录包含时间、指标、异常、决策和遗留项；
- [ ] 原迭代计划已追加最终发布结论；
- [ ] 本地 `main`、旧工作树和归档状态已按
      [`worktree-lifecycle.md`](worktree-lifecycle.md) 核对，活跃工作树不超过 6 个；
- [ ] 当前状态与长期文档已按单一事实来源更新。

只有结论为“继续运行”且上述关闭项完成，发布状态才为“已关闭”。部署成功但
仍在观察时只能写“已发布 / 观察中”。

## 3. 交接

`G6` 通过后进入
[`iteration-retrospective.md`](iteration-retrospective.md)。本轮未发布时，也可
在明确截止对象后复盘已完成的本地或 Preview 里程碑，但不能补写生产结论。

## 4. 禁止事项

- 检查 A、发布 B；
- 只有 Git 标签，没有对应 Gitee Release；
- 以旧备份存在代替当前候选的恢复验证；
- 只确认进程存活，不验证用户关键路径；
- 应用回滚时忽略不可逆数据迁移；
- 把 Preview、模拟身份或桩服务证据写成生产通过；
- 观察未结束就关闭发布或开始下一迭代。
