# 发布与观察 SOP

版本：1.5；生效日期：2026-10-16。本文是发布动作、授权核对、故障续做和关闭的唯一流程正文。风险等级与自动生产动作以[发布自动授权策略](../knowledge/release-authorization-policy.md)为准；适用检查项见 [上线清单](../knowledge/development-release-checklist.md)，分支角色见 [Git 规则](../knowledge/remote-branch-policy.md)。当前状态只由协调者写入[唯一控制面](../knowledge/coordination-control-plane.md)。

## 职责与执行边界

- 协调者：核对候选、证据与授权，建立 attempt，安排执行，并独占状态更新。
- 审查者：审查实际候选、用户行为和失败恢复，提交可核对的结论；不得以开发者摘要替代差分。
- 发布执行者：只执行收到的候选/环境/attempt，产出外部回执；不自行改变范围、授权、候选或控制面。
- Owner：决定质量与风险边界，可给明确的持续授权并随时暂停/撤销。已覆盖的动作无需逐次再问；未覆盖的动作才需补充决定。放权等级已确定，但只有启动前条件完成且控制面记录策略后，自动生产动作才可启用。

以下动作名是统一操作契约，**不是已经实现或安装的 CLI 命令**。工具未实现时由执行者按现有命令履行同一契约；自动执行前须确认所依赖的保护、核验、回执及恢复能力真实可用。不能因写了 SOP 就声称已有无人值守流水线。

版本更新统一在固定候选及构建前通过 `npm run release:set -- <版本号>` 完成；由[版本元数据脚本](../scripts/sync-release-metadata.mjs)同步字段，并在版本号变化时递增 iOS build number。`release:sync` 仅同步已有值，`--check` 仅检查一致性，均不能替代版本更新；不得手改版本后用同步或检查代替该入口。

## 顺序与动作契约

`verify → freeze → authorize → publish → deploy → observe → close`

`verify` 和 `freeze` 之间必须完成[测试影响矩阵的有状态全局测试门](../knowledge/test-impact-matrix.md#develop--release-有状态全局测试门)。该门从 develop 的固定候选、脱敏生产快照及本机隔离 PostgreSQL 验证开始；通过后才允许冻结 release。其正文、范围及证据复用只在矩阵维护。

| 动作 | 输入及必须成立的条件 | 结果回执与状态责任 |
| --- | --- | --- |
| `verify` | 确定范围、commit/tree、测试选择依据、已有证据和真实缺口；只补受影响验证及审查 | 执行者提交验证/审查证据，协调者判定通过、退回或未完成；不触发外部写入 |
| `freeze` | 有状态全局测试门已通过；verify 所绑定的代码/依赖/配置/环境没有漂移，制品与快照摘要可追溯 | 协调者固定候选 ID、SHA/tree、制品/配置引用及 release 引用；引用名不替代身份 |
| `authorize` | Owner 决定的原始引用及覆盖的环境、动作、数据范围、预算、窗口/失效条件、回滚权限均可核对 | 协调者判断本 attempt 是否已在授权内；测试通过不产生权限；超范围只暂停对应动作 |
| `publish` | 已授权且候选与远端目标一致；审查和保护要求满足 | 推送指定候选引用；需要时创建不可变 RC 标签和候选发行记录；保存远端 SHA、对象 ID/URL，不提前写正式 main |
| `deploy` | 指定制品和目标环境，实际运行基线已核对；适用备份/恢复、兼容性、开关和回滚条件有效 | 部署固定对象，执行对应冒烟，回传实际运行 SHA/摘要及变更回执；进程启动不等于用户任务成功 |
| `observe` | 已部署对象与观测对象一致；关键路径、错误、资源/费用和回退触发条件已定义 | 记录样本、持续时间、异常和限制；满足退出条件才建议关闭，缺样本不伪称长期达标 |
| `close` | 观察结论成立，外部动作无未决回执，正式制品身份可核对 | 按授权创建正式不可变 tag/Release、推进 main 到已正式发布提交；协调者核对远端/运行对应关系，完成下述正式发布回流后关闭，并登记反馈 |

候选上传、生产部署和正式发布完成是不同事实。为满足 main 只含正式版本的规则，普通候选先经 release/preview 路径核验；main 在正式晋级时推进。现有部署器若只接受先推 main，须先调整适配方案并验证，不能提前把候选推入 main 冒充已经正式发布。

正式 tag 可在完成观察后指向已运行的精确提交，无需再次部署。若托管平台不支持候选/预发行模式，publish 只上传候选引用；正式发行记录留到 close 创建。不创建一条假正式 Release 充当占位。关闭过程中发布记录创建失败，保留“已部署，发布元数据待补齐”，不盲目重新部署。

## 正式发布回流与下一版起点

正式发布晋级 `main` 后，必须按顺序完成：**核对正式发布节点 → 正常合并回 `develop` → 核对回流结果 → 确定下一版基线 → 从该基线创建 `feat/*`**。发布合并节点尚未进入 `develop` 时，不得将下一版基线标记为已固定或启动其实现。

1. 协调者获取对应远程的最新 `main` 引用，核对实际晋级提交、正式 tag、发布候选和运行回执；区分发布提交与平台额外产生的合并提交，不按分支名或文件树相同推定祖先关系。
2. 在 `develop` 执行正常合并，保留已有开发提交、未提交改动与双方历史。不得以 reset、rebase、squash、强推或仅标记已合并的策略代替回流；不得覆盖工作区或删除分支。未提交内容影响合并时，先明确归属并保护现场，再继续。
3. 有冲突时逐项审查发布侧与开发侧的实际契约，保留双方有效工作；有实现差异时按测试影响矩阵补必要验证。只有合并关系变化、文件树未变时，核对祖先和树一致性即可，复用有效业务验证，不重测或重部署。
4. 确认正式 `main` 节点已是 `develop` 的祖先，核对合并前后差分，记录发布节点、回流提交、冲突处理及验证结论。已在祖先链中时只核验，不制造重复合并。
5. 协调者通过唯一控制面更新入口记录回流实际结果，再基于回流后的最新有效 `develop` 确定下一版起点及规则基线；下一版范围仍须另行确认。未完成回流时保留“已正式发布、开发线回流待完成”，不冒称收口完整。

本地回流不自动授权远程推送；需要推送 `develop` 时仍核对已有授权和远程保护。本条仅规定发布后的集成顺序，不改变各分支职责，不从 `main` 创建普通功能分支。

## 每次外部动作

1. 读取控制面 revision、工作模式、候选和 attempt；确认 Owner 没有暂停/撤权、运行基线没有被另一任务改变。
2. 核对“目标环境 + 候选 + 操作”的已有回执，确定是首次执行还是恢复未完成动作。同一目标不并发部署。
3. 只执行授权动作，保存脱敏回执；协调者核对后推进当前状态。状态回写失败不意味着外部动作未发生。
4. 网络超时或响应丢失先查询远端实际状态：tag 已存在则核对目标，部署则核对运行身份，迁移则核对事务/账本。未知结果不盲重试，尤其不能重复付费或数据写入。

本协议要求执行者这样操作，不宣称目前已有自动幂等、并发锁、持久队列或机器人权限。后续工具实现必须按契约验证其实际能力。

## 失败与返回位置

| 发现的问题 | 停止范围 | 返回位置及恢复条件 |
| --- | --- | --- |
| 需求/范围/验收有歧义 | 受影响切片 | 需求选择与范围确认；其他无关任务继续 |
| 行为缺陷或失败断言 | 相关候选 | develop/feat 修复；审查及影响验证通过后重新 freeze |
| 公共契约/依赖/版本/制品变化 | 消费该变化的候选 | 开发或集成，生成新候选身份；复用未失效证据 |
| 环境/工具不可用 | 相应验证或部署动作 | 环境恢复；保留失败与 partial，不改成产品通过 |
| 授权缺失、过期或范围不符 | 对应外部动作 | authorize；取得覆盖范围的决定后继续原有效候选 |
| push、tag、发行记录失败/结果未知 | 对应 publish/close 动作 | 查询外部回执，只补缺少部分，不重新跑全部测试或部署 |
| 部署或观察触发回退条件 | 本环境的发布与放量 | 在授权内停止/关闭功能/回滚；数据恢复单独核对，不将代码回滚冒充数据回退 |
| 只有说明文档修正 | 对应 feat 的文档差分 | 随对应实现或规则在 feat 完成并审查；验证选择遵循测试影响矩阵 |

## 验证、partial 与收尾

复用对象、依赖、配置及相关环境未变的证据；不固定双轮、不因为阶段名变化重跑全量。适用恢复证据要能支持本次变更，不能仅凭存在旧备份放行。

partial 记录未验证的行为、原因、可能影响、补验条件和责任人。它既不等于通过，也不一律阻断所有工作；是否影响当前发布由实际用户损害及已明确的风险决定判断，执行者不能自行豁免权限/数据故障。

暂停立即停止新的派发和生产变更；对已经在途的动作先获取结果并按现有授权保护现场，不将暂停自动解释为回滚/删除数据。恢复后从最后确认的回执继续。

观察后仍需分别核对技术运行和产品验收；没有用户价值反馈时不写需求验收完成。收尾只向控制面提交证据，由协调者更新状态、安排规则/需求回流和工作树回收。报告保留当时事实，其他文档只引用控制面。

项目记录的对象标识遵循[完整哈希与展示简称约定](../knowledge/coordination-control-plane.md#项目记录的哈希与集合差量)，Git 与工具协议必需标识不截断。
