# Git 工作树生命周期 SOP

- SOP 编号：`SOP-DEV-006`
- 版本：`1.0`
- 状态：生效
- 适用阶段：`G0-G7` 全部门禁、并行开发、串行集成与版本收尾

本 SOP 是工作树盘点、审查、合并、归档和移除的唯一操作来源。其他 SOP 只检查
门禁结果并引用本文，不复制处理步骤。工程、提交和远端授权边界继续以
[`knowledge/engineering-rules.md`](../knowledge/engineering-rules.md) 为准。
多 Agent 的角色、知识、通信和文件所有权由
[`multi-agent-orchestration.md`](multi-agent-orchestration.md) 约束。

## 1. 硬门与定义

任何 `G0-G7` 门禁判定时，当前仓库的**活跃工作树不得超过 6 个**。创建新工作树
前也要执行同一检查；已有 6 个时，必须先收尾、归档或移除一个，不能先创建再补
治理。

```bash
git worktree list --porcelain
```

计数以 `worktree` 条目为准，包含根工作区、主线集成工作树、平台工作树、临时
reviewer 工作树和功能工作树。仅保留在 `refs/heads` 或 `refs/tags` 中、但没有
注册工作目录的分支/标签不计为活跃工作树。

多 Agent 调度不能绕过该上限。reviewer 和思考秘书默认只读且不创建工作树；
并行开发者只有取得空闲槽位、独立文件所有权和明确收尾条件后才能创建隔离
工作树。

状态定义：

| 状态 | 判定 | 处理 |
| --- | --- | --- |
| 活跃 | 当前正在实现、审查、集成、发布或必须立即恢复 | 保留，记录负责人、HEAD、下一步 |
| 不完善 | 有未提交内容、未合入提交、失败证据或明确后续任务 | 保留现场，不强制清理 |
| 待合并 | 工作树干净，存在主线未吸收且仍需要的提交 | reviewer 审查后串行合并并测试 |
| 已结束且有意义 | 已被主线吸收，但分支/标签有追溯价值 | 保留 ref，移除工作树 |
| 已结束且无意义 | 已被主线吸收或内容为空，且无独立追溯价值 | 移除工作树后用安全删除移除本地分支 |
| 可修剪 | 注册记录指向已消失目录，且无待恢复现场 | 核对后执行 prune |

“分支落后主线”“同名提交不同哈希”或 `git cherry` 显示 `+` 都不能单独证明需要
合并；必须比较实际行为、测试和最终文件。相同功能经重写、rebase、squash 或
串行集成后，提交哈希可以不同。

## 2. 角色

| 角色 | 责任 |
| --- | --- |
| 工作树负责人 | 说明任务状态、未提交内容、验证证据和恢复条件 |
| reviewer | 独立比较分支与主线，判断必要提交并批准或拒绝接入；默认只读 |
| 集成负责人 | 保护本地 main、控制合并顺序、运行合并后测试 |
| Owner | 决定有争议的范围、风险、无来源脏现场和远端/生产动作 |

reviewer 不以分支名、提交标题或“看起来已完成”代替 diff、patch 等价和测试证据。
同一 Agent 从 reviewer 切换为集成负责人后可以执行合并，但必须先提交审查结论
并记录角色切换；写入后的结果需要另一独立 reviewer 复核。

## 3. 标准流程

### 步骤 0：冻结清单

先记录全部工作树，不删除、不 reset、不 stash：

```bash
git worktree list --porcelain
git branch --all --verbose --no-abbrev
git stash list --date=iso-local
```

对每个工作树记录：

- 绝对路径、分支、完整 HEAD；
- `git status --porcelain=v1`；
- 相对 `origin/main` 或所属产品线主线的 ahead/behind；
- `git cherry <main> <branch>` 与独有提交；
- 最后提交、任务状态、已知测试和未覆盖项。

平台、中台或孤儿产品线使用自己的远端主线比较，不能错误合入主应用 main。

### 步骤 1：先保护脏现场

只要工作树有未提交或未跟踪内容：

1. 不使用 `git worktree remove --force`。
2. 不 reset、checkout 或清理未知文件。
3. 读取 diff、文件归属、调试目录和最近提交，判断是否仍可恢复。
4. 明确记录负责人、任务、阻塞、下一步和保留理由。
5. 只有内容已确认可丢弃，且 Owner 明确授权时，才能删除。

不完善工作树可以保留。数量超门时优先收尾干净历史工作树，不能为了凑数破坏脏
现场。

### 步骤 2：识别主线是否已经吸收

按以下证据由强到弱核对：

1. `git merge-base --is-ancestor <head> <main>`；
2. `git cherry <main> <branch>` 的 patch 等价；
3. 同主题主线提交与分支提交的 `git range-diff` / 文件 diff；
4. 最终主线是否包含同一业务行为、失败路径和回归断言；
5. 主线候选或生产证据是否已经验证该行为。

若主线实现更新、更完整，旧分支的同主题提交不再合并；保留 ref 作为历史，移除
工作树。若仍有独有必要行为，进入 reviewer 合并流程。

### 步骤 3：reviewer 批准、集成负责人串行合并并测试

1. reviewer 写明分支意图、必要提交、冲突和风险。
2. 集成负责人依据审查结论执行合并；reviewer 不直接写集成工作树。
3. 本地 `main` 先快进到已核对的 `origin/main`；本地有合法领先提交时保留并
   记录，不覆盖。
4. 一次只合并一个工作树。共享契约先于消费者，禁止多分支同时写主线。
5. 合并后立即运行该分支专项、受影响 Journey Smoke 和必要系统门。
6. 测试失败时停止后续合并，保留失败提交和证据；用新修复或显式 revert 处理，
   不使用历史重写掩盖失败。
7. 测试通过后记录主线 SHA、命令、结果和未覆盖项，再处理源工作树。

合并、测试和本地主线移动不授权 push、tag、Release、部署或生产写入。

### 步骤 4：归档或删除

工作树必须干净，且必要提交已进入主线或可靠归档后，才执行：

```bash
git worktree remove <path>
```

禁止默认使用 `--force`。

有意义的历史：

- 已有 release、archive、远端分支或标签时保留现有 ref；
- 只有临时功能分支但需要追溯时，先创建
  `archive/<topic>-<YYYYMMDD>` 指向完整 HEAD，再删除原本地分支；
- 核对 `git cat-file -e <archive-ref>^{commit}` 后再移除工作树。

无意义的历史：

- 工作树移除后只使用 `git branch -d <branch>`；
- `-d` 拒绝时返回审查，不改用 `-D` 绕过；
- 删除远端分支仍需单独授权。

工作目录已不存在时，先确认没有待恢复文件，再执行：

```bash
git worktree prune --dry-run
git worktree prune
```

### 步骤 5：复核硬门

清理后重新读取：

```bash
git worktree list --porcelain
git status --short --branch
```

必须证明：

- 活跃工作树 `<= 6`；
- 每个保留工作树都有负责人、状态和下一步；
- 脏工作树未被修改或强制删除；
- 已移除工作树的必要提交仍可由 main、archive、release、tag 或远端 ref 找回；
- reviewer 合并后的主线测试通过；
- 没有执行未经授权的远端或生产动作。

## 4. 门禁检查

每个门禁只检查下列结果，具体操作返回本文：

| 门禁 | 必查结果 |
| --- | --- |
| G0 | 新需求是否需要新工作树；当前计数是否允许 |
| G1 | 本轮工作树预算、并行上限和保留历史是否明确 |
| G2 | 任务工作树、共享热点、端口/数据隔离已就绪；总数 `<= 6` |
| G3 | 切片工作树可恢复，状态为待集成/阻塞；总数 `<= 6` |
| G4 | reviewer 已串行合并并测试；临时 reviewer 工作树已移除；总数 `<= 6` |
| G5 | 发布候选工作树干净且唯一；无历史工作树夹带 |
| G6 | 发布/观察工作树收尾，旧候选已归档或移除；总数 `<= 6` |
| G7 | 复盘记录保留/归档/删除结论；无无人负责的活跃工作树 |

## 6. 禁止事项

- 活跃工作树超过 6 个仍通过任一门禁或继续创建工作树；
- 为降低数量强制删除脏工作树、不完善实现或失败证据；
- 只看提交标题、分支名、ahead/behind 或单次 `git cherry` 就决定合并；
- 作者未经 reviewer 复核直接把多个功能分支同时合入主线；
- 测试前删除源工作树，导致失败时无法定位原现场；
- 把“移除工作树”误写成“删除分支”或“删除远端”；
- 用 `git reset --hard`、`git checkout --`、`git branch -D` 或
  `git worktree remove --force` 绕过保护条件；
- 借工作树治理执行未授权的 push、tag、Release、部署或生产写入。
