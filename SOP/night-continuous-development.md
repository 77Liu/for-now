# 夜间连续开发与三 Prompt 队列 SOP

本 SOP 用于在 Owner 无法持续在线时生成三条可依次投递、也可单独恢复现场的
高质量 Prompt。目标是在不降低测试、数据安全、候选一致性和生产权限要求的
前提下，持续推进当前版本、隔离 Preview、下一版本及必要技术债，避免因某个
发布节点缺少权限而让整条开发火车停止。

本 SOP 只定义夜间队列的生成、授权路由和持续调度。需求范围、工程实现、
多 Agent 调度、测试和生产发布分别以当前迭代计划、
`knowledge/engineering-rules.md`、`SOP/multi-agent-orchestration.md`、
`knowledge/system-testing.md` 和 `SOP/release-and-observation.md`
为准。

## 1. 核心原则

1. **权限阻塞节点，不阻塞整条队列**：缺少生产、费用、Base 或云配置权限时，
   将对应节点标为 `blocked`，立即切换到其他已授权工作。
2. **三条 Prompt 不是三个串行阶段**：每条都必须先恢复真实状态、重算 DAG，
   并能在当前版本、质量/Preview、下一版本三条车道之间切换。
3. **允许跨版本本地开发**：当前版本等待 Preview、生产或人工验收时，可以在
   隔离分支/工作树开发已经登记的后续版本，不要求上一版本先完成生产 G7。
4. **Preview 与生产分开授权**：隔离 Preview 可使用本 SOP 的持续授权；生产
   push/main、tag、Gitee Release、生产部署、数据迁移和真实付费调用仍需逐次
   明确授权。
5. **持续工作不等于制造工作**：只执行已登记需求、真实技术债、测试缺口和
   发布证据任务，不为保持 Agent 忙碌重复测试、重复审查或发明需求。
6. **完成节点后继续重排**：提交、测试、review、候选、Preview、阻塞变化或
   资源释放后立即选择下一可执行节点，不在切片完成时结束整轮。

## 2. 长期授权矩阵

Owner 于 2026-10-07 为按本 SOP 生成并明确引用本 SOP 的夜间队列提供以下
持续授权，直至 Owner 明确撤销或修改。

| 操作 | 夜间队列授权 | 限制 |
| --- | --- | --- |
| 本地读取、侦察、规划、测试和文档 | 允许 | 不读取或记录密钥、私人正文 |
| 已登记当前及后续版本的本地代码开发 | 允许 | 独立分支/工作树，不污染冻结候选 |
| 低风险本地任务提交 | 允许 | 遵循 commit gate、单一目的和验证要求 |
| 创建后续版本本地分支/工作树 | 允许 | 总工作树 `<=6`，基线和回收路径明确 |
| 推送 `preview/vX.Y.Z` | 允许 | 仅固定候选、仅版本专属 Preview 分支 |
| 部署现有隔离 Preview | 允许 | 隔离用户/env/data/端口；允许失败回滚 |
| Preview 自动化和合成数据 E2E | 允许 | 不写生产账户，不调用未获准付费服务 |
| 读取/更新已授权的项目 Base | 允许 | 连接 scope 存在时最小字段更新并回读 |
| push `main` | 不允许 | 每次另行授权 |
| 创建或推送 tag、Gitee Release | 不允许 | 每次另行授权 |
| 生产部署、迁移、写入、停服 | 不允许 | 每次另行授权 |
| DNS、证书、CDN、OSS/IAM、云配置 | 不允许 | 每次另行授权 |
| 真实供应商或其他付费调用 | 不允许 | 每次确认矩阵和费用上限 |

Preview 持续授权只在以下条件全部满足时有效：

- 候选具有固定 commit/tree/manifest，工作区干净。
- 本地必需门和独立 Reviewer 已通过，未关闭 blocker/P0/P1 为 0。
- 目标为现有隔离 Preview，不修改生产域名、生产数据或共享云配置。
- 推送分支严格为 `preview/vX.Y.Z`，并核对远端 SHA 与部署 SHA 一致。
- 部署前保存旧 Preview SHA；失败时允许回滚到该 SHA。
- Preview 中需要真实供应商、费用或生产数据时，改用模拟/合成数据；不能满足
  时只阻塞该验证节点，继续其他本地工作。

本授权不要求上一版本已经生产发布，才允许后续版本本地开发。后续版本代码必须
隔离，不能进入当前冻结候选、当前 Release 分支或生产。

## 3. 生成前的事实恢复

生成三条 Prompt 前，先读取：

- `PROJECT_RULES.md`、`README.md`、`one-mistake-one-rule.md`
- `SOP/README.md`、本 SOP、多 Agent、迭代规划和发布规则
- 当前及后续版本迭代计划、唯一调度报告、发布/复盘报告
- 唯一协调控制面、版本历史和机器模块登记
- 可用时读取 Base 需求、交付与版本表；不可用时登记外部回填缺口

至少核对：

```text
当前生产版本 / 当前开发版本 / 下一已登记版本
HEAD / origin/main / tag / Preview SHA / candidate tree 或 manifest
工作区 / worktree / Agent / 进程 / 端口 / 数据库 / 浏览器资源
当前版本未关闭节点 / 后续版本 ready 节点 / 技术债与测试缺口
本地 / Preview / 生产 / 云资源 / 费用 / Base 授权
```

不得把聊天摘要、提交标题或旧计划状态直接当作当前事实。未知字段写
`unknown`，并在 Prompt 中要求运行时发现，不能编造 SHA、进度或 ETA。

## 4. 非终点队列模型

三条 Prompt 共用同一组工作车道，但主要职责不同：

| 车道 | 内容 | 权限不足时 |
| --- | --- | --- |
| A 当前版本关键路径 | blocker/P0/P1、实现、接线、候选和本地门 | 转 B 或 C |
| B 质量与 Preview | 测试、review、恢复、文档、隔离 Preview | 转 C 或 D |
| C 后续版本开发火车 | G0-G3、叶子实现、测试、技术验证 | 转 A、B 或 D |
| D 安全备用 | 测试缺口、技术债、文档、回放样例、侦察 | 转任一 ready 车道 |

每个 Prompt 内都使用以下循环：

```text
恢复事实
-> 重算唯一 DAG
-> 选择最高优先级可执行节点
-> 派发/执行/验证/提交
-> 回写证据并释放资源
-> 再次重算 DAG
-> 继续下一个节点
```

以下内容不能成为整个夜间运行的停止理由：

- 当前版本缺少生产授权。
- 当前版本等待人工视觉验收。
- Base、某个云服务或某个真机暂不可用。
- 当前版本本地候选已经完成。
- Preview 正在等待第二次生产授权。
- 下一版本尚未发布，但已有已登记需求和可隔离开发节点。

这些情况只阻塞相关节点。Prompt 必须从其他车道选择工作。

只有以下情况允许结束当前 Prompt：

- Owner 明确要求停止。
- 上下文或执行时限耗尽；必须先写可恢复检查点和下一 Prompt 交接。
- 发现可能破坏生产/私人数据、安全边界或不可逆资产，且所有其他本地车道均
  无法继续。
- 当前及后续已登记版本、真实技术债和验证缺口全部没有可执行节点；必须列出
  已检查的队列，不能只写“等待授权”。

## 5. 跨版本开发规则

跨版本开发是本 SOP 的默认能力，不是例外：

1. 当前版本候选冻结后，后续版本可以立即进入 G0-G2 和本地 G3。
2. 后续版本必须已经存在于 Base、TODO、路线图或明确的迭代计划；Agent 不得
   为持续工作自行发明产品需求。
3. 后续版本分支以已测试的当前候选或已发布主线为基线，选择依据必须写入计划。
   当前候选后续回滚时，后续分支重新评估，不静默合入。
4. 当前 Release 候选保持不可变。后续版本不得修改其分支、版本元数据、发布
   文档、manifest 或测试证据。
5. 当前和后续版本共享文件时，由不同工作树准备叶子；实际接线在各自版本的
   唯一集成者处串行完成。
6. 后续版本本地提交可以持续形成；不得在当前版本 Release 关闭前合并到
   `main`、创建正式 tag 或部署生产。
7. 工作树总数始终 `<=6`。资源不足时优先回收已吸收的干净工作树，不能以
   扩大工作树数量换取并行。

## 6. Prompt 质量硬门

每条生成的 Prompt 必须包含：

- 当前任务可能处于任意阶段，先读取事实而非相信 Prompt 中的进度。
- 主要目标、非目标、授权矩阵和生产禁区。
- 当前、下一版本及安全备用三层任务池。
- 事件驱动重排和 `ready/notDispatchedReason` 规则。
- 最多两条非重叠写线；共享入口和公共契约单写。
- Reviewer、Validator、Scout 的使用条件和真实 Agent 名册回写。
- 工作树 `<=6`、脏现场保护、完成后回收。
- 候选 commit/tree/manifest 与证据失效规则。
- 专项、影响门、Release 门的分层，禁止为占用时间重复全量门。
- 2–3 小时检查点和上下文切换交接。
- 无权限时切换车道，不以“等待授权”结束。
- 明确禁止生产、tag、Release、云配置和付费调用。
- 完成一项后继续下一项，直到允许的结束条件出现。
- 启动时若主要目标已经完成，不得只汇报状态；立即从其他车道选择 ready 节点。
- 进度同时报告完整需求、工程工作量和发布闭环三个口径；ETA 使用最近三批
  可比任务的实际事件给出范围，并将授权等待单列，不用任务数量伪造百分比。
- 下一版本本地开发的最晚入口是当前版本候选冻结；更早存在完全隔离的 ready
  叶子时也可启动，不把生产发布或观察关闭设为本地编码入口。

每条 Prompt 必须使用实际路径、版本和已知候选；无法确定的值写成发现步骤，
不得保留无意义的 `<placeholder>`。

## 7. 三条标准 Prompt

生成结果固定为三条。三条可以依次投递，也可以在任何中断点单独启动。

### Prompt 1：主调度与当前关键路径

```text
执行夜间连续开发，遵循 SOP/night-continuous-development.md。你可能接管任意
阶段，先恢复当前生产、当前版本、下一版本、Git/worktree/Agent/进程、候选和
授权事实，不假设上一 Agent 已完成或失败。

主要职责是推进全局关键路径。按 blocker/P0/P1、当前版本未关闭关键路径、
当前候选验证/Preview、下一版本 ready 叶子、安全备用任务排序。每次提交、
测试、review、候选、Preview、阻塞或资源变化后重算唯一 DAG，完成一项后继续
下一项，不在切片或版本候选完成时结束。

当前版本缺少生产、tag、Release、费用、Base 或云配置权限时，只阻塞对应节点。
候选满足 SOP 条件时允许推送 preview/vX.Y.Z 并部署现有隔离 Preview；不得
push main、创建正式 tag/Release、部署生产或产生未经授权费用。Preview 或
生产等待期间，立即在隔离工作树推进下一已登记版本的 G0-G3 和本地代码。

主 Agent 独占共享入口、schema、registry、runner、依赖锁和发布文件；最多
两条独立写线，工作树始终 <=6。使用有独立价值的 Reviewer、Validator、Scout，
不为凑人数重复任务。所有结论绑定固定 commit/tree/manifest。

每 2–3 小时形成可恢复检查点。上下文接近上限时写完整交接并切换上下文继续，
不得把“等待授权”作为结束理由。只有本 SOP 允许的停止条件出现时才能结束。
```

### Prompt 2：质量、Release 与 Preview 车道

```text
执行夜间质量与 Preview 车道，遵循 SOP/night-continuous-development.md。
先识别当前是否存在 dirty candidate、固定本地候选、待验收 Preview、生产授权
阻塞或下一版本候选，不依据旧摘要猜测状态。

优先完成候选身份、版本元数据、专项/影响/Release 门、恢复、性能、PWA、
独立 review、发布说明和回滚证据。测试和 Reviewer 必须绑定同一固定
commit/tree/manifest；候选变化后按失效矩阵重跑，不用旧结果证明新候选。

固定候选达到 0/0/0 且本地门通过时，本 Prompt 已获得推送版本专属
preview/vX.Y.Z 和部署现有隔离 Preview 的持续授权。部署前记录旧 Preview SHA，
验证远端/部署 SHA、隔离数据、noindex、ready、核心旅程、响应式和性能；失败
自动回滚 Preview。不得 push main、tag、创建 Gitee Release、部署生产、修改
云配置或调用未经授权付费服务。

某个 Release 节点缺权限、环境、真机或 Base scope 时，登记 blockedBy 和恢复
入口，立即切换到下一版本候选验证、测试补强、回放样例、技术债治理或只读审计。
不得因等待生产授权结束整轮。每个事件后继续重排，直到执行时限耗尽或出现全局
安全阻断；结束前必须写检查点和下一条队列可直接使用的交接。
```

### Prompt 3：后续版本开发火车与安全备用

```text
执行夜间后续版本开发火车，遵循 SOP/night-continuous-development.md。上一
版本是否已发布不是本地开发的入口条件。先核对上一版本冻结候选、下一已登记
版本、Base/TODO/计划范围、分支基线、共享文件和工作树资源。

若下一版本缺少 G0-G2，先完成范围去重、Epic/叶子 DAG、验收/恢复矩阵、热点
预警和 Agent/资源计划；随后立即开始最高优先级、无外部依赖的本地纵向切片。
若已有计划，直接恢复 ready 节点。允许连续推进更多已登记版本，但不得发明
需求或把探索结论写成已确认范围。

下一版本代码必须在隔离分支/工作树；上一版本候选、发布文档和 manifest 不得
改变。最多两条非重叠写线，共享契约由该版本唯一集成者串行接入。每个状态、
请求、事件和资源首次引入时明确 owner、生命周期、取消、恢复与负例；Prompt、
感知和个性化必须版本化并覆盖来源、注入、纠错、撤回和回放。

切片按专项、影响门、独立 Reviewer、提交和资源回收闭环。外部权限不足时改做
本地模拟、契约、测试、文档或下一 ready 切片，不结束整轮。当前版本若出现
blocker/P0/P1 或 Preview 失败，立即回到其修复关键路径；否则持续下一版本
开发。每 2–3 小时写检查点，上下文耗尽时交接并继续。
```

## 8. 生成算法

每次生成夜间队列：

1. 根据第 3 节恢复事实，建立当前、下一版本和安全备用任务池。
2. 每个任务标记 `ready/blocked/active/review/validated/closed`、依赖、写集、
   资源、授权和下一复核事件。
3. 至少准备：
   - 一条当前版本或候选关键路径；
   - 一条独立质量/Preview 路径；
   - 一条后续版本本地路径；
   - 两条不依赖远端权限的备用任务。
4. 将真实版本、路径、SHA、计划和调度报告写入三条标准 Prompt。
5. 删除会形成终点状态机的句子，例如“只有上一版本发布后才能启动下一版本”、
   “无授权则停止”或“完成后等待用户”。
6. 保留节点级安全边界，改写为“阻塞该节点并转向其他车道”。
7. 检查三条 Prompt 单独启动时都能恢复现场、执行有效工作并留下检查点。

## 9. 夜间检查点与晨间汇报

每 2–3 小时或每个重要候选后记录：

- 当前生产、Preview、版本、HEAD、candidate tree/manifest。
- 完成节点、失败样本、修复、测试和 Reviewer。
- Agent/工作树/端口/数据库/浏览器资源。
- blocked 节点、缺少的授权及已切换到的备用车道。
- 下一批 ready 节点和实际 ETA。

晨间汇报必须区分：

- 已本地实现、已验证、已提交。
- 已部署 Preview。
- 等待生产授权。
- 已跨版本推进的本地工作。
- 未执行的生产、付费、真机和外部配置。

不得用“整夜持续工作”替代实际提交、测试、候选或可复核证据。

- [ ] 没有“缺权限即结束”的全局终止条件。
- [ ] Preview 授权范围和生产禁区明确。
- [ ] 明确允许后续已登记版本的本地代码开发。
- [ ] 当前候选与下一版本工作区完全隔离。
- [ ] 每条都有当前、质量/Preview、下一版本和安全备用路径。
- [ ] 每个事件后重排并继续，不在切片完成处停止。
- [ ] 工作树、Agent、候选、测试和 review 规则完整。
- [ ] 不通过重复测试、重复 review 或虚构需求制造工作量。
- [ ] 有检查点、上下文交接和晨间汇报格式。
