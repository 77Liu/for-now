# 夜间持续推进 SOP

修订：2026-10-17，Owner 已批准，接入 develop 后生效。本页只负责已授权任务的持续调度与中断恢复，不授予新的开发、Preview、生产或费用权限。

## 恢复与执行

1. 先读[当前控制面](../coordination/current.json)，核对 Owner 最新指令、当前候选、活动任务、阻碍和允许动作；规则与历史按需展开。
2. 根据真实依赖选择最高优先级且已获准的可执行任务。优先处理当前版本的核心故障和候选缺口；某个环境或授权缺失只阻塞依赖它的动作。
3. 完成实现、自查、必要验证和主控接入审查后，记录关键实际结果，按依赖选择下一项。不得凭开发者回复直接接入。
4. 普通说明合并交接；关键范围、授权、候选和结果变化按[事件规则](../knowledge/coordination-control-plane.md)及时落盘，不按每条命令记事件或独立提交。
5. 无新的证据目的不重复测试或审查，不自行创造需求、角色、工作树或重构来维持运行。

## 边界

- 授权只见[发布自动授权策略](../knowledge/release-authorization-policy.md)及当前 Owner 限制；夜间不另存权限矩阵。已覆盖动作不重复申请，暂停立即生效。
- 分支和 checkout 分别见[Git 规则](../knowledge/remote-branch-policy.md)、[工作树生命周期](worktree-lifecycle.md)。没有实际并行或隔离需求不新建工作树，不设夜间专用数量上限。
- 下一版需求可提前收集、调查和拟案；正式发布后先回流 develop，再按[发布 SOP](release-and-observation.md#正式发布回流与下一版起点)确定下一版基线。旧“冻结即从候选／main 开下一版”规则不再使用。
- Preview、生产及付费动作各自核对环境和已有授权；无法执行时选择其他已获准且无依赖的任务，不改变目标环境绕过限制。

## 中断与继续

Owner 停止、执行时限到达或全部已授权任务都被实际条件阻塞时，保留可恢复现场并说明下一动作。可执行工作存在时持续推进；没有可执行工作时如实汇报，不能无休止轮询或制造工作。

上下文切换或重要检查点记录当前基线、有效成果、真实阻碍和下一动作，复用控制面及回执。不同工具的等待／自动唤醒能力按实际工具执行，不声称聊天结束后仍在后台运行。

## 队列提示的制作

用户要求生成多条接续 Prompt 时，每条均应能从控制面恢复：目标及非目标、读取入口、当前授权、优先级、实际写集、候选保护和停止条件。条数按用户请求，不默认固定三条或重复复制规则全文。

Prompt 中的版本、候选和进度只是生成时的上下文；运行时必须重新核对控制面。不得嵌入“本 Prompt 已授权生产”等自行扩权内容。

## 汇报

区分本地实现、验证、接入、Preview、正式发布、运行观察及未验收；给出有效证据与实际阻碍。ETA 证据不足时明确未知，不用任务数或“整夜工作”伪造进度。
