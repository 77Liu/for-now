# 需求收集与准入 SOP

- SOP 编号：`SOP-DEV-001`
- 版本：`1.1`
- 状态：生效
- 对应阶段：需求收集
- 退出门禁：`G0 需求可进入`

本 SOP 用于把用户反馈、生产异常、产品想法、技术风险和 Agent 建议转为可追溯
的候选需求。生命周期和门禁定义以
[`knowledge/development-lifecycle.md`](../knowledge/development-lifecycle.md)
为准。

## 1. 适用范围

以下输入必须经过本 SOP：

- 用户原话、访谈、评论、截图和使用记录；
- 生产错误、监控异常、支持请求和复盘行动项；
- Owner 提出的产品方向或业务约束；
- Agent 在开发、审查和测试中发现的改进建议；
- 被当前迭代拒绝、延期或拆出的后续事项。

生产事故可先按 [`hotfix.md`](hotfix.md) 止损，但事后仍须补齐需求/问题记录。

## 2. 角色

| 角色 | 责任 |
| --- | --- |
| Owner | 确认用户事实、价值判断、优先级和是否进入规划 |
| 收集者 | 保存来源、归一化问题、查重、补齐验收线索 |
| Agent | 提供分析与建议，明确标注推断，不代替用户立场 |

## 3. 最小输入

- 原始来源或可核对证据；
- 发生时间、用户或账户类型、使用场景；
- 当前表现及造成的影响；
- 已知数据、权限、费用和生产边界。

没有原始证据时可以登记为“待验证假设”，不得写成已确认需求。

## 4. 标准流程

### 步骤 0：保护来源与隐私

1. 原话、截图和日志保留必要上下文。
2. 密钥、密码、Cookie、Session Token、邀请码和私人正文不得进入公开文档。
3. AI 回答、推理和建议与用户原话分栏保存，不把模型内容当成用户立场。
4. 生产数据只做获准范围内的只读核对；普通需求收集不得产生生产写入。

### 步骤 1：写成用户问题

每条记录回答：

1. 谁在什么场景遇到什么问题？
2. 当前如何处理，损失或不便是什么？
3. 希望发生什么变化，为什么值得做？
4. 最小可用结果是什么，如何观察效果？

优先描述行为与结果，不先绑定按钮、字段、框架或供应商方案。

### 步骤 2：标记事实类型

| 类型 | 含义 |
| --- | --- |
| 用户事实 | 用户明确表达或实际操作证据 |
| 系统事实 | 日志、代码、数据或可复现行为 |
| Owner 决策 | 已确认的方向、优先级或约束 |
| Agent 判断 | 基于现有证据的解释或建议 |
| 待验证假设 | 证据不足但值得验证的可能性 |

同一段内容包含多类信息时拆开记录。

### 步骤 3：查重与归类

1. 搜索需求池、研发交付记录、唯一协调控制面、近期计划和复盘。
2. 相同用户问题合并来源，不重复创建平行需求。
3. 区分产品需求、缺陷、系统质量、调研、一次性交付和纯证据。
4. 重复、取消和延期记录保留原因与关联对象，不直接删除历史。

### 步骤 4：评估优先级与风险

至少考虑：

- 用户影响和发生频率；
- 证据可信度和紧迫性；
- 是否影响数据正确性、安全、权限或恢复；
- 开发与验证成本；
- 与当前主要目标、公共契约和外部依赖的关系。

优先级表达选择顺序，不代替风险门禁。P00/P0 也不能跳过必要验证和授权。

### 步骤 5：形成候选需求

推荐记录：

```markdown
需求 ID：
标题：
类型与优先级：
来源与时间：
用户 / 场景 / 问题：
当前影响：
期望结果：
最小可用结果：
观察指标或验收线索：
已知风险与依赖：
事实 / 判断 / 假设：
重复或关联项：
当前状态：候选 / 待验证 / 待规划
```

当前业务需求维护在飞书 Base“需求池”；工程执行状态不在需求记录中混写。

### 步骤 6：执行 `G0 需求可进入`

逐项核对：

- [ ] 能说明谁在什么场景为什么需要；
- [ ] 有来源，或明确标为待验证假设；
- [ ] 用户事实、系统事实、Owner 决策和 Agent 判断已分开；
- [ ] 最小结果和观察方式可理解；
- [ ] 已完成查重与关联；
- [ ] 不包含凭据或未经授权的私人数据；
- [ ] 类型、优先级和下一状态明确。
- [ ] 已按 [`worktree-lifecycle.md`](worktree-lifecycle.md) 检查活跃工作树不超过 6 个。

通过后进入“待规划”。未通过时补证据、合并重复项或保留为待验证假设。

## 5. 输出与交接

`G0` 通过后至少输出：

- 需求池记录及 ID；
- 来源与证据链接；
- 初步优先级、风险和依赖；
- 建议进入的迭代或保持候选的理由。

进入本轮冻结时，交给 [`iteration-planning.md`](iteration-planning.md)。只有
Owner 在 `G1` 确认后，候选需求才成为本轮承诺。

## 6. 本地采集快照管理

生效：2026-10-13。本节是需求采集文件管理的唯一正文，不改变线上需求事实或工程控制面的维护边界。

1. 仅维护忽略目录 `artifacts/local/requirements-current.json`，同一文件包含需求、版本、交付记录，以及实际采集开始/完成时间、各表 revision、记录数、字段覆盖与分页完整性。定向读取不能冒充全池完整采集；无法证实的时间或字段标为未知。
2. 完整采集并校验三表分页结束、记录数、唯一 ID、revision 和字段覆盖后，先在同目录受保护临时文件完整写入并持久化，再原子替换快照并持久化目录。失败不得用部分结果覆盖上次完整数据；保留原记录、revision 与采集时间，原子更新同一文件的陈旧标记、失败时间和脱敏原因。没有成功快照时明确无可用完整基线，不制造空的成功快照。
3. 中间结果只使用内存或临时目录，完成或失败后清理；禁止持续保存 before/after、时间戳副本、summary、manifest 等重复文件，不另存原始采集历史。
4. 最新快照及临时材料不进入 Git，沿用 `artifacts/` 的忽略规则。有意义的排期、范围、派发等决定由协调者按[控制面事件协议](../knowledge/coordination-control-plane.md)记录，快照不维护第二份工程状态。
5. 替换旧采集材料前核对必要引用，将仍需保留的脱敏安全核验结论与局限提炼到同一快照，再清理旧材料。不得改写追加历史；历史中“当时保留文件”的事实不等于当前可用证据，当前使用方不得引用已清理文件。

## 7. 常见错误

| 错误 | 正确处理 |
| --- | --- |
| 把 Agent 建议写成用户需求 | 标为 Agent 判断，等待用户或行为证据 |
| 一开始就写具体实现 | 先写问题、场景、结果，再在规划阶段选方案 |
| 用“体验不好”代替问题 | 写明任务、当前行为和实际影响 |
| 重复需求另起记录 | 合并来源并保留关联历史 |
| 紧急问题没有记录 | 先止损，随后补齐事故与需求证据 |
