# 迭代复盘与过程报告 SOP

- SOP 编号：`SOP-DEV-007`
- 版本：`2.0`
- 状态：生效
- 对应阶段：复盘与回流
- 进入条件：迭代或里程碑对象已固定；正式发布通常已通过 `G6`
- 退出门禁：`G7 迭代已关闭`
- 流程负责人：产品 Owner
- 执行者：负责本轮开发、集成或发布的 Agent

生命周期、状态和证据契约以
[`knowledge/development-lifecycle.md`](../knowledge/development-lifecycle.md)
为准。

## 1. 目的

本 SOP 用于在一个迭代、版本或重要里程碑结束后，以可核验证据还原实际过程，
形成两层产物：

1. **事实层**：开发过程报告。记录做了什么、何时发生、由什么指令触发、
   修改了哪些文件、执行了哪些命令、等待多久、哪里失败、如何重试、哪些
   内容最终提交或上线。
2. **复盘层**：问题与行动项。仅在 Owner 明确要求复盘或允许分析时，基于
   已完成的事实层描述有效做法、损耗、原因、行动、责任人和验收方式。

事实层是每次执行的必需产物。若用户要求“只做描述”“不做反思”，到事实层
验收后立即结束，不生成原因推断、评价、建议或行动项。

本 SOP 不替代：

- 需求收集与回流：`SOP/requirement-intake.md`
- 工程和提交规则：`knowledge/engineering-rules.md`
- 发布动作与观察门：`SOP/release-and-observation.md`
- 详细上线检查项：`knowledge/development-release-checklist.md`
- 当日重要变化：`knowledge/iteration-history.md`

## 2. 触发条件

满足任一条件时可启动：

- 一个正式版本或热修复完成发布与观察。
- 一个大版本的本地开发、串行集成或候选冻结完成。
- 发生跨工作树、跨 Agent、大规模 rebase、迁移或生产切换。
- 同一问题出现多次失败、等待或返工，需要形成过程证据。
- Owner 要求生成开发过程报告、迭代复盘或 Agent 工作记录。
- 现有阶段记录分散，后续 Agent 无法仅靠项目文件还原过程。

启动复盘不表示版本已经发布。必须分别标注：

```text
工作区已实现
本地已验证
本地已提交
已 push
已创建标签与 Release
生产已部署
生产迁移已完成
观察已关闭
```

## 3. 输出与命名

### 3.1 事实层报告

事实层写入该版本唯一正文 `docs/versions/<version>/README.md`。跨版本结论压缩
写入 `knowledge/iteration-history.md` 并链接各版本正文，不创建平行过程报告。
历史验收节点、流程图和决策记录采用追加保留，不覆盖或压缩成无法追溯的汇总
节点。

### 3.2 复盘层

复盘层写入版本正文的独立“复盘结论与行动项”章节。跨版本长期有效的原则回流
对应 `knowledge/` 唯一正文；行动状态进入协调控制面，不另建复盘文件。

### 3.3 最小交付

每次至少交付：

- 一份事实报告。
- 一张版本/提交链表。
- 一条按时间排序的开发与发布主线。
- 一份等待、失败、重试和重复工作记录。
- 一份 Git 与文件变化记录。
- 一份证据索引。
- 一份验收结论。

## 4. 角色

| 角色 | 职责 |
| --- | --- |
| Owner | 确认范围、事实争议、敏感边界和最终验收 |
| 记录 Agent | 收集证据、建立时间线、撰写报告、执行核对 |
| 独立复核者 | 从原始证据重新检查事实；没有独立 Agent 时由记录 Agent 开启新上下文或按冻结证据重新核对 |

同一 Agent 执行记录与复核时，必须把“撰写”和“事实核对”分成两个步骤，不能
只凭刚写完的记忆确认。

## 5. 流程状态

```text
启动
→ 范围冻结
→ 证据冻结
→ 证据台账完成
→ 时间线完成
→ 事实层初稿完成
→ 事实审计通过
→ 可选复盘层完成
→ Owner 验收
→ 归档
```

发现关键证据冲突时，状态改为“待核实”，不得用推测补齐。取得新证据后返回
冲突所属步骤。

## 6. Step 0：冻结复盘范围

开始前写明：

| 字段 | 内容 |
| --- | --- |
| 复盘对象 | 版本、迭代、里程碑或事件名称 |
| 起点 | 起始标签、提交、时间或生产版本 |
| 终点 | 结束标签、提交、时间或生产版本 |
| 截止时间 | 此后发生的工作不进入本报告 |
| 模式 | 仅事实 / 事实 + 复盘 |
| 代码仓库 | 本地路径、远端和产品线 |
| 生产范围 | 未涉及 / 只读 / 部署 / 迁移 / 观察 |
| 排除范围 | 明确不进入报告的并行任务和私有内容 |

规则：

- 起点和终点优先使用完整 Git 哈希，不只写分支名。
- 跨多个工作树时逐一列出，不把当前 `cwd` 自动当作唯一事实来源。
- 复盘期间原则上不做产品开发。发现产品问题只记录，不顺手修复。
- 若必须修正文档事实，记录修正时间和证据，不修改历史原文来掩盖变化。

## 7. Step 1：冻结工作区与 Git 事实

先执行只读命令，不清理、不 reset、不切换用户分支：

```bash
date
git status --short --branch
git rev-parse HEAD
git remote -v
git worktree list --porcelain
git stash list --date=iso-local
git branch --all --verbose --no-abbrev
git tag --list --format='%(refname:short)|%(objectname)|%(creatordate:iso-local)'
```

对起点和终点执行：

```bash
git log --date=iso-local \
  --pretty=format:'%H%x09%ad%x09%d%x09%s' \
  <start>..<end>

git reflog --all --date=iso-local \
  --pretty=format:'%h%x09%gd%x09%ad%x09%gs'

git diff --shortstat <start> <end>
git diff --dirstat=files,0 <start> <end>
git diff --numstat <start> <end>
git diff --name-status <start> <end>
```

记录：

- 当前分支和 HEAD。
- 起点、终点及标签 peel 后的提交。
- 工作树、临时分支和命名 stash。
- 未提交、未跟踪和用户已有改动。
- commit、amend、reset、rebase、checkout、stash 的实际顺序。
- 本轮是否发生 push、tag、Release 和部署。

禁止：

- 为了让报告“好看”而清理 reflog、stash、临时分支或未跟踪文件。
- 把多个工作树的状态合并成一个状态。
- 把 annotated tag 对象哈希误写成其目标提交哈希。

## 8. Step 2：建立证据台账

先列证据，后写结论。建议使用：

| ID | 时间 | 来源 | 事实 | 证据等级 | 敏感性 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| E-001 | ISO 时间 | Git / 报告 / 命令 / Prompt | 单一事实 | A/B/C/D | 公开/内部/私密 | 已核对/冲突/缺失 |

### 8.1 证据等级

| 等级 | 来源 | 使用方式 |
| --- | --- | --- |
| A | Git 对象、机器 JSON、命令原始输出、生产只读观测 | 可直接支持事实 |
| B | 当时形成的阶段报告、发布记录、测试日志 | 与 A 交叉核对 |
| C | Agent commentary、人工 Prompt、会话摘要 | 用于还原意图和过程 |
| D | 根据多项事实形成的解释 | 必须标为判断，不得写成原始事实 |

冲突处理顺序：

1. 先检查时间和对象是否一致。
2. 当前事实以更接近事件发生时的 A 级证据为主。
3. 阶段报告保留其当时结论，但后文追加后续变化。
4. 无法确定时写“未能从现有证据确认”，不选择更顺眼的版本。

### 8.2 必查来源

- `PROJECT_RULES.md`
- `README.md`
- `README-TODO.md`
- `one-mistake-one-rule.md`
- `knowledge/iteration-history.md`
- 本轮计划、检查、迁移、测试和发布文档
- Git log、reflog、stash、worktree、tag
- 测试日志和机器可读 JSON
- 部署、备份、恢复和观察证据
- 人工 Prompt 与 Agent 可观察工作日志

## 9. Step 3：收集人工 Prompt 与 Agent 命令

### 9.1 人工 Prompt

只复制与本轮决策直接相关的原文：

- 目标与范围。
- 优先级调整。
- 不做范围。
- commit / push / deploy 授权。
- 生产风险接受。
- 环境、费用和外部服务授权。
- 对 Agent 的纠正。

要求：

- 能取得完整原文时直接引用。
- 只能取得摘要时标为“原文片段”，省略处使用省略号。
- 不从摘要反推或补写用户没说过的话。
- 同一指令多次变化时按时间分别记录。

### 9.2 Agent 命令

记录能解释结果的命令，不把每个 `ls` 都写入正文。至少包括：

- 关键搜索与读取。
- 测试、构建和检查。
- Git 历史与提交操作。
- 数据库迁移与恢复。
- 部署、健康检查和观察。
- 失败后更换的命令或路径。

凭据、Cookie、Token、密码、私钥和私人正文必须删除或用占位符替换。报告只
保留命令结构和结果。

## 10. Step 4：还原时间线

时间线按事件发生时间排序，不按报告章节或 Git 拓扑强行排序。每个节点至少写：

| 字段 | 要求 |
| --- | --- |
| 时间 | 精确到可取得的最小粒度，并注明时区 |
| 触发 | 人工指令、测试失败、阶段门或生产事件 |
| 动作 | 修改、命令、等待、重试、提交或部署 |
| 对象 | 分支、工作树、提交、文件、环境 |
| 结果 | 通过、失败、部分通过、NO-GO |
| 证据 | 文件、哈希、日志、URL 或机器报告 |
| 后续 | 下一步实际发生了什么 |

推荐分层：

1. 版本与提交链。
2. 每日或阶段主线。
3. 并行工作树和串行集成。
4. 发布与生产操作。
5. 发布后修复与观察。

不得：

- 用最终状态覆盖早期失败。
- 把“本地验证”写成“已上线”。
- 把提交时间当成全部实现时间。
- 把未执行的计划写成实际动作。

## 11. Step 5：记录等待、重复、失败与判断

### 11.1 等待台账

对超过约 30 秒或影响流程推进的等待记录：

| 开始/结束 | 用时 | 等待对象 | 是否阻塞 | 结果 |
| --- | ---: | --- | --- | --- |
| 时间 | ms / s / min | 测试、编译、下载、部署、观察 | 是/否 | 通过/失败/超时 |

可聚合相同类型的短等待，但以下项目单独记录：

- 完整系统测试。
- 数据库构建、启动、迁移和恢复。
- 大依赖或浏览器下载。
- 部署回滚测试。
- 生产停写。
- 固定观察窗口。

### 11.2 重复工作

同一命令或动作反复执行时，说明每次证据目的：

- 代码或映射发生变化。
- 工作区变为固定提交。
- 从活动目录切换到干净归档。
- 修复测试本身后重验。
- 生产环境和本地环境分别验证。
- 第一次失败后更换假设或执行路径。

如果只是误操作，直接写“重复执行，无新增证据”，不为其制造价值。

### 11.3 失败与纠正

每项失败使用：

| 尝试 | 原命令/方法 | 原始错误 | 是否产生副作用 | 纠正动作 | 最终状态 |
| --- | --- | --- | --- | --- | --- |

必须保留：

- 原始错误文本。
- 失败发生在本地还是远端。
- 是否已经进入业务断言。
- 是否产生数据、费用、文件或服务状态变化。
- 后续是修复、绕过、回滚还是接受为已知问题。

### 11.4 可观察判断摘要

不能公开隐藏内部推理或逐字思维链。可以记录由外部动作验证的判断：

```text
证据：Store v15 映射已变化，旧 PostgreSQL 基线只覆盖 v14。
判断：旧 40 项结果不能关闭本轮数据库门。
动作：保留 NO-GO，取得新环境后重跑。
```

判断摘要必须包含证据和动作，不使用无法验证的心理描述。

## 12. Step 6：建立文件编辑账本

至少记录：

- 文件总数、总新增、总删除。
- 按目录的文件数量或占比。
- 新增、修改、删除、重命名。
- 最大改动文件。
- 二进制、生成物和静态资产。
- 配置、依赖锁、迁移、部署和测试文件。

命令：

```bash
git diff --shortstat <start> <end>
git diff --dirstat=files,0 <start> <end>
git diff --numstat <start> <end> | sort -nr -k1,1
git diff --name-status <start> <end>
```

大版本报告应附完整 `--name-status` 清单。若正文过长，可放在报告附录，但不能
只写“修改很多文件”。

文件账本必须区分：

- 最终版本的净差异。
- 中间提交的改动规模。
- 最后仅用于关闭发布的文档提交。
- 未进入版本的 stash、探索资产和并行工作树。

## 13. Step 7：建立验证与发布账本

### 13.1 测试

每次关键测试记录：

| 阶段 | 命令 | 候选/工作区 | 通过数 | 用时 | 结果 | 未覆盖 |
| --- | --- | --- | ---: | ---: | --- | --- |

若测试阶段数逐步增加，保留增长过程。不能只保留最终一次，也不能把旧结果写成
新候选结果。

### 13.2 Git 与发行版

记录：

- 每个关键提交的完整哈希、时间、标题和变更规模。
- 标签 peel 后的目标提交。
- push 时间和远端状态。
- Gitee Release URL。
- 上一发行版和比较范围。
- 是否完成“新功能”“Bug 修复”“架构调整”三个固定栏目。

### 13.3 生产

适用时记录：

- 部署前运行版本。
- 部署版本和时间。
- 维护窗口。
- 数据数量、摘要和附件 inventory。
- 备份与恢复。
- 关键冒烟。
- 观察开始/结束、采样数、重启、内存、Swap、OOM 和告警。
- 已知非阻断项及接受人。

发布事实以 `SOP/release-and-observation.md` 定义的动作回执和控制面状态为准。

## 14. Step 8：撰写事实层

推荐结构：

```text
# <版本范围> 开发过程记录

## 1. 范围与证据边界
## 2. 版本与提交链
## 3. 按日期/阶段的过程
## 4. 并行与集成
## 5. 环境、数据库与生产
## 6. 等待、重复、失败与纠正
## 7. 可观察判断摘要
## 8. Git 历史与提交规模
## 9. 文件编辑记录
## 10. 人工 Prompt 与 Agent 命令
## 11. 证据索引
## 12. 截止状态
## 附录：完整文件清单
```

写作规则：

- 先写事实，再写解释。
- 每个“通过”都附命令、对象和结果。
- 每个“失败”都保留错误和后续。
- 使用绝对时间或注明时区。
- 重要原文用引用块。
- 数字保留来源中的精度，不擅自换算成更精确结论。
- 区分代码候选、发布提交和最终运行提交。
- 不使用“应该”“大概”“基本完成”替代状态。
- 不把 Agent 生成内容写成用户立场。

## 15. Step 9：可选复盘层

只有模式为“事实 + 复盘”时执行。事实层必须先冻结，复盘不得反向改写事实。

### 15.1 分类

- 有效做法。
- 失败与返工。
- 等待与资源损耗。
- 范围、协作和上下文问题。
- 测试、环境和工具问题。
- 发布、迁移和恢复问题。
- 可自动化但尚未自动化的重复动作。

### 15.2 每项格式

| 字段 | 要求 |
| --- | --- |
| 现象 | 客观发生了什么 |
| 证据 | 时间、命令、日志、提交或报告 |
| 影响 | 时间、范围、风险或重复次数 |
| 原因 | 已证实原因；未证实时写“未确认” |
| 保留/改变 | 保留有效做法，或改变具体步骤 |
| 行动 | 单一可执行动作 |
| 责任人 | Owner / Agent / 外部负责人 |
| 截止点 | 日期或下一版本门 |
| 验收 | 如何证明行动完成 |

禁止：

- 用“Agent 应该更认真”之类不可执行评价代替行动。
- 把环境偶发错误直接上升为长期规则。
- 没有证据时猜测人员动机或根因。
- 同时创建多个职责相同的流程文档。

若发现具有复发风险的真实错误，按 One Mistake → One Rule 判断是否更新
`one-mistake-one-rule.md`；一次性命令输错不自动上升为规则。

## 16. Step 10：事实与格式审计

### 16.1 Git 核对

```bash
git cat-file -e <commit>^{commit}
git rev-parse <tag>^{}
git show --format=fuller --shortstat <commit>
git diff --check
```

检查：

- 报告中的所有关键提交存在。
- 标签解析到报告中的目标提交。
- 提交规模与 Git 输出一致。
- 起止范围和净差异一致。
- 完整文件清单与 `git diff --name-status` 逐行一致。

### 16.2 文档核对

- 引用文件存在。
- 标题层级连续。
- Markdown code fence 成对。
- 表格列数一致。
- 相对链接可以从报告位置解析。
- 没有把旧状态写成当前状态。
- 没有删除历史验收节点。

### 16.3 敏感信息扫描

至少检查：

- 私钥头。
- AccessKey。
- Bearer Token。
- API Key。
- Cookie。
- 数据库 URL 与密码。
- webhook。
- 用户私人正文。
- 本地或服务器受限凭据路径中的文件内容。

发现敏感值时删除值，保留“已配置”“已验证”和权限证据。

### 16.4 工作区核对

```bash
git status --short --branch
```

确保：

- 只新增或修改本次复盘文件和必要路由。
- 未覆盖并行任务改动。
- 未把日志、截图、临时数据库、浏览器 profile 或生产数据纳入 Git。
- 文档任务没有无理由运行或修改产品代码。

## 17. Step 11：Owner 验收

向 Owner 提交：

- 报告路径。
- 覆盖范围和截止时间。
- 报告行数或大致规模。
- 已核对的 Git、文件、证据和脱敏项。
- 尚未确认的事实。
- 是否包含复盘层。
- 当前是否已 commit、push 或发布。

Owner 验收选项：

```text
通过
要求补证据
要求修正事实
要求增加复盘层
仅归档事实层
```

Owner 没有明确验收前，报告状态写“待验收”；不能把文档写完等同于结论已被
Owner 接受。

## 18. Step 12：归档与长期上下文

验收后：

1. 按提交规则决定是否创建独立 `docs` 提交。
2. 只暂存 SOP、报告和必要路由，不夹带产品代码或其他工作树改动。
3. 重要版本结论追加到 `knowledge/iteration-history.md`。
4. README 只增加高信号状态或路由，不复制报告正文。
5. 被新报告完全替代但仍需追溯的临时文件移入 `recyclebin/`。
6. push、tag、Release、部署仍按发布流程另行授权。

普通复盘文档可以使用项目允许的低风险 `docs` 提交规则；SOP 自身、治理规则
或发布门禁变更仍按工程规则判断是否需要人工提交授权。

## 19. 完成定义

以下是事实报告的完成条件：

- [ ] 起点、终点、截止时间和模式明确。
- [ ] Git、worktree、stash 和未提交状态已冻结记录。
- [ ] 证据台账完整，关键冲突已关闭或标记未知。
- [ ] 人工 Prompt 和 Agent 命令已按边界引用。
- [ ] 等待、重复、失败、回退和纠正已记录。
- [ ] 可观察判断有证据和后续动作。
- [ ] 提交链、标签目标和文件清单与 Git 一致。
- [ ] 测试、发布、迁移和观察没有跨状态表述。
- [ ] 敏感信息扫描通过。
- [ ] 报告未夹带产品改动。
- [ ] Owner 已验收，或报告明确标为待验收。
- [ ] 归档位置和长期上下文已按需更新。

### `G7 迭代已关闭`

只有同时满足以下条件，才能把迭代状态写为“已关闭”：

- [ ] 主要目标的实际用户或系统结果已与原验收对照；
- [ ] 需求、执行、候选、发布和观察状态没有混写；
- [ ] 返工、等待、失败、并行收益和人的负担有事实依据；
- [ ] 每项行动有负责人、优先级、验收方式和回流位置；
- [ ] 新需求已按 `SOP/requirement-intake.md` 登记，未塞入已关闭范围；
- [ ] 可复发工程问题已进入测试、工具、规则或 `one-mistake-one-rule.md`；
- [ ] 原迭代计划、当前状态和迭代历史已同步；
- [ ] 已按 [`worktree-lifecycle.md`](worktree-lifecycle.md) 记录保留、归档和
      删除结论，活跃工作树不超过 6 个；
- [ ] Owner 已接受复盘结论及行动项。

事实报告完成但未开展复盘，或行动尚未归属时，报告任务可以结束，但迭代状态
仍为“复盘待关闭”，不得写 `G7` 通过。

## 20. 快速执行清单

```text
1. 定义起点、终点、截止时间和“仅事实/完整复盘”模式
2. 记录所有 worktree、branch、HEAD、stash 和未提交状态
3. 收集 Git、报告、测试、生产、Prompt 和 Agent 日志
4. 建立证据台账，先关闭冲突
5. 按真实时间还原阶段主线
6. 单列等待、失败、重试、重复工作和可观察判断
7. 生成提交链、变更规模和完整文件清单
8. 写事实层；获准后再写复盘层
9. 核对哈希、标签、文件、链接、格式和敏感信息
10. 提交 Owner 验收并按规则归档
```
