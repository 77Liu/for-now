## 1. [P1] 已撤销会话仍能在竞态中完成改密

**引入提交：`675408c`。影响默认 document 模式及 PostgreSQL row 模式。**

位置：

- [改密服务](../src/modules/auth/index.mjs)：`createPasswordChange`，先 `requireUser(token)`，再独立读取凭据。
- [document 改密命令](../src/shared/persistence/auth-repository.mjs)：244–248 行。
- [PostgreSQL 改密命令](../src/shared/persistence/postgres-auth.mts)：492–500 行。

触发顺序：

1. 改密请求通过首次鉴权，会话与用户版本均为 1。
2. Owner 撤销该用户的旧会话资格，例如角色变更使用户 `sessionVersion` 升至 2。
3. 改密请求继续执行独立凭据查询，得到版本 2 的新快照。
4. 提交时只比较用户凭据与新快照，未比较会话版本 1 与用户版本 2，因而改密成功，版本再升至 3。

这违反了提交时重新确认会话有效性的要求。基线实现会在写事务内通过 `authenticationFromDocument` 检查会话世代；本次拆分后漏掉了该检查。

**复现结果：**

- 真实 PostgreSQL 命令：`sessionVersion=1`、`userVersion=2` 时返回改密成功，最终版本 3。
- 默认 document 模式的真实 `createAuthService.changePassword`：在首次鉴权与凭据读取之间注入撤销，真实 KDF 校验后密码确实被替换，最终版本 3。
- 这是需要已有会话及正确旧密码的竞态，不是任意账户接管。

**修复建议：**两种存储适配器都在提交事务内校验 session 存在、未过期、归属匹配，且 `session.sessionVersion === user.sessionVersion`；再比较凭据快照。保留锁外 KDF。新增“首次鉴权后、凭据快照读取前撤销”的服务级回归。

## 2. [P1] 新审计格式破坏用量失败后的重启恢复

**引入提交：`1bf34d3`。默认 `AI_AUDIT_DB_ENABLED=0` 即受影响。**

位置：

- [AI 审计](../src/modules/ai/audit.mjs)：296–315、398–415 行，写入用量失败后仅记录 `persistence.usage=pending` 与摘要。
- [恢复消费者](../src/app/ai-runtime.mjs)：453–494 行，仅通过 `usageEntryFromAudit` 恢复文件中的用量。
- [回归断言](../scripts/ai-domain-regression.mjs)：620 行。

旧实现会在用量写入失败时把完整 `usageRecovery` 写入终态审计，重启后按 callId 幂等补账。新实现移除了这个字段，但 `usageEntryFromAudit` 仍只识别该字段，恢复入口没有适配新格式。

因此，供应商成功、用量存储失败、审计文件成功写出后，只要进程在内存 pending Map 重试成功前退出，该次真实调用就不能被现有重启恢复路径补入账本。账户调用次数、费用统计与额度事实会少一笔。

**复现结果：**通过真实 `createAiAudit.providerCall` 注入用量写失败；供应商替身调用 1 次，终态为 `success`、用量为 `pending`；用现有恢复解析器读取实际生成的审计记录，得到 **0 条可恢复记录**。

**测试质量问题：**原来的“审计恢复内容等于用量记录”断言被改为断言 `usageEntryFromAudit(...) === null`。运行时恢复测试仍使用手工构造的旧 `usageRecovery` 数据，所以测试能够通过，却没有验证新生产者与恢复消费者相容。

**修复建议：**为仍受支持的文件模式保留完整恢复载荷，或实现新格式的无损恢复；增加“真实审计生产者 → 持久记录 → 新进程/新实例恢复 → 幂等账本”的故障测试。数据库模式也需要单独核实用量与审计分事务失败后的持久对账能力，不能把当前进程的 Map 重试等同于重启恢复。

## 3. [P2] 两个会话并发改密会形成数据库死锁

**引入提交：`675408c`。仅 PostgreSQL row 模式。**

位置：[PostgreSQL 认证](../src/shared/persistence/postgres-auth.mts)：149–161 行与 507–509 行。

`lockedAuthentication` 先锁当前 session，再锁 user；改密取得 user 后会删除该用户的所有 session。两个合法会话同时进入时：

- A 持有 session A 和 user，删除全部会话时等待 session B；
- B 已持有 session B，等待 A 持有的 user。

PostgreSQL 必须中止其中一个事务。正常账户操作因此产生数据库错误，并额外等待死锁检测。改密与其他先锁 session 再锁同一 user 的操作也应一起检查。

**复现结果：**在真实 PostgreSQL 16.14 中，让两个改密事务都完成各自 session 锁定后继续；一个成功，另一个明确失败为 **`40P01`（deadlock_detected）**。事务已回滚，没有据此声称出现半写密码。

**修复建议：**统一认证命令的锁顺序，例如先确定 userId、锁 user，再锁定并复验 session；所有涉及用户及会话的命令遵循同一顺序。回归需要使用两个真实数据库连接，验证第二个请求得到明确凭据/会话冲突，而不是死锁。

## 4. [P2] 用量数据库查询与统计页面使用不同的日界线

**引入提交：`1bf34d3`。`AI_AUDIT_DB_ENABLED=1`、非 UTC 服务时区下受影响。**

位置：

- [数据库用量读取](../src/shared/persistence/ai-usage-repository.mts)：140–150 行，默认 `timezone="UTC"`。
- [统计服务](../src/modules/statistics/index.mjs)：181 行，仅传 `from/to`。
- [费用服务](../src/modules/ai/costs.mjs)：112–117 行及 `usageDashboard`，按 `localDateKey` 计算日期。
- [部署默认时区](../deploy/for-now.env.example)：4 行，`TZ=Asia/Shanghai`。

统计页面的日期范围按本地日期解释，但数据库先用 UTC 日期过滤。以 `2026-10-17T18:00:00Z` 为例，上海时间是 10 月 18 日凌晨 2 点；查询 10 月 18 日时，数据库已经把它排除，之后的页面聚合无法补回。

**复现结果：**真实数据库插入该时间的一次调用；按当前消费者参数查询返回 **0 条 / 0 次**，显式传入 `Asia/Shanghai` 返回 **1 条 / 1 次**。这会漏掉统计范围起始日凌晨的调用及费用；不是 UTC 日额度汇总本身的错误。

**修复建议：**明确统计日的时区契约，由消费者传入一致时区，或提前计算 UTC 起止时间并进行区间查询。增加上海午夜两侧及范围首尾日期测试；额度使用 UTC 的既有契约应单独保留。
