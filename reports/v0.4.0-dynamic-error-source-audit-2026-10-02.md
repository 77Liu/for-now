## 3. 根因：同一 message 混合六种来源

`public/frontend/api/index.mjs` 当前构造 HTTP 错误的优先级是：

```text
服务端 error.message / error 字符串 → 调用方 fallback
```

错误对象同时保留 `status`、`code`、`details`、`requestId` 和 `retryAfterMs`。
因此调用方直接展示 `error.message` 会跳过更稳定的结构化字段，并可能显示：

- 供应商名、模型名、API 或密钥配置；
- HTTP/存储/幂等/任务内部措辞；
- 浏览器 `DOMException`；
- 服务端原始英文错误；
- 与当前对象数据安全无关的底层失败。

但以下本地校验已经提供可行动的用户文案：

- 图片和音频格式、数量、大小；
- 表单必填、范围和日期校验；
- 账户字段规则；
- 本地业务冲突中已经归一化的动作提示。

结论：不能全局把 `error.message` 替换成“操作失败”，也不能继续默认透传。展示层
必须依据错误来源、当前对象、操作阶段和实际留存状态生成文案。

## 4. 错误来源分类

| 来源 | 可依赖字段 | 普通用户展示规则 | 诊断保留 |
| --- | --- | --- | --- |
| 本地输入校验 | 明确的本地 public message | 可直接显示具体修正要求 | 校验类型 |
| 网络中断/超时 | name、status=0、稳定网络文案 | 说明未确认/待同步和下一步 | requestId 若有 |
| HTTP 业务错误 | status、code、details | 按 code 映射，不默认显示 message | code/status/requestId |
| 浏览器能力/权限 | DOMException name | 说明权限或能力，并给替代路径 | exception name |
| 供应商/后台任务 | task kind、status、code | 只说明当前步骤、原始内容和重试 | provider code 仅诊断 |
| 同步/版本冲突 | syncStatus、409/412、双方版本 | 说明两端差异和选择，不声称自动覆盖 | operationId/version |

禁止通过匹配服务端 message 文本来推断业务语义。稳定判断优先使用
`code/status/syncStatus/task kind`；没有稳定 code 时使用当前操作的保守 fallback。

## 5. 用户表面 inventory

### 5.1 读取与恢复

| 表面 | 当前风险 | 目标表达 |
| --- | --- | --- |
| 初始页面 load | 全局 toast 拼接原始错误 | 当前页暂时未更新；已有记录不变；重新读取 |
| 草稿/图片/音频恢复 | 四类恢复 toast 拼接原始错误 | 指明哪类草稿无法恢复、其他内容是否受影响 |
| 同步协调器恢复 | toast 透传底层错误 | 本机内容仍在；恢复网络后重试同步 |
| 后台结果同步 | toast 透传任务错误 | 结果暂未更新；原始内容不受影响 |
| 导出下载 | 页面直接显示原始错误 | 未生成文件；账户数据没有变化；重新生成 |

08D-A 已处理寻迹、通知、回收站、反馈、导出清单和个人概要的初始读取状态；本批
次重点处理用户主动操作与后台恢复，不重复实现已有状态机。

### 5.2 创建、更新与删除

当前念起、日记、思绪、日录、书间、拾句、批注、行动和小物中仍有大量
`status.textContent = error.message` 或 `showToast(error.message, "error")`。

目标按操作阶段区分：

| 阶段 | 必须回答 |
| --- | --- |
| 提交前校验 | 哪个输入需要修改 |
| 服务端未确认 | 草稿/本地队列是否仍在，是否可安全重试 |
| 已保存但刷新失败 | 明确已保存，只重试读取，不重复创建 |
| 删除未确认 | 对象是否仍在，不显示“已删除” |
| 删除已提交待同步 | 说明将在网络恢复后完成 |
| 版本冲突 | 本地与服务端内容是否都保留，在哪里选择 |

“失败”不能覆盖“已保存但刷新失败”，toast 也不能同时显示成功与失败结论。

### 5.3 图片、音频与小物

| 对象 | 风险 | 安全边界 |
| --- | --- | --- |
| 图片选择/上传 | 本地校验与服务端上传错误混用 | 草稿引用、已上传对象分别说明 |
| 原图查看 | 可能显示存储或附件内部错误 | 只说当前原图无法读取，可返回原记录 |
| 图片理解 | 供应商错误进入就地状态与 toast | 原图已保留；只重试理解 |
| 录音权限 | 浏览器错误文本直接进入状态 | 正文仍在；允许选择音频文件 |
| 转写 | 任务错误直接 toast | 原音已保留；只重试转写 |
| 语音播放 | DOMException 直接 toast | 说明无法播放，不暗示原音丢失 |
| 小物抠图/理解 | 分割、读取、候选错误混放 | 原图、轮廓、候选和正式记录分别反馈 |

本地 `validatedImageFiles`、音频验证等明确校验文案可保留；浏览器、HTTP 和供应商
错误必须经过对象映射。

### 5.4 AI 回答与后台任务

以下普通用户路径仍拼接原始动态错误：

- 思绪即时回答；
- 回答草稿；
- 追问回答；
- 日记回望；
- 批注应答；
- 认知复盘；
- 后台任务排队和结果同步。

统一边界：

1. 用户原文或问题是否已经保存；
2. 失败发生在排队、生成、保存结果还是刷新；
3. 重试是否会复用幂等键，避免重复费用或对象；
4. 旧输入完成的结果不得覆盖当前输入；
5. 普通文案不出现供应商、模型档位、Token 或内部 task code。

### 5.5 认证与账户

登录、注册、改用户名、改密码、退出和 bootstrap 仍直接展示动态 message。应分为：

- 字段不合法；
- 凭据不匹配；
- 会话过期；
- 网络不可用；
- 服务端暂时不可用。

退出失败时“本地内容已锁定”可以保留，但后半段不应拼接内部错误。账户操作不得
把另一个账户的错误、草稿或请求结果带入当前会话。

### 5.6 Owner/管理表面

统计、AI 成本、架构、商业化、本地测试和模型设置允许比普通页面更详细，但也应
分两层：

- 首层：用户可行动的摘要；
- 诊断详情：`code/status/requestId` 和必要配置线索。

在 08D-C capability 完成前，不新增“显示诊断”入口，也不把管理错误规范当作
普通用户可见性的解决方案。

## 6. 错误展示契约

建议建立单一展示函数，输入错误和明确上下文，输出结构化结果，而不是返回一个
不带语义的字符串：

```text
presentError(error, {
  operation,
  object,
  phase,
  retained,
  retry,
  diagnostic
})
→ {
  message,
  kind,
  action,
  diagnostic: { code, status, requestId }
}
```

约束：

1. `retained` 必须由调用点依据真实状态传入，不能由错误类型猜测。
2. `message` 固定回答“发生了什么、什么仍安全、下一步”。
3. `action` 最多一个主恢复动作。
4. 普通 UI 不读取 `diagnostic`。
5. 未知错误使用当前 operation 的保守文案，不显示原始 message。
6. 本地公开校验必须显式标记，不能依赖字符串白名单。
7. `requestId` 只用于诊断和支持，不进入默认 toast。

推荐稳定错误族：

| 错误族 | 普通文案方向 |
| --- | --- |
| `validation` | 指明字段或文件约束 |
| `network` | 当前操作尚未确认；说明本地留存 |
| `auth` | 当前身份状态与重新登录/重试 |
| `conflict` | 两端有差异；保留双方并选择 |
| `not_found` | 对象不可用；返回安全列表 |
| `permission` | 当前账户无权访问；不展示旧数据 |
| `rate_limit` | 当前额度/频率暂不可用；说明何时再试 |
| `processing` | 当前派生步骤失败；原始内容保留 |
| `unknown` | 当前操作未完成；保守恢复动作 |

## 7. 推理可见性审计

候选中 `reasoningDisclosure(...)` 有 1 个定义和 7 个普通页面调用点：

1. 有效批注中的应答；
2. 漂流批注中的应答；
3. 思绪回答块；
4. 追问回答；
5. 日记回望；
6. 共参回答；
7. 认知复盘。

此外，即时回答 modal 会实时展示 reasoning 流，并在完成后保留可展开内容。现有
UI 回归还明确断言 reasoning 可见，并输出 `/tmp/growth-saved-reasoning.png`。

普通用户目标：

- 展示回答、AI 应答标识、必要来源和“本次参考”；
- 不展示供应商内部 reasoning、思考链或完整推理流；
- 不删除服务端审计数据；
- 不把 reasoning 写入用户原文；
- 只有未来通过 capability 的诊断表面可按授权读取。

因此 08D-B 需要同时修改渲染和测试，不能只用 CSS 隐藏。普通 DOM 中不应存在
reasoning 内容，避免复制、读屏、查找和无障碍树继续暴露。

## 8. 来源标签审计

6 处“用户原文”按职责分为：

| 位置 | 结论 |
| --- | --- |
| 每个非 AI 思绪块 | 改为只在与 AI 内容并列且来源可能混淆时显示 |
| 每条追问摘要 | 默认删除；“追问”已经说明对象 |
| 每条备注 | 默认删除；“备注”已经说明对象 |
| 商业化证据判断 | Owner 页面，可保留以说明只使用原文 |
| 商业化证据计数 | Owner 页面，可保留 |
| 寻迹跨体裁来源 fallback | 可保留，承担真实来源职责 |

“原文”不是禁用词。只有当用户内容与 AI 派生内容并列、跨体裁搜索或证据核对时，
它才提供必要边界；纯用户列表中重复贴标签属于证明式文案。

## 11. 验收

### 11.1 静态门

- 普通用户 sink 不再直接写入 `error.message/err.message`；
- 允许内部记录错误对象，但必须在展示前映射；
- 普通 DOM 不包含 `reasoningContent` 内容；
- 不通过 CSS、`hidden` 或不可发现 URL 冒充角色隔离；
- 3 处纯用户内容的固定“用户原文”标签删除或按并列条件显示。

### 11.2 自动化场景

至少注入以下内部 sentinel，并断言页面、toast 和无障碍树均不出现：

```text
DISCOVERY_BACKEND_INTERNAL
PROVIDER_TIMEOUT_DEEPSEEK
OSS_NO_SUCH_KEY_INTERNAL
WORKER_LEASE_EXPIRED
AUTH_STORAGE_READ_FAILED
```

每个关键操作断言：

- 当前对象和失败阶段清楚；
- 原文、草稿、原图或原音的安全状态准确；
- 只有一个下一步；
- 重试不重复创建对象或费用；
- 已保存但刷新失败不显示“保存失败”；
- 账户切换后旧错误和异步结果不出现。
