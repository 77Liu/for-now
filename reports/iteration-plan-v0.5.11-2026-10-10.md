### 本版实施

- 新用户完成五问，老用户通过清楚标示的补答入口继续；用户可跳过或表达未知，
  不从旧记录静默生成核心模型。
- 冷启任务本身可运行并建立 `ready` 核心模型；其他需要个性化上下文的 AI
  请求在模型未就绪时持久等待，不预编译上下文或调用回答模型。就绪后使用当时
  最新的有效模型、许可和当前问题重新编译；过期、取消或跨账户任务不执行。
- 每次相关回答将核心模型作为稳定序列化前缀携带。模型项保留用户答案来源和
  精确原文片段；未知/拒答显式保留。AI答案、预测及来源不明内容不得进入核心模型。
- 回答引用仅接受本次请求实际提供且仍有效的来源 ID；由服务端校验。模型卡注明
  “本次已携带”，不将编排等同于实际引用。普通账户的 API 与界面都不暴露模型
  细节；只有现有服务端 Owner 身份可展开。
- 复用当前问卷、证据许可、持久任务、用户模型和上下文回执；只增加完成上述闭环
  所需的状态/契约，不引入新的任务平台或通用学习系统。

## 2. 可验证结果

1. 新用户与老用户补答均能生成核心模型；空答案/全跳过不产生虚假 ready 模型。
2. 核心生成可排队、取消、失败重试和服务重启恢复；来源变化或撤权会使旧模型
   失效，不能由过期结果覆盖新版本。
3. 核心未 ready 时，其他 AI 请求只保存待处理意图，provider 调用数为零；ready
   后才编译上下文，且包含最新核心、当前问题与当前有效来源。
4. 相同模型版本的核心序列化字节稳定；动态状态位于该稳定前缀之后。
5. 引用通过/伪造/过期/未提供来源的服务端校验；普通账户 API 不返回私有模型
   细节，Owner API 可以读取；UI 不给普通账户伪装成可展开的交互。
6. 运行现有 onboarding、用户模型、任务上下文、权限/来源边界与相关 Journey
   测试，并增加一条核心 ready/等待/引用闭环回归及其用户旅程登记。

## 3. 风险与阶段

G1 已冻结上述三个需求，不自动接入未知状态的 UI 候选。G2 先固定 readiness 与
等待任务的持久化契约、核心序列化和引用校验边界；G3 由功能专项覆盖代码结果，
再做一次同候选独立 review。当前没有新数据库 DDL 计划；若实现证明必须新增，先
单独说明迁移和恢复影响并按该影响补测。G4-G5 和生产部署已完成；G6 等待 30 分钟观察闭环，G7 随后复盘。

当前仍未验证 provider 对引用标记的实际遵循情况，因此 P00 仅承诺服务端可核验
引用，不将模型声称视作已使用来源的证明。真实 provider 回放单独按固定夹具和
有界费用授权执行，不阻塞无付费的核心确定性验证。
