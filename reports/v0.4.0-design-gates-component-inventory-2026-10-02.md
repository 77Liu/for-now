## 3. G0：问题成立

### 3.1 用户问题

当前问题可由用户行为描述，而不是审美偏好描述：

- 记录前要扫描图片、语音、标签、时间等并列模块；
- 内容、操作、系统状态和技术说明争夺同一层注意力；
- 保存、同步、附件上传和 AI 处理边界不稳定；
- “我的”同时出现个人入口、供应商、成本、架构和商业化能力；
- 相同按钮、状态、圆角、断点和页面标题在不同页面继续分化。

### 3.2 范围

任务 04 负责：

- 用户任务和页面职责；
- 一级/二级导航与角色可见范围；
- 全站内容职责；
- 正常、空、加载、失败、权限、冲突和恢复路径；
- 为任务 05 提供可实施的结构输入。

不负责：

- 直接重写生产页面；
- 修改 API、业务对象、数据口径、认证或持久化；
- 决定 AI 预算和 Apple 分发输入；
- 执行生产迁移、真实供应商调用或发布。

### 3.3 结论

问题、版本、范围和非目标均可验证，`G0 = 通过`。

## 5. G2：结构冻结

### 5.1 已形成的候选

- 一级导航保持“今日、所见、所思、我的”；
- 导航最多三级，主任务在所属一级入口两次操作内可达；
- 页面按用户任务而不是数据库对象组织；
- “我的”只应默认承载账户、同步和关键设置；
- AI 成本、架构、商业化、本地测试、供应商和模型密钥属于 Owner/开发表面；
- 原型路由仅用于评审，不替代生产深链和历史恢复。

### 5.2 Owner 必须逐项确认

| 决策 ID | 待确认内容 | 未确认的影响 |
| --- | --- | --- |
| G2-D1 | 24 个视图的页面职责表 | 无法判断保留、拆分或后移 |
| G2-D2 | 一级/二级导航和“我的”入口集合 | AppShell 不能冻结 |
| G2-D3 | 普通用户、专业用户、Owner 的可见范围 | 08D-C 不能实施 |
| G2-D4 | 每页唯一首要任务和主操作 | PageHeader/PrimaryAction 不能验收 |
| G2-D5 | AI 成本、架构、商业化、测试设置的去向 | 不能仅靠 CSS 隐藏 |
| G2-D6 | 旧 URL、浏览器返回、筛选和滚动恢复方式 | 页面迁移会产生兼容风险 |

### 5.3 当前实现冲突

`public/frontend/pages/index.mjs` 把 AI 成本、架构和商业化与普通“我的”页面归入
同一 section；`public/index.html` 也直接展示这些入口。当前认证模型没有可复用的
页面 capability。视觉隐藏、删除菜单项或依赖难猜 URL 都不能替代授权。

### 5.4 URL 与返回历史事实

当前 24 个视图没有页面级 URL：

| 行为 | 当前实现 |
| --- | --- |
| 页面标识 | `data-view` 和模块内 `currentView` |
| 地址栏 | 页面切换时不写 path、query 或 hash |
| 浏览器返回/前进 | 没有 `popstate` / `hashchange` 监听 |
| 普通切页 | `switchView()` 激活 DOM，并平滑滚动到顶部 |
| 页面内返回 | `data-view="mine"` 等按钮再次调用 `switchView()` |
| 全局重绘 | `restoreView()` 只恢复内存中的当前视图，不运行 effect |
| 刷新/新标签 | bootstrap 重新进入 `today`，不能恢复原页面 |
| 对象定位 | 先修改内存筛选/对象 ID，再切页并 `scrollIntoView()` |
| 异步局部合并 | 只临时保存当前滚动位置，不构成页面历史 |

`frontend-shell-regression` 验证的是未知 view 名称回退 `today`，不是旧 URL 映射。
因此 G2-D6 的准确问题不是“保留哪些现有页面 URL”，而是：

1. 根入口和 `/platform/` 等现有外部入口保持兼容；
2. 首次建立页面/对象 canonical URL；
3. 定义新 URL 上线后的旧书签迁移策略；
4. 定义浏览器返回、界面返回、刷新和深链的一致行为。

页面迁移前必须确认：

- 使用 path、query 或 hash 中的哪一种 URL 契约；
- 哪些切换使用 `pushState`，哪些局部状态使用 `replaceState`；
- 页面、筛选、选中对象和详情分别进入哪一级 URL；
- 返回列表时如何恢复滚动、筛选和展开状态；
- 无效或无权限 URL 返回安全列表、404 还是权限页；
- 旧根 URL 如何继续进入默认页面。

### 5.5 capability 与管理员边界事实

当前普通认证用户公开结构只有：

```text
id, username, createdAt
```

认证文档、session 和 `/api/auth/me` 都没有 role/capability。业务 API 在账户认证
之后按账户隔离，但没有“普通用户/专业用户/Owner”页面能力判断。

现有 `/api/admin/v1/snapshot` 也不能复用为用户 Owner 权限：

- 只允许主应用所在机器的回环请求；
- 要求独立 Bearer 服务令牌；
- 浏览器和普通 session 都不能读取该令牌；
- 输出是给独立中台的脱敏聚合，不是用户页面数据；
- Nginx 对公网主应用路径固定返回 404。

`/platform/` 是独立中台入口，使用自己的账户权限。它证明“管理表面与用户产品
分离”在系统中已有先例，但不提供主应用页面 capability。

G2-D3 至少需要 Owner 确认：

- capability 是附着于用户、独立 Owner 身份，还是完全迁出主应用；
- 现有账户默认能力和迁移规则；
- API、页面入口和直接 URL 使用同一服务端判定；
- 未授权时返回 403、404 或安全列表；
- 专业用户是否存在，若存在可访问哪些来源/诊断而非全局管理信息；
- Owner 能力的授予、撤销、审计和会话失效方式。

未形成服务端 capability 前，不新增只在前端判断的 `isOwner`、用户名白名单、
首账户特权或隐藏菜单方案。

### 5.6 建议决策顺序

1. 先确认普通/专业/Owner 的信息范围和管理表面归属。
2. 再确认服务端 capability 来源、默认值和直接 URL 行为。
3. 确认页面职责后选择 canonical URL 与 history 契约。
4. 冻结 AppShell 导航、返回和滚动恢复。
5. 最后实施 08D-C、07A 和页面迁移。

角色和 URL 若同时迁移，必须先让服务端拒绝越权访问，再显示对应入口；不能先上线
可猜 URL，再等待后续补授权。

### 5.7 结论

`G2 = 待 Owner 决策`。G2 通过前：

- 不迁移生产导航和页面职责；
- 不实现 08D-C；
- 不删除现有入口或自行发明深链；
- 不把 05A 基础样式扩散到全站页面。

## 10. 明确禁止的全局重构

05A 不得：

1. 全局覆盖 `:root` 或一次性替换 607 个颜色字面量。
2. 重写通用 `.card`、`button`、`input`、`.status` 使未迁移页面被动变样。
3. 把原型 `app.js`、原型 localStorage 或演示数据复制进生产 runtime。
4. 同时迁移 24 个视图，或用一组全局 CSS 声称完成页面迁移。
5. 改变思绪、念起、日记、媒体、时间、来源、版本和权限语义。
6. 删除管理入口、隐藏 URL 或用 CSS 冒充 capability。
7. 修改 API、认证、数据库、费用、供应商和生产配置。
8. 以截图相似替代键盘、读屏、失败恢复和持久化验证。
