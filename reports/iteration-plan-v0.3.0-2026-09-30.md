## 6. 个人上下文·可见的边界

本切片先回答两个问题：

1. 系统目前如何依据用户自己的记录描述这个人？
2. 本次 AI 回答实际使用了哪些记录？

最小输出包括：

- 一份只读、结构化的个人概要。
- 概要的生成时间、版本、时间窗和 Token 预算。
- 每条结论对应的用户原始记录来源。
- 用户事实、用户观点、模型摘要三类信息的明确区分。
- AI 回答中的“本次参考”入口，展示记录类型、发生时间、来源定位和必要摘录。

本切片不包括：

- 自动形成长期记忆。
- 用户逐项排除或调整上下文预算。
- 对概要进行人工纠正并回写派生记忆。
- 知识图谱、向量服务和外部上下文连接器。

删除、回收、越权或不允许进入上下文的记录不得被采用，这是既有数据安全
边界，不因“可纠正”后置而放宽。

## 9. 串并行开发流程

默认采用一个实现任务加一个独立审查角色。连续两轮交付都能在无返工合并、
无工作树遗留的情况下关闭后，才允许同时运行两个实现任务。

```mermaid
flowchart TD
  MAIN["main\n已集成并通过规定检查"] --> SCOPE["串行冻结本批范围、契约与文件所有权"]
  SCOPE --> FEAT_A["实现线 A\nfeat/v0.3.0-xx-a"]
  SCOPE --> REVIEW["审查线\n只读检查契约、测试与风险"]
  SCOPE --> CAN_TWO{"前两轮流程是否稳定"}
  CAN_TWO -->|否| FEAT_A
  CAN_TWO -->|是| FEAT_B["实现线 B\nfeat/v0.3.0-xx-b"]
  FEAT_A --> LOCAL_A["任务专项 + 本地提交"]
  FEAT_B --> LOCAL_B["任务专项 + 本地提交"]
  REVIEW --> GATE["串行集成门"]
  LOCAL_A --> GATE
  LOCAL_B --> GATE
  GATE --> RELEASE["release/v0.2.x\n逐提交审查、影响测试"]
  RELEASE --> FULL["完整功能回归\n适用时加 PostgreSQL/恢复专项"]
  FULL --> APPROVE{"人工批准远端操作"}
  APPROVE -->|否| HOLD["保留本地候选与证据"]
  APPROVE -->|是| MAIN_MERGE["并入 main\npush/tag/Release/部署分别确认"]
  MAIN_MERGE --> CLEAN["记录交付提交并归档工作树"]
```

并行边界：

- 同一共享契约、schema、模块登记、根入口、全局样式或依赖锁只有一个负责人。
- 两条实现线必须有不同的模块所有权、端口、数据目录和测试资源。
- PostgreSQL 工作树必须使用独立临时集群或独立数据库，不能只换 HTTP 端口。
- 发现公共契约缺口时暂停支线，回到串行任务修订并重新冻结。
- 每个工作树只承载一个任务；提交后记录 SHA，合并后立即归档。

## 10. 小版本合入流程

```mermaid
flowchart LR
  ISSUE["需求池记录"] --> TASK["V0.3.0-xx 交付任务"]
  TASK --> BRANCH["短期 feat/fix/test/docs 分支"]
  BRANCH --> COMMIT["可验收切片本地提交"]
  COMMIT --> INTEGRATE["release/v0.2.x 串行集成"]
  INTEGRATE --> VERIFY["固定 SHA 分层验证"]
  VERIFY --> MAIN["经授权并入 main"]
  MAIN --> EVIDENCE["回填需求与交付证据"]
  EVIDENCE --> NEXT["下一 v0.2.x 批次"]
```

每个 `v0.2.x` 批次必须满足：

1. 范围、依赖、允许修改目录和共享文件负责人已经写明。
2. 每项需求有验收标准、专项测试和失败恢复路径。
3. 功能分支从已提交的 `main` 基线创建，不复制未提交工作区。
4. 合并按依赖顺序逐个执行，每次合并后运行影响矩阵命中的测试。
5. 固定候选 SHA 后再运行全量回归；测试报告引用该 SHA。
6. 文档或证据更新是否导致重跑，由其对候选代码和运行配置的影响决定。
7. push、tag、Gitee Release、部署和生产写入逐次取得人工授权。

## 11. 分层验证

| 阶段 | 最低验证 |
| --- | --- |
| 开发调试 | 当前功能专项；失败先保留可复现断言 |
| 任务交付 | `npm run check` 加影响矩阵命中的后端或前端测试 |
| 合并批次 | 合并后相关集成测试；共享契约变化扩大到完整一侧 |
| 小版本候选 | 干净候选 `npm run test:system`；持久化变化追加 `npm run test:postgres:stable` |
| 恢复相关候选 | PostgreSQL、备份、逻辑恢复和数据库级恢复专项 |
| 上线后 | 运行版本、核心操作、错误日志、资源和观察窗口 |

不因没有代码变化重复调查同一环境问题。候选 SHA、依赖、测试脚本或环境没有
变化时复用有效证据；任一项变化时只重跑受影响层级。发布候选最终仍必须从
干净目录执行规定的完整检查。

## 12. Git 规则

1. 一个任务一个短分支；需要并行时再创建独立工作树。
2. 所有任务从已提交基线开始。
3. 完成一个可验收切片就提交。
4. 多任务始终串行合并，并验证合并后的结果。
5. 任务结束记录交付提交并归档工作树。
6. 本地低风险提交只允许在明确任务范围内执行；新增依赖、公共契约、数据库
   迁移、认证、部署和生产相关变化先说明。
7. 任何远端 push、tag、Release、部署和生产写入仍需本次人工明确授权。

每次交付固定报告：

```text
任务：

未提交内容及原因：
是否已合并：
工作树保留或归档：
下一步需要 Owner 决定什么：
```
