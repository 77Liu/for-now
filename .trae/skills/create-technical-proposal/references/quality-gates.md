# 技术方案质量检查

按每份需求独立检查。评审格式、行级入口及生效范围只按[项目评审规则](../../../../knowledge/review-presentation-rules.md)；旧稿使用历史布局校验，不要求回溯改排。以下检查不代表 Owner 已批准。

## 1. 先检查是否回答了需求

- 文档数与独立需求数相同；子任务和协作方没有被误拆成独立需求。
- 每个需求点均能追踪到设计、协议/实体/代码、用例和观测方式；范围外内容有边界。
- 每份方案可独立评审。跨需求共享设计写出必要契约、版本和依赖，再链接公共材料，不能让 Owner 靠拼接多篇文档理解关键行为。
- 输出是已保存的完整文档，非提纲或模板复述。除评审阶段 4.1 外，不留空白必填节。
- 主动建议和事实分开；没有“已完成研发”“测试通过”“依赖方已承诺”等无证据断言。

## 2. 检查证据与决策

- 现状引用真实需求文档、已读代码、协议或日志证据，记录版本/读取时间；引用材料的结论适用范围准确。
- 未能访问的文档明确标记未读，不能用标题推导内部细节。
- 代码路径、符号和接口如未验证，标注拟新增或待核对；不得把设计建议写成已有实现。
- 未知基线、SLO、流量、容量、费用和目标收益不补伪造数字。建议参数写依据与校准方式。
- 有备选方案时，使用同一需求、负载、兼容和成本口径比较；明确推荐和放弃理由。无需备选时写真实限制。
- 关键未知项有推荐、影响和核对责任，不是一长串无优先级问题；非阻塞缺口不应阻止完成其他章节。
- 示例仅是写法参考，不能成为当前需求中的系统、姓名、时间、配置默认值或指标事实。
- 对照[固定导读顺序](../../../../knowledge/review-presentation-rules.md#评审稿的固定导读顺序)检查新稿标题和五列决策表，确认名词表紧跟决策表、来源位于导读区最后。
- 对照[名词解释规则](../../../../knowledge/review-presentation-rules.md#名词解释的选择与写法)逐个读摘要与决策表中的术语、方法名和通用动词；三列表语境必须来自本文真实原句，解释不依赖未解释的上下文。
- 真实评审意见已贯穿所有受影响章节；保留修订历史，区分单项决定与全稿审批状态。

## 3. 检查上下游是否闭合

建立临时核对表，逐项标记“图中存在 / 正文解释 / 协议定义 / 代码或负责方 / 用例覆盖”：

|对象|至少核对的范围|
|---|---|
|生产入口|用户请求、后台操作、批量导入、定时任务、MQ、回调、重试、补偿及历史入口|
|外部依赖|数据源、模型、审核、资源平台、元信息、鉴权与配置中心，按实际需求取舍|
|写入与状态|数据库、缓存、对象存储、索引、消息、阶段标记、幂等记录|
|消费者|C 端、后台、审核前端、其他服务、Feed/Push/搜索/离线等实际消费面，包括不改协议的消费者|
|边与分支|同步/异步、成功/拒绝/失败、超时、重试/死信/补偿、终态和生效时机|

- 图和表覆盖所有已识别对象；枚举了核查范围和未确认的具体缺口。
- 同一对象命名一致，不把展示值、持久化值和事实源混用。
- 图中的每条路径能解释最终结果；每个外部请求/副作用能找到失败处理。
- Mermaid 可解析且可阅读，节点 ID 稳定，复杂节点文字加引号；长链路拆图并保持关联，不用截图代替唯一的可编辑源。
- 重要生产与消费动作分别有事务陈述表：处理动作、原所在事务、本次事务、事务粒度、事务内新增逻辑、事务外与提交后。现有事务有证据；没有事务说明原因，内存锁/文件替换不冒称数据库事务。
- 粒度包含业务作用范围和实际锁范围、开始/提交时点；新增校验/写入、回滚、外部副作用及提交后的可见性与流程和伪代码一致，不能只写“短事务”。

## 4. 检查协议与实现的一致性

对关键字段或状态逐个穿行：

`生产示例 → 请求/回调 → 数据实体 → 存储 → 打包/转换 → 消费示例 → 伪代码 → 用例`

- 名称、大小写、路径、层级、类型、空值、枚举、单位和编码完全一致；不能同时出现两套未说明映射的字段。
- 每个实体包含业务键、事实源、约束和生命周期；需要持久化时明确索引、TTL、迁移与清理，无则说明。
- 每个变更接口包含契约、鉴权、预算、错误语义、重试及幂等；本方无新入口不等于依赖方无新接口。
- 所有配置集中登记，示例、默认值、作用域、读取时机、依赖、开关组合与关闭行为一致。
- 旧写者/新读者、新写者/旧读者、版本混跑分别有策略。既有协议新增必选字段必须给迁移依据；独立新协议允许合理的必选字段。
- “复用”有能力边界证据；“不直接复用”解释状态、上下文、副作用、签名或性能差异，不能只写风格偏好。
- 核心伪代码不是成功路径摘要，必须落实文字承诺的关键约束；每个 return/error 都能对上异常处理。
- 所有 JSON 示例为独立 `json` 围栏，2 空格缩进，字段与非空数组元素逐行展开，可用 JSON 解析器读取；禁止单行、表格内/行内 JSON、注释或省略号。类型声明不能冒充 JSON 样例。
- 数据实体结构包括嵌套对象，每字段独占一行；检查分号/逗号拼字段及同一行开闭对象的情况。
- 核心伪代码的每个流程代码块均为小写 `python` 围栏且通过 `ast.parse` 语法检查。变量/helper 可以未定义、算法可抽象；不要求运行或类型检查。不能把 JS/TS 伪代码改围栏后视为合格；保留工程签名表与伪代码的语义对应。

## 5. 检查异常、性能与状态

- 非法/空/部分响应、超时、依赖不可用、读写失败、权限错误、重复/乱序/并发事件均按实际风险覆盖。
- 明确每种异常是放弃本次、降级、重试、补偿还是人工处置；写清用户可见结果、允许的持久化、停止条件与恢复方式。
- 容量公式带单位和假设。例如下游峰值调用量由入口峰值 × 扇出 × 实际重试放大估算；并发可按请求率 × 平均耗时估算，并用压测校正。
- 总耗时预算与各阶段超时/重试/并发相容，明确串并行。禁止各接口分别给很大超时却承诺更小的端到端预算。
- 队列积压、载荷、批量、缓存、并发和资源使用均有边界；过载后的结果明确。
- 幂等键包含正确业务维度，TTL 覆盖实际重试/回放窗口；不要只写“加锁保证幂等”。
- 明确外部副作用成功而本地标记失败、租约过期、并发重复、部分落库和旧回调晚到的窗口。说明如何防重复和旧版本覆盖。
- 状态、事实源、历史数据和在途任务在灰度、降级、关闭开关后仍满足不变量。

## 6. 检查可验证与可观测性

- 每个验收用例写前置条件、输入/操作、实际可观察输出、持久化/副作用和通过标准。
- 正常、边界、故障、兼容、并发、回滚覆盖与设计风险相符，不用大量重复用例伪装覆盖率。
- Mock 只替换明确依赖，保留真实协议和关键校验；随机方案可复现；隔离测试环境并能切换回真实依赖。
- Mock 通过不能证明真实模型效果、依赖吞吐、真实鉴权或第三方 SLA 达标。
- 指标有分子/分母、单位、统计窗口、维度、阈值状态、最低样本和告警后动作。
- 监控既覆盖服务内部，也覆盖最终用户可用性。请求 ID 等高基数信息用于受控日志/追踪，不直接充当指标标签。
- 告警、实验护栏、上线观测和回滚阈值引用同一规则，不能各节写不同值。
- 效果观测区分功能通过、稳定性达标和业务收益；样本不足标记不确定，不下因果结论。

## 7. 检查上线与回滚是否可执行

- 上线依赖是具体的先后关系：多端与服务内部组件、协议、存储、元信息、生成代码、配置和开关；允许并行的步骤有就绪依据。
- 每个放量阶段有范围/比例、停留时间或样本、护栏、负责角色和下一步条件；建议值未伪装为已对齐。
- 服务回滚、代码回滚、数据回滚分别说明操作与验证；目标版本未知时标待确认而不捏造版本号。
- 关闭开关后说明新流量、旧数据、在途消息、缓存和外部副作用如何处理；不自动认为旧代码能读新数据。
- 无法逆转的动作给补偿方案与限制，不承诺“恢复数据库即可”。
- 上线 CheckList 未把计划勾为完成，依赖交付和观测证据可定位。
- 评审阶段 4.1 完全空白；开发后只按真实证据回填。编写方案不等于获得执行上线或联系协作方的授权。

## 8. 完稿处理

1. 修正可从现有资料和推导解决的问题，直到全文约束一致。
2. 缺外部证据而影响主要结论时，在评审摘要写明前提和待决项；提供条件化推荐，不能宣称已满足上线条件。
3. 运行结构脚本，按新稿或历史稿选择布局，检查文件数量、导读与决策表、固定目录、占位符、图块、4.1 阶段规则、语境文本出现性、事务表、JSON/字段格式及 Python 语法。自动检查不能证明语境是完整原句、术语覆盖充分或事务设计正确。
4. 复核链接、附件、表格、代码围栏和最终格式中的图。工具不能渲染时明确技术限制并保留可编辑图源，不谎称已视觉验证。
5. 最终交付对照[重点评审表规则](../../../../knowledge/review-presentation-rules.md#agent-交付中的重点评审表)，逐行核对逻辑链粒度、链下追加的具体背景与当前问题、两列实际行级链接和决策状态。人工验收每行是否无需其他对话、表格行或链接正文便能理解关注点并作决定；背景缺失时补写，不以字数短或链接齐全代替可理解性。不要把脚本结构检查称作“高质量认证”或“Owner 审核通过”。
