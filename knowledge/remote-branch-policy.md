# Git 分支职责与远程保护规则

版本：1.2；生效日期：2026-10-13。本文是本地分支职责、普通开发起点、远程分支命名/保护和历史调整的唯一正文。既有远程引用、标签及历史不改写；远程规则从下一次 push 起执行。

## 分支职责

普通业务、测试、构建、配置和工具代码，以及规则与其他文档修改，统一在从当前 `develop` 创建的 `feat/*` 上编写。协调者负责 develop 的串行集成；开发 Agent 在指定 feat 上实现。不得从未集成 feat 再派生开发线。

| 分支 | 允许内容与推进 | 不允许 |
| --- | --- | --- |
| `develop` | 唯一普通开发基线及集成线；接入已审查切片和规则文档 | 将未验证分支直接宣称为生产 |
| `feat/<主题>` | 从明确 develop SHA 创建；功能、非生产修复、测试、工具、构建、规则和文档切片；验收后回 develop | 从其他分支继续开发；绕过共享写集责任 |
| `main` | 正式发布版本的稳定引用；在相应发布事实成立后由协调者按保护规则推进 | 编写代码、独立文档提交、未发布候选、日常开发入口 |
| `release/<版本或候选ID>` | 从 develop 固定发布候选；只接收协调者已核对的候选引用/集成结果并验证 | 就地修代码、改版本/依赖/配置或写发布报告；以“候选修正”为名继续开发 |
| `preview/<候选ID>` | 指向用于预览部署的精确候选；记录预期部署对象，实际是否部署由回执证明 | 产生独立开发提交；将分支存在当作部署成功 |
| `hotfix/<事件ID>` | 跟进实际生产基线的紧急修复候选及验证；只接收审查后的修复投影 | 在 hotfix 上直接编写代码、普通需求开发或混入尚未发布功能 |
| `docs/<主题>` | 仅保留既有分支引用供协调者裁定审计或恢复 | 新建分支或承载后续写入；自动删除既有分支 |

main、release、preview、hotfix 均不得作为新的普通功能分支起点；既有 docs 分支保留为历史引用，不自动删除或续写。所有实现及规则/文档修改统一在从当前 develop 创建的 feat 上完成，再经审查接入 develop。版本号、包清单、测试矩阵的可执行实现也属于代码/配置。

## 候选修复与热修回流

- 候选发现缺陷：回 develop/feat 修复并验证，再生成新候选 ID 和 SHA。旧候选及失败证据保留，绝不移动已发布标签。
- 紧急热修：协调者可从已核验的生产提交建立 hotfix 跟踪/组装线；**修复代码仍在从 develop 创建的 feat 中编写并审查**。协调者将最小已验证修复选择性投影到生产基线上，在实际热修 tree 上验证兼容性；投影是受控接入，不是在 hotfix 上继续开发。
- 投影有冲突或依赖未发布功能时，退回 feat 准备兼容修复，不在 hotfix 上现场改代码，不把 develop 全量带入生产。
- 正式发布后 main 记录对应的正式提交；热修结果核对已进入 develop，并使受影响的在途 release 重新取证。生产运行 SHA 不因 main 名称或 ahead/behind 推断。
- main 晋级前检查祖先关系和制品身份。不能安全快进或会生成未经核验的新运行内容时，先回 develop/feat 解决集成，再固定候选；禁止靠 force push、重置正式标签或现场改 main 绕过。
- 候选、tag、制品和运行 SHA/摘要的对应关系由控制面保存；分支移动不替代部署。

## 远程保护与生命周期

1. 长期分支只有 main 与 develop；目前不创建独立平台线。既有 platform、codex、fix、chore 等引用保留历史身份，不自动迁移或删除。新普通代码任务统一使用 feat；提交类型仍可用 fix/test/build 等表达实际目的。
2. main/develop 禁止普通直接推送、强推、删除和历史重写；用 PR 或托管平台可强制验证的等价受保护合入。获准的协调/发布机器人可以执行这些动作，但必须受同一状态检查和审查约束。文档批准不等于远端保护已经配置。
3. release/preview/hotfix 引用仅由协调者指定的发布执行者推进；发布标签不可变。缺少必要保护时先补齐对应配置，不凭手工审查记录绕过机器保护。
4. 每个任务记录起始分支/SHA、规则基线、角色、写集和验证范围。所有权与当前状态只读[控制面](coordination-control-plane.md)，不能靠分支名称推断。
5. 短期分支在成果接入或明确裁定后关闭；回收前核对唯一提交、活跃依赖、工作树和恢复证据。远程删除须处于相应授权范围，不能因任务关闭自动删除历史引用。
6. archive/ref 与旧工作树仅用于审计恢复。需要复用时在当前 develop/feat 选择性重建并验证，禁止恢复后直接续写。

## 提交历史与规则生效

共享历史默认只追加提交或回滚提交，不强制重写 main、共享 develop、正式 tag 或既有发布记录。未共享短期提交可以经协调者审查后整理；任何远程历史重写另立方案。

规则修改在当前指定 feat 上与相应实现一并完成，经审查接入 develop 后生效；协调者通知受影响任务使用该规则 commit。冻结候选的代码不因规则更新被暗中替换；需改变代码时走新的 feat/候选。各工作树读取的规则版本由控制面引用，禁止把物理根目录中较旧的 main 文档冒充现行规则。

## 新规则启动前整理

状态模型或自动发布策略变更后，普通开发恢复前必须由协调者完成一次可回滚的启动整理：

1. 记录 `main`、`develop`、正式标签、远端引用、所有工作树、stash、未提交差分和未跟踪文件；每份差分都有责任人、SHA-256 和归档位置。
2. 在从当前 `develop` 建立的唯一 `feat/*` 上维护规则变更；只接入已审查的规则，不从旧 `release/*`、`preview/*`、`hotfix/*`、`docs/*` 或归档分支续写。
3. 初始化 `coordination/current.json`，写入协调者、规则基线、工作模式和未知项；未知项不补成通过。
4. 核对远程保护能否阻止 main/develop 直接推送、强推、删除和历史重写；保护未生效前不以人工记录替代机器检查。
5. 固定测试影响矩阵、候选身份格式、发布回滚目标、canary/告警和自动暂停条件；至少完成一次不写生产的演练。
6. 由 Owner 记录发布自动授权策略及失效时间。策略记录完成前，可以本地开发和验证，但不能启用自动生产写入。
7. 只读审查通过后，协调者确认后续 `feat/*` 起点；旧工作树和旧分支是否保留由协调者裁定，不自动删除。

整理过程中不删除未提交工作树、不强制重写共享历史、不移动正式标签。每一步失败都保留现场并回到上一可恢复检查点。
