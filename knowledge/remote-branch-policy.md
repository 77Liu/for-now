# 远程分支与提交历史规则

生效日期：2026-10-11。本文是远程分支命名、保护、生命周期和提交历史调整的唯一正文。规则从下一次 `push` 起适用于本项目；既有远程分支、标签、发布记录和提交历史不因本文落地而自动修改。

## 长期分支

| 分支 | 用途 | 允许来源与写入 |
| --- | --- | --- |
| `main` | 已发布稳定代码和生产热修回流 | 仅接收已验收的 `release/*` 或生产 `hotfix/*`；禁止普通功能直接写入 |
| `develop` | 下一阶段唯一普通开发和集成基线 | 新的 `feat/*`、`fix/*`、`docs/*`、`chore/*` 从此分支创建；由协调者串行接入 |

当前不建立独立平台长期分支。远端已有的 `platform/*` 属于历史引用，在单独审查和授权前不作为新任务基线、不向其继续开发，也不由本规则自动删除或迁移。

## 短期分支

| 分支 | 起点 | 用途与归宿 |
| --- | --- | --- |
| `feat/<主题>` | `develop` | 独立功能；验收后回 `develop`，关闭并删除远端短期引用 |
| `fix/<主题>` | `develop` | 非生产缺陷修复；验收后回 `develop`，关闭并删除远端短期引用 |
| `docs/<主题>` | `develop` | 短期规则或文档修改；合入后关闭，不建立长期 docs 线 |
| `chore/<主题>` | `develop` | 工具、构建或维护性改动；验收后回 `develop` |
| `release/vX.Y.Z` | `develop` | 发布候选冻结线；只允许候选修正、发布文档和发布验证，完成后回 `main` 与 `develop` |
| `preview/vX.Y.Z` | 对应候选发布线 | 隔离预览和观察；不得写生产，观察结束后关闭引用，标签、证据和发布记录保留 |
| `hotfix/<主题>` | 当前生产 `main` | 生产紧急修复；发布后必须回流 `main` 和 `develop`，随后关闭 |

`archive/*` 仅用于本地审计和恢复。它不是远程开发入口，也不用于创建新分支、继续开发或绕过当前 `develop`。

## 保护与协作要求

1. `main` 和 `develop` 应设置远程保护：禁止直接推送、强制推送、删除和历史重写；合入使用可审查的 Pull Request 或等价审查记录。
2. 保护规则至少要求：提交状态检查通过、审查责任人明确、分支已更新到目标基线；发布线还必须有发布验证和回滚条件证据。
3. 每个任务卡和合并记录写明起始分支、起始 SHA、分支角色、规则基线、写集、验证范围和未完成项。分支名、ahead/behind 或可自动合并不能代替内容验收。
4. 共享写集只能有一个当前负责人。发现冲突时暂停受影响写任务，由协调者决定串行接入、选择性搬运或归档；不得互相覆盖或把未集成分支作为新基线。
5. 普通功能不得从 `main`、`release/*`、`preview/*`、`hotfix/*` 或历史远程分支派生。生产热修是唯一从 `main` 派生的普通例外。
6. 删除短期远程分支前，必须确认没有唯一未合入提交、没有未交接工作树、相关标签/发布证据已保留，且没有其他活跃负责人依赖。删除分支引用不会删除标签、发布记录或归档证据。

## 远程提交历史

- 允许的整理方式是新增提交、回滚提交、建立清晰的分支引用、为已发布提交补充不可移动的标签，以及在未共享分支上经审查的 rebase/squash。
- 默认不改写 `origin/main`、已共享 `develop`、生产标签或已发布提交；不使用强制推送、`filter-repo` 或 BFG 处理普通分支整理。
- 远端旧分支可以在完成交接、审查和归档后按授权删除；本规则不授权本次自动删除既有远程引用。
- 需要重建干净发布线时，从已确认生产标签或当前 `develop` 创建新分支，并保留旧提交和证据作为审计来源；不得把新分支冒称为旧历史的原地改写。
- 任何远程历史调整都必须先形成影响说明、恢复点和执行窗口，由主控确认后单独执行；未获确认时保持只读。

## 本次落地边界

本次只写入本地规则并提交到 `develop`，不创建远程 `develop`，不修改已有远程分支、标签、发布记录或提交历史。后续首次推送新分支时，按本文命名和保护要求执行；若远端保护尚未配置，主控不得以手工操作绕过，而应先补齐保护配置或登记阻塞。
