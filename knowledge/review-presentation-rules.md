# 评审输出与导读规范

生效：2026-10-18 本次 Owner 明确要求之后。本文是本项目评审表、摘要导读顺序与名词解释的唯一规则正文，由 [PROJECT_RULES](../PROJECT_RULES.md#读取与规则归属) 导航。技能、模板和检查脚本只负责执行，不另立相反口径。

## 生效范围

- 技术方案、跨需求评审、代码评审和规则评审按下述裁剪边界选择表达，四列重点评审表及完整稿导读作为适用时的标准格式。裁剪不改变业务要求、必要证据和未解决项，也不代表完整布局检查器已支持裁剪。
- 采用完整格式的新建评审稿使用本文的摘要导读顺序；生效前已有且不符合的方案、报告、索引和评审记录不回溯改排，不因普通事实补充或开发回填要求整篇迁移。后续明确重写成新评审稿时使用新格式。
- 本规则只改变表达与入口，不新增审批关卡；Owner 已明确的决定不重复询问，不把建议冒充已拍板。

## 裁剪边界

按语义风险判断，不按文件数、代码行数或“简单任务”标签判断。普通小修可用一份事实、改动结果、验证及限制说明；涉及共享协议、持久化、费用、权限、跨进程生命周期或重大取舍时，展开实际受影响的链路、状态、失败和验证。完整设计也无需填写无关角色或复制同义表。

可以合并或省略：聊天与文档重复的决策表、无新信息的背景复述、不适用章节、正文已解释清楚的术语表、无助理解的图和没有合理备选的比较栏。已有定义可引用真实位置，写清本次变化及兼容边界；已有有效证据可引用，不重复抄录。影响判断的不适用项简述依据，显然无关项无需逐一造空章节；未知不能写成不适用。

不能裁掉影响本次判断的用户目标与范围、实际改变的业务行为、账户/实体归属、状态及失败恢复、兼容承诺、关键取舍、实际验证与未覆盖项、未解决问题和授权边界。必要内容可合并到正文，不必一项一个标题。重大取舍保留可比较的选项、推荐和代价；没有合理替代方案时写清约束即可。

决策正文只维护一处。聊天可给关键结论及定位链接，不必再复制文档中的表；有多个待决事项且表格更便于比较时使用标准重点评审表，每行仍须自包含。无新增待决项可直接说明已落实结果及范围，不为保留表头编造待决项。保留章节沿用原编号，避免破坏引用；裁剪后核对链接与语义，不能仅凭旧布局工具报错否定合规裁剪，也不能跳过实际内容检查。

## Agent 交付中的重点评审表

采用标准重点评审表时，在用户可见的最终交付中展示，不能只提供文档入口或在进度消息里展示。可在表前附总入口；总入口不能代替逐项链接。使用 Markdown 表格，固定四列：

|方案|逻辑链|评审关注点|Owner拍板|
|---|---|---|---|
|简短的业务、需求或领域名称|业务/需求 -> 场景 -> 处理环节 -> 当前决策层级<br>当前问题：用简单易懂的话交代具体背景、发生了什么，以及当前要决定的问题。|这一层尚不明确的具体问题，并链接到相关 Markdown 或代码行|建议结论及具体做法，并链接到对应 Markdown 或代码行|

- 一行对应一个可以独立拍板的事项。同一方案有多项决定时拆行，不用一行包住不同抽象层的问题。
- “方案”让 Owner 快速知道在谈什么，优先短中文名称，不堆需求编号、方法名或术语。
- “逻辑链”使用 `xx -> yy -> zz` 逐层下探；最后一层恰好是当前决策层级，不仅列函数调用顺序，也不跳过必要的业务上下文。
- 在“逻辑链”原有内容下方、同一单元格内，追加“当前问题”的具体描述。用简单易懂的完整句子说明：涉及什么业务和对象、用户在什么场景做什么、正常应当怎样、当前实际怎样或哪里尚未确定，以及为什么需要作出本行决定。涉及对象之间的关系时，先讲清谁属于谁、这次操作影响哪一部分；技术名词在本行解释成读者能理解的话，不能用函数名、编号或抽象标签代替背景。方案取舍按实际情况说明现状、约束和待定点，不把待选方案虚构成已发生的故障。
- 背景与问题描述以说清楚为先，不设字数上限，不为缩短表格删去理解和决策必需的信息。验收时只读本行，不借助之前的对话、其他表格行或链接正文：应能理解“评审关注点”具体在说什么、为什么重要，以及“Owner拍板”建议解决什么、涉及什么取舍，并有足够信息作出决定；否则补写背景后再交付。链接用于核对证据和深入阅读，不能代替本行必须交代的背景。
- “评审关注点”写清当前层级的歧义、缺口或取舍；链接直接落到问题、证据或约束所在行，不能只给整个文件。
- “Owner拍板”先写推荐怎么定，再链接到建议的具体设计或代码行。尚未实现时链接方案行，不虚构源码；已确认时标明“已确认”并链接真实决定，不重新列为待决。
- 没有新待决项时可省表；保留表时明确“无新增待决项 / 已按本轮要求落实”，链接到结论及其范围，不编造问题凑表。

## 评审稿的固定导读顺序

采用完整稿格式时，标题和文档信息之后，适用的导读章节按以下相对顺序使用同级二级标题；可裁剪项按上节处理，只保留一份正文：

1. `## 评审摘要`：先给简短摘要，再紧接“评审摘要决策表”。
2. `## 名词解释`：紧跟决策表，不能插入需求追踪、资料表或评审记录。
3. `## 评审记录`：保留真实意见、日期、状态和处理结果。
4. `## 需求追踪`：连接需求、设计、落点、验收和观测。
5. `## 资料来源与前提`：放在这组评审导读的最后；技术方案其后继续原有 1—5 章，不把来源移到技术正文末尾。

摘要从具体业务事项和推荐结果写起，说明关键取舍、影响面及待定边界，使 Owner 不读技术正文也能判断讨论的层级。摘要中影响决定的前提要简述，详细证据放在后面的来源表。

评审摘要决策表固定五列，不增加独立“编号”列；需要稳定编号时写入“决策事项”单元格：

|决策事项|建议结论及具体方案|其他方案|排除的选择与代价|影响面|
|---|---|---|---|---|
|D1：具体待定事项|明确推荐、行为、边界和依据|仍可考虑的可行备选；没有则说明原因|已经排除的做法、排除原因及其代价；与备选区分|业务、需求、模块、接口、数据、验证或负责角色|

完整稿按裁剪边界选择适用的导读章节和表格；保留章节按上述相对顺序组织。无新增待决项可省决策表，既有决定仍需在正文明确状态和证据。同时使用两种表时事项与状态须对应，不建立两份独立台账。历史稿补充可直接链接既有决定与证据，不要求补表或改排；仅聊天交付的代码或规则审查不因此另建技术方案文档。

## 名词解释的选择与写法

需要独立名词表时沿用 `|名词|解释|语境|` 三列表，位置按上述导读顺序；少量术语可在首次出现时解释。优先检查评审摘要与决策表，再补理解具体方案所必需的术语：

- 覆盖缩写、方法名、业务术语，以及虽通用但依赖本场景才能理解的英文名词、动词和中文描述；不能只解释架构缩写。
- 摘要或决策表出现 `audit`、`dispatch`、`invocation contract`、`终态事件`、`provider`、`upsert` 时，都要解释本场景的含义；没有出现且方案也未使用的词不机械补入。
- 解释使用普通中文，说明“指什么、由谁在什么环节使用、会造成什么结果”。方法名同时说明输入、动作和结果，不只翻译字面，也不用另一个未解释术语代替。
- “语境”逐字引用本文实际原句，优先来自摘要或决策表。不得编造例句、只填章节号或只重复词名；确需引用技术正文时，解释仍应使只读摘要的人能理解。
- 已收到用户点名不理解的词必须覆盖，统一错别字和别名；事实、建议、已确认决定与未实现状态要分清。

## 行级链接与校验

- “评审关注点”和“Owner拍板”两列都必须包含有意义的链接文本及真实行号。单行使用 `#L起始行`，范围使用 `#L起始行-L结束行`；范围只覆盖相关问题或结论，不用整篇行号范围规避定位。
- 保存、移动段落或重排后重新读取目标行，确认链接仍落到相应内容。不能只验证文件存在，也不能用章节锚点代替行号。
- 仓库文档中的链接继续采用 [PROJECT_RULES](../PROJECT_RULES.md) 规定的相对路径并加行号片段；Agent 对话链接按当前平台的文件交付规范生成。外部代码链接固定到实际评审 revision，无法核实时明确缺口，不虚构行号。
- 模板和结构校验入口为[技术方案技能](../.trae/skills/create-technical-proposal/SKILL.md)。新稿使用当前布局检查；旧稿只做原有格式校验，不以本次规则追罚历史。语境是否为完整原句、术语是否解释清楚、逻辑链层级及两列链接的语义仍须人工核对。
