## 何时增加基础设施

先用当前业务、数据规模和生产指标定位瓶颈，优化查询范围、索引、传输、事务与重复工作，再评估新增组件。每项基础设施独立说明收益、复杂度、成本、恢复方式和适用证据，不因一个瓶颈整套升级。

| 选项 | 应先取得的依据 |
| --- | --- |
| 扩大连接池 / 池代理 | 真实连接利用率、锁等待、查询时间及服务端资源；先区分慢查询与缺连接 |
| 多 API 实例 / 独立 worker | 单实例瓶颈，以及跨进程身份、额度、领取、租约、幂等和停止恢复契约 |
| 只读副本 | 读 CPU 或读延迟已成为瓶颈，业务可接受复制延迟 |
| 消息队列 / Redis | 任务吞吐、等待或轮询成本超过现有方案；不是为“未来高并发”预建 |
| 向量索引 / 重排序 | 召回质量已有业务收益，规模与延迟确实需要该能力 |
| 按账户分片 | 索引、纵向扩容和归档仍不足，且恢复/迁移代价已有论证；账户数量本身不是理由 |

任务结果只能写回绑定的账户、目标和输入版本。供应商已成功而本地终态不确定时，不能盲目重放付费或其他外部副作用；先依据供应商幂等/查询能力确定恢复方案。

多实例必须先处理共享限流/额度、任务领取和调度唯一性，不能把单实例内存护栏复制后当全局限制。服务端 AI 场景不能同时声称服务端无法访问原文的纯端到端加密。
