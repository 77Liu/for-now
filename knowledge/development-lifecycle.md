# 需求到复盘生命周期标准

标准编号：`STD-DEV-002`；版本：`2.0`；生效日期：`2026-10-11`；状态：生效。

本文是需求选择、开发、候选、发布、观察、复盘和失败回流的唯一生命周期正文。具体步骤由 `SOP/` 承载；测试选择由 [`test-impact-matrix.md`](test-impact-matrix.md) 承载；自动发布权限由 [`release-authorization-policy.md`](release-authorization-policy.md) 承载；当前事实只写入[唯一协调控制面](coordination-control-plane.md)。

## 1. 目标流程

```text
需求池收集
→ 去重与证据核验
→ 价值/风险/成本选择
→ 迭代契约冻结
→ feat 实现
→ develop 集成与候选固定
→ develop 有状态全局门通过后冻结 release / preview
→ 策略授权与自动发布
→ canary 观察与回滚判断
→ 正式节点回流 develop 后关闭
→ 用户反馈、事故和工程问题回流需求池
```

生产异常走旁路：

```text
异常发现 → 判断影响 → 停止放量或回滚
→ 选择 hotfix / 原候选修复路径
→ 最小验证 → 重新候选 → 观察 → 复盘回流
```

## 2. 外部状态

| 状态 | 进入条件 | 退出条件 | 失败返回 |
| --- | --- | --- | --- |
| `INBOX` | 有原始问题、来源和用户/系统影响 | 事实去重完成，可比较价值和风险 | 保留原始记录或标记重复/取消 |
| `SELECTED` | 进入本轮候选，明确目标和非目标 | 形成用户行为、验收、负责人、版本和风险等级 | 回 `INBOX` 重新选择 |
| `READY` | 共享契约、依赖、失败恢复、影响测试和分支基线清楚 | 可在授权范围内开始实现 | 回 `SELECTED` 补范围，或标记 `BLOCKED` |
| `BUILDING` | 从当前 `develop` 创建 `feat/*` 并开始实现 | 切片专项、审查和交接证据成立 | 代码/测试失败回本状态；契约变化回 `READY` |
| `CANDIDATE` | 接入 develop，固定提交/tree/制品 | 影响矩阵和集成审查完成 | 回 `BUILDING` 修复，或回 `READY` 改范围 |
| `RELEASING` | release/preview 对象、授权策略和回滚目标齐全 | 发布、部署回执可核对 | 授权问题回 `READY`；部署问题留在本状态恢复 |
| `OBSERVING` | 运行对象与候选一致，canary 和停止条件有效 | 观察退出条件成立或触发回滚 | 触发回滚回 `RELEASING`，产品不符回 `SELECTED` |
| `CLOSED` | 正式身份、运行结果、产品验收和回流事项已记录 | 只允许追加复盘或新需求 | 新问题进入 `INBOX`，不重写关闭事实 |

`PARTIAL`、`BLOCKED`、`FAIL`、`NOT_RUN` 是结论，不是绕过状态。它们必须附责任人、影响和解除条件；不能改写成通过。

## 3. 需求选择契约

每个进入 `SELECTED` 的需求至少包含：

```text
需求来源与原文引用
用户/系统问题和影响
重复、已修、已发布和取消关联
本轮目标与明确非目标
可验证用户行为和失败/恢复结果
预估风险、成本、依赖和最小版本范围
候选负责人、审查人和协调者
```

选择优先级由用户价值、影响紧急度、证据可信度、风险、成本和依赖共同决定。需求管理维护原始事实和未冻结建议；只有协调者将其写入控制面后，才成为当前迭代范围。

## 4. 开发与集成契约

- 实现及规则/文档修改的起点、原 feat 返修和各引用职责，仅按[Git 规则](remote-branch-policy.md)执行；develop 负责集成。
- `READY` 前必须写清共享契约、账户隔离、持久化、权限、外部调用、失败恢复和测试影响域。
- `BUILDING` 先核对真实调用链及必要复现，再做最小纵向改动；编辑后自查，主控独立接入审查，验证确认结论，不用运行试错代替契约核对。
- 共享契约和共享写集串行接入 develop；候选只接受已核对的切片，不接受未审查半成品。
- `CANDIDATE` 绑定完整对象身份；候选变化即生成新候选，不移动已发布标签。

## 5. 发布与观察

发布统一执行 [`SOP/release-and-observation.md`](../SOP/release-and-observation.md) 的：

```text
verify → freeze → authorize → publish → deploy → observe → close
```

是否能自动执行由 [`release-authorization-policy.md`](release-authorization-policy.md) 判定。质量门、风险等级、候选身份、回滚目标和 canary 条件缺一项，自动链路停止。

## 6. 失败回流

| 事实 | 回流节点 | 是否保留原候选 |
| --- | --- | --- |
| 需求不成立、重复或价值改变 | `INBOX / SELECTED` | 保留历史，不继续开发 |
| 范围、验收、契约不清 | `SELECTED / READY` | 不把半成品当候选 |
| 代码或专项断言失败 | `BUILDING` | 保留失败证据，修复后新候选 |
| 公共契约或集成冲突 | `READY / BUILDING` | 旧候选失效 |
| 授权不覆盖当前动作 | `READY` | 候选可保留，外部动作不执行 |
| 预览/部署环境失败 | `RELEASING` | 保留候选，恢复后续做 |
| canary 触发回滚 | `RELEASING` | 保留运行和回滚证据 |
| 用户验收不符 | `SELECTED` | 不把技术通过当产品完成 |
| 外部权限/资源缺失 | `BLOCKED` | 保留已完成证据 |

## 7. 兼容旧阶段名

旧 G0-G7 只作为历史报告和迁移期别名，不再创建第二套状态：

| 旧阶段 | 新状态或边界 |
| --- | --- |
| G0 | INBOX → SELECTED |
| G1 | SELECTED → READY |
| G2 | READY → BUILDING |
| G3 | BUILDING 完成 |
| G4 | CANDIDATE |
| G5 | RELEASING 前的授权边界 |
| G6 | OBSERVING 关闭 |
| G7 | CLOSED 与复盘回流 |

## 8. 复盘与回流

关闭时分别核对：技术运行、用户验收、未覆盖项、生产观察、成本/资源、事故和规则改进。复盘行动只能回到三类唯一位置：

- 用户问题、反馈或新目标：`INBOX`；
- 当前规则或测试缺陷：对应规则正文或测试矩阵；
- 生产故障：事故记录、hotfix 路径和受影响候选。

复盘报告保留当时事实，不能成为第二个“当前状态”文件。控制面只保存索引、决策和下一动作。

## 9. 启动与维护

改变状态模型、放权策略或分支职责时，先完成一次启动前整理：核对 Git 起点、工作树、未提交差分、远程保护、控制面初始化、测试矩阵、发布/回滚演练和授权策略；完成后再允许新一轮普通开发。历史报告不因新模型改写。

项目记录的提交/tree 摘要按[控制面协议](coordination-control-plane.md)保存完整对象身份，简称仅用于展示。
