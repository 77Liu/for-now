# 上线前确认与发布流程

本文档定义从“功能开发完成”到“生产发布关闭”的阶段顺序、人工闸门、证据要求和回退规则。它负责流程编排，不复制详细检查项：

- 工程规则：`knowledge/engineering-rules.md`
- 逐项上线清单：`knowledge/development-release-checklist.md`
- 更新说明内容规范：`knowledge/release-notes-rules.md`
- 系统测试矩阵：`knowledge/system-testing.md`
- 生产部署：`deploy/README.md`
- 容量、告警、备份与恢复：`knowledge/operations-capacity.md`

## 核心原则

1. **发布对象必须固定**：每轮检查都要写明生产基线、候选分支和候选提交；不能检查 A、发布 B。
2. **证据先于结论**：测试通过、配置完成、备份可恢复和部署成功都必须有实际输出或观测，不使用“应该没问题”。
3. **两轮检查职责不同**：第一轮允许补实现、补测试和优化；第二轮在冻结候选上做独立、对抗性的发布审计。
4. **人工确认分两次**：配置与风险确认发生在第二轮前；最终生产写入授权发生在 Git 发布和服务器上线前。
5. **阻断项不能带病通过**：阻断项只能“通过”或“NO-GO”，不能用“上线后再看”替代。
6. **任何变更都会使部分证据失效**：检查后修改代码、依赖、部署脚本、数据迁移或生产配置，必须按影响范围重跑。
7. **部署完成不等于发布完成**：只有生产冒烟、观察窗口和恢复能力都正常，发布才可关闭。

## 发布状态

一次发布按以下状态推进：

```text
草稿
→ 范围已冻结
→ 第一轮通过
→ 人工配置已完成
→ 人工预确认
→ 第二轮通过
→ 文档已同步
→ 最终 GO
→ Git 已发布
→ 生产已部署
→ 观察完成
```

任一阶段发现阻断问题即进入 `NO-GO`。修复后返回问题所属阶段，不允许跳过中间闸门。

## 0. 发布立项与范围冻结

在第一轮检查前建立本次发布记录，建议路径：

```text
reports/pre-launch-YYYY-MM-DD-<short-name>.md
```

记录以下内容：

- 发布名称、目标、验收标准和明确不做的范围。
- 当前生产版本、候选分支、候选提交或工作区基线。
- 影响的数据结构、API、页面、认证、附件、AI、第三方服务和部署资产。
- 风险等级：低 / 中 / 高；判断依据和回滚负责人。
- 本次适用的测试、人工验收、外部服务和数据迁移。
- 已知未提交改动及归属；不得覆盖、回退或夹带其他任务改动。

范围冻结后新增需求默认进入下一发布。只有阻断当前目标的必要修复可以进入本次，并须更新发布范围和验证矩阵。

## 1. 第一轮检查：实现完整性

第一轮目标是发现并修复问题，允许修改代码、测试和文档。每次修复后先跑相关专项测试；全部收口后再执行完整系统测试。

### 1.1 阅读完整项目规则

至少重新读取：

- `PROJECT_RULES.md`
- `README.md`
- `one-mistake-one-rule.md`
- `knowledge/engineering-rules.md`
- `knowledge/development-release-checklist.md`
- 与本次功能直接相关的架构、指标、Prompt、隐私、运维和产品文档

检查结果写入发布记录：实际读取的文件、与本次发布直接相关的规则，以及发现的规则冲突或过时内容。不得只写“已阅读”。

### 1.2 完善测试、执行测试与优化

先把验收标准映射为测试矩阵：

| 验收行为 | 自动化测试 | 人工测试 | 生产冒烟 | 关键失败路径 |
| --- | --- | --- | --- | --- |
| 每项需求填写一行 | 文件/用例 | 操作步骤 | 上线后步骤 | 失败、重试、回滚 |

要求：

- 新行为至少有成功路径和一个最关键失败路径。
- Bug 修复应有修复前可失败、修复后可通过的断言。
- 认证、账户隔离、数据迁移、异步任务、附件、AI、共享组件和部署变更必须进入对应专项回归。
- 高频读写、队列、限流或全量 JSON 改动必须核对并按需更新压测场景；是否执行 `npm run test:load` 以 `knowledge/system-testing.md` 为准，仅用于容量评估、扩容决策或用户明确要求，不得为通过而直接放宽阈值。
- 页面主流程或移动样式变更必须覆盖桌面、窄屏、移动模拟和必要截图；真机能力单列人工测试。
- 默认完整入口为：

```bash
npm run test:system
```

- `test:oss`、`test:aliyun`、生产账户、真机和真实供应商测试不属于默认本地测试；只有凭据、费用和数据范围获得明确授权后才能执行。
- 每次测试记录命令、提交或工作区版本、时间、退出码、摘要和产物位置。

优化只针对已证实问题：正确性、数据完整性、安全、性能回退、可用性或维护成本。不得借发布检查进行无关重构。

### 1.3 遗漏检查与代码质量检查

在测试之外，再按 `knowledge/development-release-checklist.md` 完成逐项审查，重点检查：

- 需求是否全部落到代码、测试、错误提示、日志和文档。
- 旧数据、空数据、损坏数据、并发、重复提交、超时、断流和进程重启。
- 未登录、越权、跨账户、CSRF、XSS、SSRF、路径穿越和文件上传边界。
- AI 的输入边界、结果校验、用量费用、失败终态、幂等和审计。
- 数据删除、恢复、附件引用、清理重试、备份和代码回滚兼容性。
- 性能、磁盘、内存、日志增长、队列积压和第三方限额。
- 部署候选构建、依赖锁定、环境变量、systemd、Nginx、健康检查和自动回滚。
- `git diff` 中是否夹带格式化、生成物、密钥、测试数据或其他任务内容。

问题按严重度、文件位置、影响、复现方式和处理结论写入发布记录。阻断问题全部关闭后，第一轮才可标记通过。

## 2. 人工介入与确认

第一轮通过后，Agent 必须先输出“人工介入清单”，不能直接进入发布。人工事项分为两类。

### 2.1 必须由人工决定

- 发布范围、上线时间、维护窗口和可接受中断。
- 隐私、运营主体、用户告知、数据保留、导出和删除承诺。
- 成本预算、供应商费用、邀请人数和放量范围。
- 未关闭的非阻断风险是否接受，以及负责人和截止时间。
- 桌面/移动端的关键视觉、文案、信息密度和真实使用体验。
- 是否批准最终 commit、push 和生产部署。

### 2.2 必须人工配置或授权

下表按本次发布适用范围填写；不适用必须写原因。

| 类别 | 当前项目需确认内容 | 完成证据 |
| --- | --- | --- |
| 生产身份 | 目标 Gitee 仓库、`main`、服务器、部署账户和 SSH 权限 | 只读远端核对 |
| 应用环境 | `/etc/for-now.env` 必需键已配置，权限 `0600` | 仅记录“已配置/未配置”，不记录值 |
| 认证 | 邀请码摘要、Cookie HTTPS、安全会话和邀请范围 | 配置状态与登录冒烟 |
| DeepSeek | 账户密钥、模型可用性、预算和额度 | 脱敏测试结果 |
| 阿里云 RAM | imageseg、VIAPI、OSS 备份与附件最小权限 | 真实冒烟结果 |
| OSS | 私有桶、阻止公共访问、HTTPS、加密、生命周期和容量 | 控制台截图或只读查询 |
| 飞书告警 | webhook、可选签名、接收人和恢复通知 | 真实测试消息 |
| 网络与证书 | 安全组、80/443、Nginx、证书有效期和续期 | `nginx -t`、证书状态 |
| 备份恢复 | 最新成功备份、校验和、保留期和隔离恢复 | 备份及恢复演练报告 |
| 隐私运营 | 运营主体、联系人、同意记录、导出/删除入口 | 人工签字或确认记录 |
| 真实设备 | iOS Safari、安装态 PWA、Android Chrome、键盘/安全区/触觉 | 设备、版本、截图和结果 |

密钥、密码、邀请码、webhook、Cookie、令牌和私钥不得写入确认文档、Git、日志或聊天。文档只保存配置状态、责任人、验证时间和脱敏证据。

### 2.3 人工预确认

进入第二轮前，人工明确确认：

```text
候选范围、人工配置和风险清单已核对；
阻断配置已完成；
同意以当前候选进入第二轮发布审计。
```

这不是最终部署授权。第二轮仍可能给出 `NO-GO`。

## 3. 第二轮检查：冻结候选审计

第二轮必须基于冻结的候选提交或可复现工作区执行，不沿用第一轮“已经看过”的结论。

优先由不同审阅者或新上下文执行；仍由同一审阅者执行时，也必须从规则、生产基线和冻结 diff 重新建立判断，不能只复查第一轮问题列表。

### 3.1 再次阅读完整项目规则

重新读取第一轮的规则入口，并检查：

- 第一轮修复是否违反范围克制、单一事实来源或已有架构。
- 人工配置是否改变了安全、隐私、成本、部署或测试假设。
- 候选状态是否仍与 README、TODO、验收报告和生产事实一致。

### 3.2 再次完善并执行测试

- 从候选提交重新安装锁定依赖或使用新的候选 release 目录，避免活动目录和旧依赖污染。
- 重新运行 `npm run test:system`，不能只引用第一轮输出。
- 按风险重跑已授权的真实外部服务、恢复、真机和生产只读检查。
- 核对测试结束后无残留端口、进程、临时目录、浏览器 profile、测试对象和费用异常。
- 对第一轮新增或修改的测试本身做质量检查，防止弱化断言、吞错、只延长超时或把失败路径改成永远通过。

### 3.3 对抗性遗漏与质量复查

第二轮重点从“如何失败”出发：

- 候选构建能否从干净目录完成，发布包是否缺文件或多文件。
- 缺环境变量、权限不足、外部服务超时、磁盘写失败和服务重启时是否安全失败。
- 老数据、当前生产快照、多账户、base path 和移动端是否仍兼容。
- 失败回滚后代码、配置、版本、Nginx、systemd 和数据是否处于一致状态。
- 日志、告警和审计能否定位问题，同时不泄露正文或凭据。
- 生产提交、远端提交和已检查提交是否完全一致。

第二轮发现需修改代码、依赖、迁移或部署脚本时，第二轮立即失效：返回第一轮完成修复和测试，再重新取得人工预确认。只有纯说明性文档修正且不改变范围、行为、配置或风险时，才可只重跑文档一致性检查。

## 4. 文档与长期上下文

第二轮通过后，按单一事实来源更新文档：

| 内容 | 主要维护位置 |
| --- | --- |
| 当前生产/候选状态与路由 | `README.md` |
| P00–P3 当前状态与验收 | `README-TODO.md` |
| 工程规则 | `knowledge/engineering-rules.md` |
| 详细上线清单 | `knowledge/development-release-checklist.md` |
| 测试矩阵与命令 | `knowledge/system-testing.md` |
| 架构和数据契约 | `knowledge/architecture.md` |
| 指标与费用口径 | `knowledge/metrics.md` |
| 日志与 AI 审计 | `knowledge/observability.md` |
| 容量、告警、备份和恢复 | `knowledge/operations-capacity.md` |
| 隐私告知与人工运营项 | `knowledge/privacy-notice.md` |
| 当日重要变化 | `knowledge/iteration-history.md` |
| 本次检查证据与结论 | `reports/pre-launch-*.md` |

要求：

- README 只保留当前状态、关键约束和路由，不复制整份流程或检查清单。
- 新事实优先修正旧状态，不能保留冲突的“当前结论”。
- “工作区已验证”“已 push”“生产已部署”“观察完成”必须严格区分。
- 执行链接、路径、命令和 Markdown 格式检查；清理被替代的临时报告或移入 `recyclebin/`。

文档同步后若发现行为或范围描述不准确，应回到相应检查阶段；不能只修改文案掩盖代码事实。

## 5. Git 发布与服务器上线

### 5.1 最终 GO

执行任何 commit、push 或生产写操作前，向人工提交最终摘要：

- 候选提交、生产基线、变更范围和风险等级。
- 两轮检查结果、完整测试结果和未执行项目。
- 人工配置完成情况和脱敏证据。
- 最新备份、恢复演练、回滚版本和回滚触发条件。
- 已接受的非阻断风险、负责人和截止时间。

人工必须明确回复同意本次 commit / push / deploy 的具体范围。历史授权、模糊的“继续”或测试通过不能替代本次最终授权。

### 5.2 Git 发布

1. 检查 `git status`、`git diff`、`git diff --check` 和暂存内容。
2. 确认当前分支符合发布策略；生产只从已确认的 Gitee `main` 提交部署。
3. 提交保持单一目的，不夹带探索分支、样例、密钥、本地数据或其他任务改动。
4. Git 发布版本时必须提供中文更新说明；Conventional Commit 英文类型前缀可以保留，但不能只写一句英文标题。更新分类、逐类结构、用户价值表达和检查清单统一以 `knowledge/release-notes-rules.md` 为准。
5. 中文更新说明至少包含：
   - 当前标签、同一产品线的上一发行版标签和可复核的 Git 对比范围；
   - 相比上一发行版的“新功能”“Bug 修复”“架构调整”三个固定核对栏目，以及按更新说明规范编写的完整分类内容；
   - 本次发布目标和最重要的用户可见变化；
   - 关键技术、数据结构、API、AI、附件或运维变化；
   - 兼容性、迁移、环境变量及需人工完成的配置；
   - 实际执行的测试、生产冒烟和结果；
   - 已知限制、未完成项、风险和回滚方式。
6. 三个固定核对栏目必须细粒度列出模块、用户行为或系统边界的实际变化；某栏目确无变化时明确写“无”，不得省略。完整条目不得使用“若干优化”“问题修复”等无法核对的笼统表述。
7. 每个推送到共享远端的 Git 标签都必须在同一发布流程中创建对应的 Gitee Release，包括主应用、中台、热修复和探索标签；Release 的标签、目标提交和产品线必须与 Git 记录一致。标签已推送但 Release 未创建或不可访问时，发布状态保持 `NO-GO`。
8. “上一发行版”按同一产品线选择最近一个已发布 Release；首个发行版写“无（首个发行版）”，并将当前完整能力作为基线。禁止用其他产品线的发行版做虚假比较。
9. 更新说明写入本次发布记录，并原样或等价同步为 Gitee Release 正文；发布记录是内容单一事实来源，不能在多个文件分别维护互相漂移的完整版本说明。
10. 创建 Release 后核对发行版 URL、标签、目标完整哈希、上一发行版和三个固定栏目；把 URL 与核对结果写回发布记录。
11. push 后核对本地提交、远端分支和准备部署的完整哈希一致。
12. 把最终提交哈希写入发布记录；后续不得用浮动分支名代替。

### 5.3 生产部署

1. 再次只读核对生产版本、服务、磁盘、备份、告警和当前错误。
2. 对数据/迁移类发布先生成并验证新备份；高风险变更先完成隔离恢复演练。
3. 核对目标环境配置，但不输出密钥。
4. 使用 `deploy/README.md` 规定的不可变 release 和 `for-now-deploy` 部署。
5. 健康检查或配置安装失败时停止继续操作，检查自动回滚结果；不得在活动 release 中临时修代码。

### 5.4 部署后冒烟

至少核对：

- `/readyz`、公网 HTTPS、运行版本和静态资源版本。
- 注册/登录、账户隔离、现有账户和关键数据数量。
- 本次修改的主流程、关键失败路径和移动端入口。
- DeepSeek、阿里云分割、OSS 附件和其他适用外部依赖。
- 系统日志、操作日志、AI 审计、用量费用和追踪 ID。
- 飞书告警、备份时间戳、恢复脚本和回滚目标。

真实写入应使用专用测试账户或可清理的最小数据，不修改用户正式记录。

## 6. 上线后观察与关闭

- 默认至少观察 30 分钟；认证、迁移、后台任务、支付或大范围数据变更应延长到约定窗口。
- 观察错误率、P95、进程重启、内存、磁盘、任务积压、AI 失败/重试、费用、附件和告警。
- 任一持久化失败、跨账户读取、不可解释数据变化、持续 5xx、费用失控或回滚失效立即停止发布并回滚。
- 观察结束后在发布记录写明：
  - 最终运行版本和时间；
  - 关键指标与告警；
  - 继续运行 / 修复后继续观察 / 已回滚；
  - 遗留项、责任人和截止时间。

只有观察结论为“继续运行”，本次发布才标记完成。

## 证据失效规则

| 第二轮后发生的变化 | 必须重做 |
| --- | --- |
| 仅错别字、无行为文档修正 | 文档一致性检查 |
| 测试代码或测试桩变化 | 受影响测试 + `test:system` |
| 业务代码、依赖或前端资源变化 | 第一轮相关检查 + 完整第二轮 |
| 认证、数据、附件、AI、迁移或部署脚本变化 | 第一轮、人工预确认、完整第二轮 |
| 生产环境变量、IAM、Nginx、systemd、证书变化 | 配置验证、第二轮相关项、部署前核对 |
| 候选提交哈希变化 | Git 核对、完整第二轮和最终 GO |
