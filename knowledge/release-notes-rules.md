# 更新说明写作规范

本文档是本项目版本更新说明的内容结构、分类口径和写作要求的单一事实来源。它适用于版本发布记录、Gitee Release、版本周报、发布会材料和项目复盘。

发布阶段、人工闸门和证据要求以 `knowledge/pre-launch-confirmation.md` 为准；逐项检查以 `knowledge/development-release-checklist.md` 为准。

## 1. 目标

更新说明用于记录版本发布中的核心变化，要求同时满足：

- **可读**：非研发人员可快速理解“改了什么、为什么改、带来什么价值”。
- **可追溯**：每项更新有明确问题、原因、方案与结果。
- **可汇报**：可直接用于版本周报、发布会和项目复盘。
- **可复用**：不同版本、不同业务统一结构与表述口径。

禁止仅记录研发动作，如“调整接口”“修改样式”“修复若干 Bug”“优化体验”等。所有更新必须转化为**用户问题 / 产品变化 / 用户价值 / 结果**。

## 2. 与发布流程的关系

- 每次发布只在对应的 `reports/pre-launch-*.md` 发布记录中维护完整更新说明，并原样或等价同步到 Gitee Release，禁止在多个文件重复维护后产生内容漂移。
- `knowledge/iteration-history.md` 维护跨版本总表和压缩后的 Release 摘要，
  只索引已经在发布记录中成立的事实，不复制完整发行说明。进行中的版本可以
  登记范围和起点，但必须标为“开发中”，不得提前填写发布时间或发布结论。
- Gitee Release 必须保留“新功能”“Bug 修复”“架构调整”三个固定核对栏目；无变化时明确写“无”。
- 本文定义的九类更新用于完整说明。“新功能”和“新特性”可汇总到 Release 的“新功能”栏目；“基础能力 / 工程优化”中涉及架构、数据、API、依赖或部署关系的内容汇总到“架构调整”栏目；其余类型保留在“核心更新”或独立分类中。
- 固定栏目是发布完整性核对摘要，不能替代本文要求的用户故事、问题原因、具体方案、用户价值和可验证结果。
- 所有数字必须来自可复核的测试、监控、埋点或发布证据；没有数据时写阶段结果或待观察指标，不得推测或补写。

### 2.1 跨版本历史的维护时点

跨版本历史使用以下固定流程：

1. **G0 范围冻结**：在版本总表新增一行，填写版本、类型、开发起点、状态和
   核心关键词；结束时间与自然周期保持“发布后补录”。
2. **固定候选**：只更新本地开发摘要和权威证据链接，不把候选写成已发布。
3. **Tag / Gitee Release**：回填不可变标签、开发结束时间和自然周期；自然
   周期使用墙钟时间，并明确不等于 Agent 工时。
4. **生产观察关闭**：把状态更新为“已发布”，将最终用户变化、关键验证、
   热修和已知边界压缩到对应版本摘要。
5. **热修**：在总表单独增加一行，并在原版本摘要下追加根因、修复和验证；
   不移动或改写原标签事实。

维护时以发布记录、Git 标签和生产观察证据为输入。版本表与摘要发生冲突时，
先修正对应 `reports/pre-launch-*.md` 或补充关闭证据，再更新跨版本历史。

## 3. 更新类型

统一使用以下分类：

| 分类 | 定义 |
| --- | --- |
| **新功能** | 从无到有新增完整产品能力、页面、模块或业务流程 |
| **新特性** | 在现有能力基础上新增可独立感知的能力、模式、配置或使用方式 |
| **功能优化** | 对已有功能的逻辑、流程、能力范围或使用效果进行增强 |
| **UX 优化** | 优化操作路径、交互反馈、理解成本、使用效率等用户体验 |
| **UI 优化** | 优化视觉层级、排版、组件样式、信息密度及视觉一致性 |
| **性能优化** | 优化速度、响应、稳定性、资源占用、吞吐等系统性能 |
| **策略 / 算法优化** | 优化推荐、搜索、识别、召回、排序、模型或规则效果 |
| **Bug 修复** | 修复原有功能在特定条件下出现的异常行为 |
| **基础能力 / 工程优化** | 埋点、日志、架构、组件、接口、数据底座等非直接用户感知能力 |

## 4. 通用写作原则

每项更新优先回答四个问题：

> **原来有什么问题 → 为什么会出现 → 这次怎么改 → 改完有什么价值或结果**

避免使用以下无信息量表述：

- 优化用户体验
- 提升系统能力
- 修复若干 Bug
- 优化部分页面
- 调整交互逻辑
- 提升性能
- 优化算法效果
- 体验更加流畅
- 页面更加美观

必须具体到**场景、对象、动作或指标**，并优先使用用户语言，而不是只写研发实现。

## 5. 新功能 / 新特性

### 5.1 必填结构

每项必须包含：

**名称 + 用户故事 + 功能说明 + 用户价值**

用户故事统一使用：

> **作为「用户画像 / 使用场景」，我希望「完成什么事情」，以「获得什么价值」。**

推荐完整格式：

> **「功能名称」｜新功能 / 新特性**
>
> **用户故事：** 作为「xxx 用户 / xxx 场景下的用户」，我希望「xxx」，以「xxx」。
>
> **更新内容：** 新增「xxx 能力」，支持「核心功能 1、核心功能 2」，解决此前「核心问题」。
>
> **用户价值：** 「降低 xxx 成本 / 提升 xxx 效率 / 获得 xxx 能力」。

### 5.2 示例

#### 热点事件时间线｜新功能

**用户故事：** 作为持续关注热点事件进展的用户，我希望快速看到事件从发生到最新进展的关键节点，以减少在多篇重复报道中自行整理信息的成本。

**更新内容：** 热点详情页新增事件时间线，自动聚合同一事件的重要进展，并按照时间顺序展示关键节点与最新变化。

**用户价值：** 用户可以在单一页面快速理解事件起因、过程与当前状态，降低重复阅读和信息整理成本。

## 6. 功能优化

功能优化重点描述：

> **此前能力不足 → 本次具体增强 → 用户获得什么改善**

推荐格式：

> **「优化项」｜功能优化**
>
> 此前「原有功能 / 问题表现」，导致「用户影响」；本次通过「具体能力调整」，使「能力或体验变化」。
>
> 如有数据，补充：「核心指标 A → B，提升 / 降低 xx」。

### 示例

#### 搜索筛选能力增强｜功能优化

此前搜索结果仅支持按内容类型筛选，当用户需要查找特定时间范围内的内容时，需要反复修改关键词；本次新增时间范围筛选，并保留用户最近一次筛选状态，使用户能够更快缩小结果范围。

## 7. UX 优化

### 7.1 定义

UX 优化关注：

- 操作步骤
- 理解成本
- 等待成本
- 误操作
- 状态反馈
- 路径效率
- 信息查找效率

不要把视觉调整归入 UX，纯视觉调整应归入 UI。

### 7.2 推荐格式

> **「优化项」｜UX 优化**
>
> 此前用户在「场景」下需要「原操作流程 / 问题」，存在「步骤多 / 易误触 / 不易理解 / 反馈不及时」；本次通过「交互调整」，将「变化结果」；使用户「获得的体验改善」。

### 7.3 示例

#### 发布流程简化｜UX 优化

此前用户发布内容需要依次完成编辑、预览、话题选择和确认发布 4 个步骤，流程较长且中途退出成本较高；本次合并预览与话题选择，并自动推荐相关话题，将核心操作缩短为 2 步；降低用户发布操作成本并提升流程完成效率。

## 8. UI 优化

### 8.1 定义

UI 优化重点描述：

- 信息层级
- 字号
- 间距
- 排版
- 颜色
- 组件样式
- 视觉密度
- 一致性
- 可扫描性

禁止只写“更美观”“视觉升级”。

### 8.2 推荐格式

> **「优化项」｜UI 优化**
>
> 此前「视觉问题」，导致「阅读 / 扫描 / 层级识别问题」；本次调整「具体视觉元素」，强化 / 弱化「信息层级」，提升「具体视觉效果」。

### 8.3 示例

#### Feed 卡片信息层级优化｜UI 优化

此前标题、来源、发布时间与操作区视觉权重接近，用户快速浏览时核心信息不够突出；本次重新调整字号、间距及辅助信息颜色，强化标题与核心内容、弱化来源和时间信息，提升 Feed 浏览时的信息扫描效率。

## 9. 性能优化

### 9.1 强制结构

性能优化必须采用以下结构：

> **优化「xxxx」【优化项；概括】：此前因「xxx 原因」，导致「体验描述」；现通过「解决方案」，使「量化结果」。**

原则：

- 必须写清楚**为什么慢 / 为什么卡 / 为什么不稳定**。
- 必须写清楚**采用了什么方案**。
- 尽量给出**量化结果**。
- 无法量化时，不得编造数据，可写观察指标或阶段结果。

### 9.2 示例

#### 优化首页首屏加载【性能优化；首屏响应速度】

此前因首页多个接口串行请求且大图资源同步加载，弱网环境下首屏内容展示较慢；现通过接口并行化、首屏资源优先加载及非核心图片懒加载，使首屏平均可见时间由 **1.8s 降至 1.2s，降低 33%**。

#### 优化搜索结果响应【性能优化；接口响应速度】

此前因搜索请求需要同步完成多路召回与排序计算，高峰期响应时间明显升高；现通过召回并行化与部分结果缓存，使 P95 响应时间由 **860ms 降至 510ms**。

示例中的数字只用于说明写法，不得直接用于实际版本。

## 10. 策略 / 算法优化

### 10.1 推荐结构

> **「优化项」｜策略 / 算法优化**
>
> 此前因「原策略 / 模型问题」，导致「结果表现」；本次通过「规则 / 模型 / Prompt / 排序 / 召回调整」，提升「目标能力」；核心指标由「A → B」。

需要区分：

- **算法动作**：改了什么。
- **业务结果**：最终效果如何。

禁止只写：

> 优化推荐算法，提高推荐效果。

### 10.2 示例

#### 搜索结果相关性优化｜策略 / 算法优化

此前搜索排序对关键词字面匹配权重较高，部分语义相关但表达不同的内容排序靠后；本次增强语义相关性、时效性与内容质量特征权重，并调整排序策略，使 Top3 相关结果命中率由 **81.3% 提升至 88.6%，+7.3pp**。

示例中的数字只用于说明写法，不得直接用于实际版本。

## 11. Bug 修复

### 11.1 强制要求

禁止：

> 修复若干 Bug。
>
> 修复部分已知问题。
>
> 修复视频播放异常等问题。

每个 Bug 必须独立记录，并严格使用三句话结构：

1. **Bug 描述**：说明“什么用户 / 什么条件 / 什么场景下，出现什么异常”。
2. **原因**：说明异常产生的直接原因。
3. **解决方案**：说明本次如何处理。

统一格式：

> **Bug 描述：** 在「xxx 条件 / 场景」下，「具体异常表现」。
>
> **原因：** 因「具体原因」，导致「异常机制」。
>
> **解决方案：** 通过「具体修复方案」，确保「修复后的正常表现」。

### 11.2 示例

#### 视频返回 Feed 后自动播放异常｜Bug 修复

**Bug 描述：** 用户全屏播放视频后返回 Feed 时，部分 Android 机型会出现视频仍保持播放状态，声音持续输出。

**原因：** 因页面生命周期切换时播放器暂停事件未在部分机型上正常触发，导致播放状态未及时同步。

**解决方案：** 增加页面返回时的播放器状态兜底校验，并统一暂停事件处理逻辑，确保退出全屏后播放器状态正确恢复。

#### 搜索筛选条件丢失｜Bug 修复

**Bug 描述：** 用户在搜索结果页设置筛选条件后进入详情页，再返回搜索页时，原筛选条件会被重置。

**原因：** 因搜索页面重新初始化时未恢复用户上一轮筛选状态。

**解决方案：** 增加搜索筛选状态缓存与页面恢复逻辑，使用户返回结果页后继续保留原有筛选条件。

## 12. 基础能力 / 工程优化

此类内容通常无法被用户直接感知，因此必须说明其业务价值或后续支撑能力。

推荐格式：

> **「能力名称」｜基础能力 / 工程优化**
>
> 本次完成「工程建设内容」，解决「当前工程问题」，为后续「具体业务 / 功能 / 数据能力」提供支撑。

### 示例

#### Feed 行为埋点统一｜基础能力 / 工程优化

本次统一 Feed 曝光、点击、停留和滑动行为埋点口径，解决不同页面事件定义不一致的问题，为后续 Feed 阅读深度分析、推荐策略评估及 A/B 实验提供统一数据基础。

## 13. 单版本文件结构

每个版本统一采用以下结构；没有对应内容的分类可以不展开，但 Gitee Release 的三个固定核对栏目不得省略：

```md
# Vx.x.x 更新说明

发布时间：YYYY-MM-DD
版本定位：一句话概括本版本核心目标。

## 发布核对摘要

### 新功能
- 逐项汇总新功能和新特性；无变化写“无”。

### Bug 修复
- 逐项汇总 Bug 修复；无变化写“无”。

### 架构调整
- 逐项汇总架构、数据、API、依赖或部署关系变化；无变化写“无”。

## 版本概览

本版本共包含：
- 新功能 x 项
- 新特性 x 项
- 功能优化 x 项
- UX / UI 优化 x 项
- 性能 / 策略优化 x 项
- Bug 修复 x 项
- 基础能力 / 工程优化 x 项

## 核心更新

### 1. xxx｜新功能
...

### 2. xxx｜功能优化
...

### 3. xxx｜UX 优化
...

### 4. xxx｜性能优化
...

## Bug 修复

### 1. xxx

**Bug 描述：** ...

**原因：** ...

**解决方案：** ...

### 2. xxx

**Bug 描述：** ...

**原因：** ...

**解决方案：** ...

## 基础能力 / 工程优化

### 1. xxx
...

## 数据结果

| 指标 | 优化前 | 优化后 | Delta |
| --- | ---: | ---: | ---: |
| xxx | xx | xx | xx |

## 配置、验证与风险

- 配置与迁移：
- 测试与生产验证：
- 已知限制与回滚：

## 灰度与遗留

- xxx 功能当前灰度 xx%
- xxx 指标继续观察
- xxx 问题计划下版本处理
```

没有可验证数据时删除“数据结果”表，不使用占位值完成正式发布。没有灰度或遗留事项时写“无”。

## 14. 汇报摘要表

对外汇报或周会中，可将详细更新进一步压缩为：

| 类型 | 更新项 | 核心变化 | 用户价值 / 结果 |
| --- | --- | --- | --- |
| 新功能 | 热点时间线 | 新增事件进展聚合 | 降低事件理解成本 |
| 功能优化 | 搜索筛选 | 新增时间筛选 | 提高查找效率 |
| UX 优化 | 发布流程 | 4 步缩短至 2 步 | 降低操作成本 |
| UI 优化 | Feed 卡片 | 重构视觉层级 | 提升信息扫描效率 |
| 性能优化 | 首页加载 | 并行请求 + 懒加载 | 1.8s → 1.2s |
| Bug 修复 | 视频播放 | 修复返回后继续播放 | 恢复正常播放状态 |

摘要只能压缩已写入完整更新说明且有证据支持的内容，不能引入新结论或未经验证的数字。

## 15. 最终检查清单

发布更新说明前逐项检查：

- [ ] 新功能 / 新特性包含**用户故事**。
- [ ] 明确写出**用户场景与价值**。
- [ ] 功能优化说明**此前问题与本次变化**。
- [ ] UI 与 UX 分类正确。
- [ ] 性能优化包含**原因、方案、量化结果**；无法量化时写明观察指标或阶段结果。
- [ ] 策略 / 算法优化同时写明**策略变化与指标结果**；没有指标时不编造。
- [ ] 每个 Bug 严格包含**Bug 描述、原因、解决方案**三句话。
- [ ] 不存在“优化体验”“提升能力”“修复若干问题”等空泛表述。
- [ ] 优先使用用户语言，而不是纯研发实现语言。
- [ ] 所有数字均可验证，没有补写或推测不存在的数据。
- [ ] Gitee Release 的“新功能”“Bug 修复”“架构调整”三个固定栏目均已填写，无变化时明确写“无”。
- [ ] 完整更新说明只维护在本次发布记录，并已原样或等价同步到 Gitee Release。
- [ ] `knowledge/iteration-history.md` 的版本总表已回填开发区间、自然周期、
      状态、关键词和权威证据链接。
- [ ] 跨版本摘要只压缩本次发布记录中已经成立的事实；开发中、Preview、
      已发布和观察关闭没有混写。
- [ ] 热修已使用独立表格行和原版本下的追加记录，没有改写原标签或原发布结论。
