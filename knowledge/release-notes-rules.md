# 更新说明写作规范

修订：2026-10-17，Owner 已批准，接入 develop 后生效。本文是发行说明的结构和写作口径唯一正文，不定义发布授权、动作顺序或当前版本状态；这些分别见[授权策略](release-authorization-policy.md)、[发布 SOP](../SOP/release-and-observation.md)和[控制面协议](coordination-control-plane.md)。

## 维护位置与事实

完整更新说明只维护在 `docs/versions/<版本>/README.md`，由本版本指定的唯一 writer 接入各切片要点，再原样或等价同步到 Gitee Release。同版本不再建计划、预发布、复盘或协作报告副本；不可再生的正式机器证据放同版本 `evidence/` 并引用。

跨版本[历史总表](iteration-history.md)只索引已成立的发布事实和权威记录，不另维护开发中候选状态。正式收口补入开发区间、发布/观察时点、自然周期、关键词和记录链接；自然周期是墙钟时间，不等于 Agent 工时。热修单独登记，旧标签和历史结论不改写。

发行说明应说明相对同产品线上一发行版的变化；首版写“无（首个发行版）”。未发布不能填写已发布时间。既有历史保留，不因本规范更新追溯重排或补写结果。

## 结构与分类

Gitee Release 必须保留“新功能”“Bug 修复”“架构调整”三个核对栏目，无变化写“无”。栏目可引用正文，不复制同一项全文。新功能/新特性归入“新功能”；数据、API、依赖、模块或部署关系变化归入“架构调整”；其他优化按实际类别展开。

| 类别 | 描述重点 |
| --- | --- |
| 新功能 | 从无到有的完整能力、页面或流程 |
| 新特性 | 原有能力中新增可感知的模式、配置或用法 |
| 功能优化 | 原能力不足、本次增强与用户改善 |
| UX 优化 | 操作步骤、反馈、等待、误操作与理解成本 |
| UI 优化 | 层级、排版、间距、颜色、密度与一致性 |
| 性能优化 | 慢/卡/不稳定的原因、具体方案及可核验结果 |
| 策略 / 算法优化 | 策略或模型变化与业务效果，不能只写算法动作 |
| Bug 修复 | 特定条件下的异常、原因与修复 |
| 基础能力 / 工程优化 | 工程问题、建设内容及实际支撑的业务能力 |

不为每个版本机械展开全部分类。用用户语言写清“原问题 → 原因 → 具体变化 → 价值/结果”，避免“优化体验”“修复若干 Bug”“提升能力”等空泛表述。

## 必需内容

**新功能 / 新特性**：名称、用户故事、功能说明和用户价值。用户故事用“作为……，我希望……，以便……”明确使用者、任务和收益。

**功能 / UX / UI 优化**：写明此前问题、本次变化和改善。视觉层级归 UI；路径和反馈归 UX，不以“更美观”代替具体说明。

**性能优化**：使用“优化……：此前因……，导致……；现通过……，使……”说明原因、方案与结果。量化结果注明环境、样本及指标口径；无可靠数据写阶段结果或待观察项，不补造百分比。

**策略 / 算法优化**：同时写清策略动作和业务效果。没有准确率、命中率等证据时保留未验证限制，不能据实现推断质量。

**Bug 修复**：每个独立 Bug 用三句话：

1. **Bug 描述：** 什么用户/条件/场景发生什么异常。
2. **原因：** 异常的已确认直接原因；未知原因明确未知。
3. **解决方案：** 本次处理及实际验证到的正常表现。

**基础能力 / 工程优化**：说明解决什么工程问题、支撑哪个真实业务或后续能力，不能把纯研发动作当用户价值。

## 版本正文模板

```md
# vX.Y.Z 更新说明

发布时间：实际发布后填写
版本定位：本版本解决的主要问题
对比基线：上一发行版及可核对范围

## 发布核对摘要

### 新功能
变化或“无”，可引用下方详情

### Bug 修复
变化或“无”，可引用下方详情

### 架构调整
变化或“无”，可引用下方详情

## 核心更新
按实际分类写用户故事、原问题、变化与价值

## 配置、验证与风险
配置/迁移变化、适用候选证据、未验证项及回退限制

## 运行与收口
实际发布/部署/观察结果的证据引用，延期去向
```

有可核验数据时可增加“指标、优化前、优化后、差异”表；没有则不放空表。无灰度或遗留事项写“无”。详细验证保留在回执，正文只给结论、适用候选、限制及引用。不可把计划、测试通过和上线完成混写。

## 发布前核对

- 三个核对栏目齐全，变更范围与上一发行版一致。
- 新功能有用户故事；优化有原因、方案和结果；每个 Bug 有三句话。
- 数字、版本、发布时点和结论均可回查，无未经证实的成功或指标。
- 分类、内容和限制对非研发读者清楚；外部 Release 与唯一正文一致。
- 正式收口历史索引与原发布记录一致；没有另建当前状态副本。

周报或汇报可从已成立正文压缩“类型、更新项、变化、价值/结果”四列摘要，不引入新结论，不作为第二个手工维护的版本状态。
