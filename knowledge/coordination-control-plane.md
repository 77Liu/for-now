# 唯一协调控制面与版本事件协议

版本：2.1；生效：2026-10-13。本文是当前状态、事件记录、更新入口与归档的唯一正文，覆盖旧的内嵌历史和逐次状态提交约定。

## 三个记录对象

| 对象 | 路径 | 用途与写入方式 |
| --- | --- | --- |
| 当前控制面 | `reports/requirement-coordination-current.json` | 覆盖更新，仅保留当前有效范围、活动任务、候选、授权、阻碍、下一动作、运行事实与证据引用 |
| 版本事件 | `reports/iterations/<版本>/events.jsonl` | 按发生顺序追加本小版本的有意义事件；已有事件不得覆盖，纠错追加事件 |
| 收口快照 | `reports/iterations/<版本>/terminal.json` | 小版本完成或明确取消时保存完整收口控制面及结果，归档后只读 |

当前控制面是当前状态唯一正文，由 `canonical_path` 指定位置；只有 Owner 指定的协调者维护。其他工作树、README、需求池、看板、报告和聊天只能引用，不得维护第二份当前状态或直接修改当前 JSON。

当前控制面禁止嵌入历史事件、旧任务过程、已结束候选和旧发布尝试。仍有效决定只保留其当前值与形成事件引用；历史归档不能作为当前状态或新任务基线。迁移前记录用原 Git 提交与旧记录的证据引用追溯，不改写原失败或制造新验收。

## 事件标准

**改变后续行动，或证明关键动作已发生的决定与结果，必须记录为事件。**

| 必须记录 | 不单独记录 |
| --- | --- |
| 需求选择、范围、验收标准变更 | 排版、措辞、字段顺序调整 |
| 基线变更、候选冻结或替换 | 同一状态的重复描述 |
| 任务派发、负责人或写集变更 | 同一任务的重复提醒 |
| 授权、暂停、恢复、撤销 | 无变化轮询 |
| 实现接入、关键验收结论 | 不改变结论的逐条输出、重复测试 |
| 缺陷确认、返工、延期、阻碍解除 | 未改变判断的调查过程 |
| 推送、发布、部署、回滚实际结果 | 聊天进度复述 |
| 影响行动的状态纠正、版本收口 | 普通文字纠错 |

事件必须有唯一 ID、版本、事件类型、发生及记录时间、原因、证据引用，并区分计划／决定／实际结果。补录标明补录及原来源，不能把补录时间当发生时间，也不能凭计划补写动作成功。

## 唯一更新入口

协调者通过 `npm run coordination:update -- <动作> --input <JSON请求文件>` 更新；入口以 `package.json` 为准，实现为 `scripts/control-plane-update.mts`，产物只在忽略的 `.build/`。请求文件不在参数中展开，不含凭据或用户正文。

请求包含 `actor`（当前协调者聊天 ID）、`expected_revision`、`iteration_id`、完整目标 `state`；有意义变更另含 `event` 的 `id/type/phase/reason/evidence`，`phase` 使用 `plan/decision/result`。`close` 另附 `closure.status/result/checks`，五类核对各有结论、原因、事件 ID 和证据引用。派生摘要、修订和收口快照只能由入口生成，不接受事件输入注入。

1. 读取当前 revision、模式与事实回执；请求注明协调者和预期 revision。
2. 范围、基线、负责人、写集、授权、候选、阻碍、下一动作或关键结果变化必须提供事件类型、原因、证据。普通措辞只能改展示摘要；结构化行动字段仍须事件，不能借“改措辞”绕过。
3. 校验后先追加事件并持久化，再原子替换当前控制面。事件保存失败，禁止推进依赖该变更的动作。
4. 同一事件 ID 重试不重复追加；同 ID 不同请求拒绝。事件已持久化而状态未更新时，按原请求恢复，不重复外部副作用。
5. 协调者单写；其他角色只产出回执，协调者独立核对后由入口更新，不能直接照抄回复推进状态。

`apply` 更新状态，`audit` 核对事件与当前状态持久化一致性，`handoff` 启动新版本，`restore-held` 恢复已有未收口版本，`close` 核对收口、保存快照并清理当前状态。交接请求含 `from_iteration_id`、目标 `iteration_id`、完整新状态及 `iteration_handoff` 事件。恢复请求含当前来源 `from_iteration_id`、目标 `iteration_id` 和 `held_iteration_restored` 决定事件；事件详情引用 `target_iteration_id`、`held_event_id`、`held_state_after_hash`，证据须包括 Owner 信号与当前授权依据。锁或持久化不一致先恢复现场，不盲删锁或继续派发。入口实现验证前，不宣称自动防漏或技术强制。

`handoff` 用于当前版本已验证并冻结、状态为 `READY_WAIT_OWNER` 且没有活动任务时启动下一版本；它不等于发布或收口，不把前版改记为完成或取消，也不创建 `terminal.json`。候选必须冻结自己的 `required_gates` 和 `test_matrix_ref`；入口只核对候选声明的每个必需门均为 `PASS`，不另选一套长期固定测试清单。矩阵之外的 `PARTIAL`/`NOT_RUN` 项如实保留。

协调者提供新版本完整目标状态和 `iteration_handoff` 决定事件。入口把事件追加到来源版本事件链，目标版本用 `started_by` 锚定该事件；目标状态的 `held_iterations` 保存未收口版本、其状态事件引用、完整状态摘要、候选 SHA 与授权摘要。候选、授权和未收口状态的完整内容仍由被引用事件提供，不能复制整份旧控制面。后续恢复和再次转移以不可变转移事件建立新的事件链段；递归审计只需核对到所引用的锚点事件，不要求该事件永远是来源日志末尾，也仍校验完整事件哈希。

`restore-held` 用于明确的 Owner 信号要求恢复某个 `held_iterations` 中的版本。当前不得有活动实施任务；协调者通过 `held_iteration_restored` 决定事件记录 Owner 信号和当前授权依据。恢复取回原版本范围、候选、授权和任务状态，并保留当前控制面的规则基线、协调者身份及最新运行观测。它本身不授予发布权限、不等于发布或收口，也不覆盖已有事件或收口快照；原版恢复后可继续使用 `close` 正常收口，先前版本仍可再次恢复。历史授权若不再包含于当前授权，恢复拒绝重新启用它。恢复失败按相同事件 ID 与请求重试；转移、恢复和收口均使用事件锚点划分历史段，`audit` 核验每段与引用完整性。

## 各方边界

| 使用方 | 可以维护 | 禁止维护 |
| --- | --- | --- |
| 需求管理 | 原话、来源、问题、验收、反馈证据及未冻结建议 | 冻结范围、开发／发布／运行状态 |
| 开发与审查者 | 设计、实现、自查、验证与审查回执 | 全局队列、当前状态或另一份控制面 |
| 发布执行者／monitor | 指定动作外部回执、运行观测、告警 | 擅自改变候选、授权、当前状态或重放旧 heartbeat |
| README／地图／聊天 | 引用当前来源、revision及读取时间 | 自写完成结论、未读取却冒充实时状态 |
| 报告／事件／收口快照 | 绑定对象与时间的历史证据及限制 | 充当当前门禁、工作基线或覆盖当前决定 |

需求池状态只能从控制面单向投影，标注修订与同步时间；滞后如实显示，不反向覆盖。原始用户数据、附件与凭据不进入正式事件或 Git。

## 收口与提交

归档前由协调者逐项核对需求与范围决定、任务交接、候选变化、关键验收、发布动作是否有对应事件和证据。缺失先补录；无法证实保留未知、失败或 `partial`，不得补写通过。未执行的动作记未执行或不适用，不虚构发布。

收口请求提供上述五类核对的事件引用、证据、结论及未确认原因。完成或取消事件先落盘，再保存完整收口控制面和结果到 `terminal.json`，最后清空不再活动的范围、任务和候选。收口快照不得覆盖，纠错用追加事件追溯。

**唯一控制面文件必须进入 Git 并随相关提交保存；不是不提交，而是不为每次变动专门创建 commit。** 事件与状态及时落盘，随相关实现、规则迁移或版本收口提交保存；一起保存当前状态所引用的正式事件，保证提交可独立追溯。每小版本收口时集中提交 `events.jsonl`、`terminal.json` 和清理后的当前控制面。正式事件与归档必须允许 Git 跟踪，不能被 `.gitignore` 排除；原始快照、凭据与编译产物仍不入 Git。

## 能力声明

脚本检查结构、事件 ID、持久化顺序、引用和收口字段；不能自动证明证据真实、判断全部语义变化或识别所有漏记。协调者仍须审查实际代码和动作回执。调用者声明身份不等于文件 ACL 或可靠认证；唯一维护者是项目权限约定。

更新入口与收口机制实现并验证前，不宣称具备自动防漏记或技术强制能力。验证部分机制后只声明实际验证范围，历史不足与未验收项保持真实。
