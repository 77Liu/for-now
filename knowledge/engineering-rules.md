# 工程与代码规则

本文档是本项目代码修改、验证、提交与协作规则的单一事实来源。目标不是穷举所有可能错误，而是用少量高信号约束减少过度设计、越界改动、虚假完成和不可审查提交。

规则优先级：

1. 用户当前明确要求与安全约束；
2. 本项目已确认的产品、数据和架构规则；
3. 本文档的工程原则；
4. 通用风格偏好。

发生冲突时按更高优先级执行，并在交付说明中指出取舍。

## 1. 核心原则

### 1.1 奥卡姆剃刀、KISS 与 YAGNI

- 如无必要，勿增实体：能在现有模块内清楚解决，就不新增依赖、目录、服务、配置层或抽象。
- 选择满足当前需求的最简单正确方案，不为想象中的未来需求预埋复杂扩展点。
- “简单”不等于省略必要的安全、数据完整性、错误恢复和验证。
- 性能优化以已知瓶颈、可测指标或明确性能目标为依据；没有证据时先保证正确和可读。

### 1.2 DRY 的适用边界

- DRY 针对知识和规则的重复：同一业务口径、数据结构、提示词契约或配置应有单一事实来源。
- 少量相似代码不必立即抽象。只有重复已经造成修改遗漏、行为漂移或测试负担时才提取复用。
- 不为了消除几行字面重复制造跨模块耦合。

### 1.3 关注点分离与低耦合

- 数据持久化、业务计算、外部 API、页面渲染和交互状态保持清楚边界。
- 模块内部围绕一个稳定职责组织；模块之间通过最小、明确的数据契约协作。
- 优先使用组合和现有辅助函数，不建立不必要的继承层次。
- 调用方只依赖完成任务所需的最小接口，避免穿透多层对象读取内部状态。

### 1.4 最少惊讶

- 新行为应符合现有页面、API、数据和命令的惯例。
- 兼容性变化、数据迁移、默认值变化和会影响用户原记录的操作必须显式说明并验证。
- 不让一次局部保存重置无关表单、滚动位置、展开状态或后台任务。

### 1.5 SOLID 的使用方式

SOLID 是面向对象设计的诊断工具，不是必须逐条套用的模板。本项目以无框架 Node 和原生 JavaScript 为主，只有当职责混杂、替换困难、接口臃肿或依赖方向确实造成维护问题时才采用相应原则；不得为“符合 SOLID”新增无实际收益的类或接口。

## 2. 范围与克制

- 只实现用户明确要求及完成该要求不可缺少的改动。
- 每一处改动都应能追溯到需求、已确认规则、测试失败或必要兼容性。
- 不因为打开了某个文件就顺手重构、格式化、改名、整理 import 或清除历史死代码。
- 不为一次性操作创建 helper、配置项、钩子、框架或通用层。
- 不修改未触及代码的注释、类型或文档；只在逻辑不自明时添加简短注释。
- 不为纯理论场景增加分支。用户输入、文件、网络、外部 API、认证和持久化等系统边界必须处理真实可发生的失败。
- 清理本次改动产生的未使用 import、变量、函数、临时文件和测试数据。
- 发现无关问题时记录在交付说明或 TODO；除非它阻塞当前任务，否则不扩大修改范围。

代码量不是独立目标。优先减少不必要复杂度，但不得用“更少行数”换取语义含糊、重复业务规则或缺失验证。

## 3. 修改流程

### 3.1 先理解再修改

1. 读取 `README.md`、`PROJECT_RULES.md`、`one-mistake-one-rule.md` 和任务相关知识文件。
2. 检查工作区状态，识别用户已有的未提交改动。
3. 搜索现有实现、测试、数据契约和相邻模式。
4. 把需求改写成可验证行为，再选择最小改动面。

不得覆盖、回退或顺带提交用户及其他任务的改动。

### 3.2 优先复用现有模式

- 使用项目已有命名、缩进、引号、文件布局、DOM 更新方式、API 结构和错误表达。
- 使用标准 API 或结构化解析器处理结构化数据，不用脆弱的字符串拼接代替。
- 仅当抽象能消除真实复杂度、减少有风险的重复，或匹配既有架构时才新增抽象。

### 3.3 数据与外部边界

- 原始用户数据、附件、模型设置和认证数据不得进入 Git。
- 数据结构变化必须考虑旧数据迁移、失败恢复和原始数据保留。
- 外部模型或云服务返回值必须按契约校验；不得把模型推断自动升级为用户事实。
- 密钥、邀请码和令牌不得写入源码、文档、日志、命令输出或聊天。

## 4. 诚实与验证

- 不编造文件路径、行号、提交哈希、API、库能力、部署状态或测试结果。
- 不以“diff 看起来正确”代替运行验证。
- Bug 修复优先先复现症状或建立失败断言，再修复根因；隐藏报错、扩大重试或吞掉异常不算修复。
- 测试范围随风险扩大：窄改动跑相关检查；共享行为、数据结构、认证、部署或用户主流程改动必须扩大回归。
- 测试无法运行时，必须说明未运行的项目、原因和剩余风险。
- 需求存在两种高影响解释且无法从项目事实判断时，先对齐；低风险细节采用最符合现有系统的方案继续推进。

本项目代码变更的默认最低验证：

```bash
npm run check
npm test
```

认证相关追加 `npm run test:auth`，页面交互相关追加 `npm run test:ui`。环境没有 `npm` 时，可使用 `启动.command` 中的 Node 路径按 `package.json` 展开执行等价命令，但必须报告实际执行方式。

## 5. 提交与发布

### 5.1 提交

- 一个提交只表达一个可独立理解的目的；不要把无关改动混入提交。
- 提交前检查 `git diff`、`git status` 和验证结果，只暂存本任务文件。
- 推荐 Conventional Commits：`feat:`、`fix:`、`perf:`、`refactor:`、`test:`、`docs:`、`build:`。
- 主题行尽量不超过 72 个字符并表达具体结果；正文解释原因、取舍和不明显的影响，不写 `update file`、`fix bug` 等无信息内容。
- 不为了追求“小步”把一个不可独立验证的改动机械拆成大量提交。

### 5.2 当前主分支策略

当前仓库是单维护者模式，生产部署源为 Gitee `main`，尚未配置 PR/CI 门禁。因此：

- 只有用户明确要求提交或部署时，Agent 才能 commit、push 或更新生产环境。
- 允许在完整验证后直接 push `main`，但必须确认没有混入其他未提交改动。
- push 不会自动部署；仍需显式执行服务器 `for-now-deploy`。
- 当项目进入多人协作或自动部署阶段时，改为功能分支 + PR + 必需 CI 检查，禁止直接 push `main`。

### 5.3 发布

- 发布前必须确认本地测试通过、目标提交已推送、工作区中的其他改动不会被带入。
- 确定准备上线时，必须按 `knowledge/development-release-checklist.md` 完成自查；阻断项未通过或未附证据时不得发布。
- 部署后验证 `/readyz`、运行版本和关键访问路径；健康检查失败必须保留现有自动回滚能力。
- 云端只部署 Git 中的代码，不双向同步 `/srv/for-now/data`，不从本地覆盖正式数据。

## 6. 沟通规则

- 直接说明正在确认什么、修改什么、验证结果和剩余风险，不寒暄、不奉承、不重复用户原话。
- 用户前提与代码事实冲突时先指出证据，再给出可执行替代方案。
- 完成声明必须对应已观察结果；部分完成应明确区分“已完成、未完成、被阻塞”。
- 交付总结聚焦行为变化、关键文件、验证和部署状态，不罗列无关过程。

## 7. 规则维护

- 规则文件应短而可执行：目标约 100 行，原则上不超过 300 行。
- 新规则应来自真实需求、重复摩擦或有复发风险的错误，不预先穷举。
- 每隔数周或规则明显膨胀时审查一次：合并重复项、删除已失效或已由自动检查替代的规则。
- 通用工程规则维护在本文档；具体产品口径维护在对应 `knowledge/` 文件；真实错误经验维护在 `one-mistake-one-rule.md`。
- 删除规则前确认其约束已不再需要，或已经由测试、lint、类型检查、权限和部署门禁可靠替代。
