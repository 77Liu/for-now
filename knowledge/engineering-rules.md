# 工程与代码规则

本文档是本项目代码修改、验证、提交与协作规则的单一事实来源。目标不是穷举所有可能错误，而是用少量高信号约束减少过度设计、越界改动、虚假完成和不可审查提交。

规则优先级：

1. 用户当前明确要求与安全约束；
2. 本项目已确认的产品、数据和架构规则；
3. 本文档的工程原则；
4. 通用风格偏好。

发生冲突时按更高优先级执行，并在交付说明中指出取舍。

## 1. 核心原则

### 1.1 奥卡姆剃刀、KISS 与 YAGNI

- 如无必要，勿增实体：能在现有模块内清楚解决，就不新增依赖、目录、服务、配置层或抽象。
- 选择满足当前需求的最简单正确方案，不为想象中的未来需求预埋复杂扩展点。
- “简单”不等于省略必要的安全、数据完整性、错误恢复和验证。
- 性能优化以已知瓶颈、可测指标或明确性能目标为依据；没有证据时先保证正确和可读。

### 1.2 DRY 的适用边界

- DRY 针对知识和规则的重复：同一业务口径、数据结构、提示词契约或配置应有单一事实来源。
- 少量相似代码不必立即抽象。只有重复已经造成修改遗漏、行为漂移或测试负担时才提取复用。
- 不为了消除几行字面重复制造跨模块耦合。

### 1.3 关注点分离与低耦合

- 数据持久化、业务计算、外部 API、页面渲染和交互状态保持清楚边界。
- 模块内部围绕一个稳定职责组织；模块之间通过最小、明确的数据契约协作。
- 优先使用组合和现有辅助函数，不建立不必要的继承层次。
- 调用方只依赖完成任务所需的最小接口，避免穿透多层对象读取内部状态。

### 1.4 最少惊讶

- 新行为应符合现有页面、API、数据和命令的惯例。
- 兼容性变化、数据迁移、默认值变化和会影响用户原记录的操作必须显式说明并验证。
- 不让一次局部保存重置无关表单、滚动位置、展开状态或后台任务。

### 1.5 SOLID 的使用方式

SOLID 是面向对象设计的诊断工具，不是必须逐条套用的模板。本项目以无框架 Node 和原生 JavaScript 为主，只有当职责混杂、替换困难、接口臃肿或依赖方向确实造成维护问题时才采用相应原则；不得为“符合 SOLID”新增无实际收益的类或接口。

## 2. 范围与克制

- 只实现用户明确要求及完成该要求不可缺少的改动。
- 每一处改动都应能追溯到需求、已确认规则、测试失败或必要兼容性。
- 不因为打开了某个文件就顺手重构、格式化、改名、整理 import 或清除历史死代码。
- 不为一次性操作创建 helper、配置项、钩子、框架或通用层。
- 不修改未触及代码的注释、类型或文档；只在逻辑不自明时添加简短注释。
- 不为纯理论场景增加分支。用户输入、文件、网络、外部 API、认证和持久化等系统边界必须处理真实可发生的失败。
- 清理本次改动产生的未使用 import、变量、函数、临时文件和测试数据。
- 发现无关问题时记录在交付说明或 TODO；除非它阻塞当前任务，否则不扩大修改范围。

代码量不是独立目标。优先减少不必要复杂度，但不得用“更少行数”换取语义含糊、重复业务规则或缺失验证。

## 3. 修改流程

### 3.1 先理解再修改

1. 读取 `README.md`、`PROJECT_RULES.md`、`one-mistake-one-rule.md` 和任务相关知识文件。
2. 检查工作区状态，识别用户已有的未提交改动。
3. 搜索现有实现、测试、数据契约和相邻模式。
4. 把需求改写成可验证行为，再选择最小改动面。

不得覆盖、回退或顺带提交用户及其他任务的改动。

### 3.2 优先复用现有模式

- 使用项目已有命名、缩进、引号、文件布局、DOM 更新方式、API 结构和错误表达。
- 使用标准 API 或结构化解析器处理结构化数据，不用脆弱的字符串拼接代替。
- 仅当抽象能消除真实复杂度、减少有风险的重复，或匹配既有架构时才新增抽象。

### 3.3 数据与外部边界

- 原始用户数据、附件、模型设置和认证数据不得进入 Git。
- 数据结构变化必须考虑旧数据迁移、失败恢复和原始数据保留。
- 外部模型或云服务返回值必须按契约校验；不得把模型推断自动升级为用户事实。
- 密钥、邀请码和令牌不得写入源码、文档、日志、命令输出或聊天。

### 3.4 模块与跨模块修改

- 模块边界、依赖方向、迁移顺序和跨模块影响矩阵统一以 `knowledge/modularization-design.md` 为准。
- 模块外只能依赖其公开入口；禁止深层导入内部文件、跨模块修改私有状态或绕过所属模块直接访问其存储。
- 修改数据、API、认证、AI、任务、删除恢复、附件、时间、渲染、导航、配置、日志或隐私契约前，必须按影响矩阵检查全部生产者、消费者、测试和文档。
- 公共契约和共享模块在并行任务中必须有唯一负责人；多个任务需要修改同一模块时应串行处理或先冻结兼容契约。
- 模块化重构默认保持行为不变。结构调整和功能变化应拆成可独立验证的任务，不在同一提交中混合。
- 新增、拆分、合并、重命名模块或改变模块职责时，必须同步维护模块化设计文件；临时兼容入口必须记录删除条件。
- v0.2.0 强制“底座串行 → 契约验收冻结 → 独立功能并行 → 串行集成”。准入条件、四路分工与工作树/目录所有权见 `knowledge/modularization-design.md` 第 11 节；底座未验收不得提前并行改业务存储、公共 API 或热点文件。
- 功能开发只运行稳定性测试；不得以数据库重构为由默认执行压测，`test:load` 仅用于明确的容量评估或用户要求。

## 4. 诚实与验证

- 不编造文件路径、行号、提交哈希、API、库能力、部署状态或测试结果。
- 不以“diff 看起来正确”代替运行验证。
- Bug 修复优先先复现症状或建立失败断言，再修复根因；隐藏报错、扩大重试或吞掉异常不算修复。
- 测试范围随风险扩大：窄改动跑相关检查；共享行为、数据结构、认证、部署或用户主流程改动必须扩大回归。
- 测试无法运行时，必须说明未运行的项目、原因和剩余风险。
- 需求存在两种高影响解释且无法从项目事实判断时，先对齐；低风险细节采用最符合现有系统的方案继续推进。

本项目代码变更的默认最低验证：

```bash
npm run check
npm test
```

认证相关追加 `npm run test:auth`，页面交互相关追加 `npm run test:ui`。环境没有 `npm` 时，可使用 `启动.command` 中的 Node 路径按 `package.json` 展开执行等价命令，但必须报告实际执行方式。

### 4.1 自 V0.4.0 起：旅程前移与分层验证

- 功能切片开始时即从 `knowledge/user-journey-matrix.json` 标出受影响旅程；
  新增或改变用户任务时，在同一切片补齐旅程、业务结果、持久化、异常恢复和
  副作用断言。旅程验证不得推迟到主版本总集成后。
- 验证按三级执行：普通切片运行功能专项和受影响 Journey Smoke；共享契约、
  跨域集成或里程碑运行系统门；冻结候选运行完整 Release 门。具体入口与
  证据失效范围以 `knowledge/system-testing.md` 为准。
- 新接入第三方供应商时，首个接入切片必须同时建立不发请求的 plan-only
  检查、取得凭据与费用授权后的本地 live 冒烟，以及发布阶段的生产 live
  冒烟；不得只用协议桩关闭真实可用性验收。

## 5. 提交与发布

### 5.1 提交

- 一个提交只表达一个可独立理解的目的；不要把无关改动混入提交。
- 提交前检查 `git diff`、`git status` 和验证结果，只暂存本任务文件。
- 自 V0.4.0 起，在没有安全、数据完整性或发布阻断，且提交授权已覆盖当前
  范围时，同一待提交单元一旦超过 500 行增删或 15 个文件，必须及时形成
  一个或多个功能级/任务级本地提交，不得因夜间或连续工作长期保持未提交。
  属于同一需求或同组需求、能够共同验证的改动可以合并一次提交；无关任务
  不得跨域合并。确因强依赖、生成工程或单一原子迁移无法继续拆分时，提交
  正文必须记录不可拆原因、受影响模块、风险和实际验证，不得仅以“集成提交”
  解释超限。
- 上述 500 行/15 文件是拆分与及时提交触发线，不是放宽提交边界：每个提交仍须先固定暂存树、检查实际内容并完成影响范围测试；高风险范围仍按本节人工授权规则处理。
- 2026-10-01 起，功能通过项目“基于真实用户行为的交互测试体系”中适用的
  用户任务闭环、业务结果、持久化、异常恢复、视觉/兼容性检查后，Agent 可
  直接创建对应的本地功能级或任务级提交，无需再次等待人工核验；测试证据和
  未覆盖边界必须写入提交或交付记录。该授权不包含 push、tag、Gitee Release、
  部署、生产写入或真实数据迁移。
- 商业化价格、预算、费用拒绝阈值及会影响用户权益的业务数值必须汇报并由
  Owner 确认；QPS、并发、分页大小、预取距离、队列长度、超时和重试次数等
  技术参数可由 Agent 根据供应商上限、容量证据和回归结果给出保守初值，并
  记录调整依据。
- 推荐 Conventional Commits：`feat:`、`fix:`、`perf:`、`refactor:`、`test:`、`docs:`、`build:`。
- 主题行尽量不超过 72 个字符并表达具体结果；正文解释原因、取舍和不明显的影响，不写 `update file`、`fix bug` 等无信息内容。
- Git 发布版本时必须附中文更新说明，详细写明用户可见变化、关键技术与数据变化、配置迁移、测试证据、已知限制和回滚方式；仅有英文提交标题不构成完整版本说明。内容分类和写法以 `knowledge/release-notes-rules.md` 为准，发布流程以 `knowledge/pre-launch-confirmation.md` 为准。
- 每个推送到共享远端的 Git 标签都必须创建对应 Gitee Release；发行说明必须相对同一产品线的上一发行版，保留“新功能”“Bug 修复”“架构调整”三个核对栏目并按 `knowledge/release-notes-rules.md` 提供完整更新内容。三个栏目不可省略，无变化时明确写“无”。
- 不为了追求“小步”把一个不可独立验证的改动机械拆成大量提交。
- Agent 可以在已指定的短期任务分支上，通过
  `npm run commit:task -- --message "<feat|fix|test|docs>(scope): 摘要"`
  自动创建本地低风险提交，不再逐次申请人工授权。提交类型必须反映实际内容，
  不得把修复、测试或文档改名为 `feat`；`commit:feat` 作为兼容别名保留。
- `feat` / `fix` 只允许一个低风险产品域及其对应测试和必要说明；
  `test` 必须声明单一功能域且只包含匹配的回归与说明；
  `docs` 只允许普通文档。任务范围外的改动必须拆出或转人工确认。
- 自动门禁最多接受 16 个文件、1200 行增删及单文件 512 KiB，固定暂存区 tree，在隔离候选目录执行 `npm run check` 与按后端/前端影响选择的回归；验证后 HEAD、分支或 tree 漂移即拒绝。提交记录必须附 `Validation-Tree`、`Validation-Commands` 和 `Commit-Gate` trailer。
- 自动门禁拒绝 `main`、`release/*`、`hotfix/*` 等受保护分支，以及门禁自身、工程治理规则、包清单/依赖锁、认证、持久化、共享入口、配置、外部供应商、部署/迁移、生产或私有数据、二进制、探索资产、跨功能域和超限改动。这些改动仍需人工逐次授权提交。
- 2026-09-30 起，Owner 对非大版本中的单一小型 `feat` / `fix` / `test` /
  `docs` 提供持续本地提交授权：专项和影响回归通过、无阻断且没有必须报告事项时，
  Agent 可直接在当前本地主线提交，不再逐次询问。自动门禁若仅因 `main`、
  `release/*` 或必要共享模块分类拒绝，可在核对固定 diff 与验证证据后使用直接
  Git 提交，并记录原因。
- 必须先报告的范围不受上述持续授权覆盖：门禁或治理逻辑自身、依赖或锁文件、
  认证与权限、数据库 schema/迁移或持久化协议、外部供应商和真实付费调用、
  部署/生产配置、生产或私有数据、二进制/原生签名资产、大范围跨域重构，以及
  任何未关闭的安全、数据完整性或发布阻断。
- 自动本地提交不是发布验收，也不授权 push、合并远端、tag、Gitee Release、
  部署、生产写入或真实付费服务调用；上述操作始终需要本次人工明确授权，
  不得把“测试通过”解释成发布授权。

### 5.2 当前主分支策略

当前仓库是单维护者模式，生产部署源为 Gitee `main`，尚未配置 PR/CI 门禁。因此：

- 除 5.1 定义的门禁提交和持续授权小任务外，Agent 只有在用户明确授权具体范围后才能 commit。
- push、tag、Gitee Release、部署和生产环境写入始终需要用户对本次操作的明确授权；本地自动提交不构成授权。
- 允许在完整验证后直接 push `main`，但必须确认没有混入其他未提交改动。
- push 不会自动部署；仍需显式执行服务器 `for-now-deploy`。
- 当项目进入多人协作或自动部署阶段时，改为功能分支 + PR + 必需 CI 检查，禁止直接 push `main`。

### 5.3 发布

- 发布前必须确认本地测试通过、目标提交已推送、工作区中的其他改动不会被带入。
- 确定准备上线时，必须按 `knowledge/development-release-checklist.md` 完成自查；阻断项未通过或未附证据时不得发布。
- 远端标签、Gitee Release、目标完整哈希、上一发行版和发行说明必须一一对应；只推标签未创建发行版不算发布完成。
- 部署后验证 `/readyz`、运行版本和关键访问路径；健康检查失败必须保留现有自动回滚能力。
- 云端只部署 Git 中的代码，不双向同步 `/srv/for-now/data`，不从本地覆盖正式数据。

### 5.4 自 V0.4.0 起：长任务检查点与发布后 Git 收尾

- 连续执行超过 2 小时的任务，每 2～3 小时形成一次可恢复检查点，至少记录
  当前分支与 HEAD、工作树状态、已完成、当前 NO-GO、下一步和证据路径。
  检查点可以是已授权的任务提交或追加式进度记录；不得为制造检查点提交
  不完整、不可验证的代码。
- 检查点只包含一个任务或强依赖任务组；出现第二个无关任务时先提交、stash
  或切换隔离工作树，不让多个任务长期共享未提交状态。
- 发布观察关闭后，在下一迭代开始前核对 `origin/main`、本地 `main`、发布
  标签和生产运行提交；本地 `main` 必须同步到远端关闭提交。
- 旧功能工作树只有在工作区干净且其必要提交已经进入主线或独立归档后才能
  移除。发现脏工作树、未合入提交或用户文件时保留现场并记录阻塞，不得使用
  强制删除、reset 或清理命令。

## 6. 沟通规则

- 直接说明正在确认什么、修改什么、验证结果和剩余风险，不寒暄、不奉承、不重复用户原话。
- 用户前提与代码事实冲突时先指出证据，再给出可执行替代方案。
- 完成声明必须对应已观察结果；部分完成应明确区分“已完成、未完成、被阻塞”。
- 交付总结聚焦行为变化、关键文件、验证和部署状态，不罗列无关过程。

## 7. 规则维护

- 规则文件应短而可执行：目标约 100 行，原则上不超过 300 行。
- 新规则应来自真实需求、重复摩擦或有复发风险的错误，不预先穷举。
- 每隔数周或规则明显膨胀时审查一次：合并重复项、删除已失效或已由自动检查替代的规则。
- 通用工程规则维护在本文档；具体产品口径维护在对应 `knowledge/` 文件；真实错误经验维护在 `one-mistake-one-rule.md`。
- 删除规则前确认其约束已不再需要，或已经由测试、lint、类型检查、权限和部署门禁可靠替代。
