# 工程与代码规则

本文档是本项目工程原则、修改流程、验证诚实与沟通规则的唯一正文入口；源码文档、提交发布和领域数据访问分别见对应 detail。目标不是穷举所有可能错误，而是用少量高信号约束减少过度设计、越界改动、虚假完成和不可审查提交。

优先级和正文归属仅见[项目规则](../PROJECT_RULES.md#读取与规则归属)，本文件不另设优先级。

## 1. 核心原则

### 1.1 奥卡姆剃刀、KISS 与 YAGNI

- 如无必要，勿增实体：能在现有模块内清楚解决，就不新增依赖、目录、服务、配置层或抽象。
- 选择满足当前需求的最简单正确方案，不为想象中的未来需求预埋复杂扩展点。
- “简单”不等于省略必要的安全、数据完整性、错误恢复和验证。
- 性能优化以已知瓶颈、可测指标或明确性能目标为依据；没有证据时先保证正确和可读。

### 1.2 DRY 的适用边界

- DRY 针对知识和规则的重复：同一业务口径、数据结构、提示词契约或配置应有单一事实来源。
- 少量相似代码不必立即抽象。只有重复已经造成修改遗漏、行为漂移或测试负担时才提取复用。
- 不为了消除几行字面重复制造跨模块耦合。

### 1.3 关注点分离与低耦合

- 数据持久化、业务计算、外部 API、页面渲染和交互状态保持清楚边界；领域、实体、事务、同步和首屏访问的具体契约统一见[设计职责与数据访问契约](design-contracts.md)。
- kernel 只承担依赖装配与生命周期接线；回答登记、数据加载等行为由所属模块提供。测试夹具、测试数据加载与验收脚本不得混入业务源码；相关能力由测试支持入口注入，实际消费者保持兼容。
- 模块内部围绕一个稳定职责组织；模块之间通过最小、明确的数据契约协作。
- 优先使用组合和现有辅助函数，不建立不必要的继承层次。
- 调用方只依赖完成任务所需的最小公开接口，避免穿透多层对象读取内部状态；复用前先核对职责和实际行为是否一致。

### 1.4 最少惊讶

- 新行为应符合现有页面、API、数据和命令的惯例。
- 兼容性变化、数据迁移、默认值变化和会影响用户原记录的操作必须显式说明并验证。
- 不让一次局部保存重置无关表单、滚动位置、展开状态或后台任务。

### 1.5 SOLID 的使用方式

SOLID 是面向对象设计的诊断工具，不是必须逐条套用的模板。本项目采用无框架 Node 和原生前端，既有 JavaScript 渐进迁移为 TypeScript，只有当职责混杂、替换困难、接口臃肿或依赖方向确实造成维护问题时才采用相应原则；不得为“符合 SOLID”新增无实际收益的类或接口。

## 2. 范围与克制

- 只实现用户明确要求及完成该要求不可缺少的改动。
- 每一处改动都应能追溯到需求、已确认规则、测试失败或必要兼容性。
- 不因为打开了某个文件就顺手重构、格式化、改名、整理 import 或清除历史死代码。
- 不为一次性操作创建 helper、配置项、钩子、框架或通用层。
- 不修改未触及代码的注释、类型或文档；本次涉及的源码与公共接口按[源码与接口文档规范](source-documentation-rules.md)维护。
- 不为纯理论场景增加分支。用户输入、文件、网络、外部 API、认证和持久化等系统边界必须处理真实可发生的失败。
- 清理本次改动产生的未使用 import、变量、函数、临时文件和测试数据。
- 发现无关问题时记录在交付说明或 TODO；除非它阻塞当前任务，否则不扩大修改范围。

代码量不是独立目标。源码可读排版、存量压缩代码整改及恢复排版后的函数职责评估统一遵循 [PROJECT_RULES 第 12 条](../PROJECT_RULES.md#修改验证与提交)。优先减少不必要复杂度，不得用“更少行数”换取语义含糊、重复业务规则或缺失验证。

## 3. 修改流程

### 3.1 先理解再修改

1. 按 [项目读取入口](../PROJECT_RULES.md#读取与规则归属) 恢复必要上下文；事故和历史按本次问题检索。
2. 检查工作区状态，识别用户已有的未提交改动。
3. 搜索现有实现、测试、数据契约和相邻模式。
4. 把需求改写成可验证行为，再选择最小改动面。

不得覆盖、回退或顺带提交用户及其他任务的改动。

### 3.2 优先复用现有模式

- 使用项目已有命名、缩进、引号、文件布局、DOM 更新方式、API 结构和错误表达。
- 使用标准 API 或结构化解析器处理结构化数据，不用脆弱的字符串拼接代替。
- 仅当抽象能消除真实复杂度、减少有风险的重复，或匹配既有架构时才新增抽象。

### 3.3 数据与外部边界

- 原始用户数据、附件、模型设置和认证数据不得进入 Git。
- 数据结构变化必须考虑旧数据迁移、失败恢复和原始数据保留。
- 普通在线业务的数据读写和增量同步遵循[设计职责与数据访问契约](design-contracts.md)；全量导入、恢复和派生重建必须走专用流程。
- 外部模型或云服务返回值必须按契约校验；不得把模型推断自动升级为用户事实。
- 密钥、邀请码和令牌不得写入源码、文档、日志、命令输出或聊天。

### 3.4 模块与跨模块修改

- 模块清单、公开入口、依赖方向和迁移顺序统一以 `knowledge/modularization-design.md` 为准；领域职责、实体访问和公共数据契约统一以 `knowledge/design-contracts.md` 为准。
- 模块外只能依赖其公开入口；禁止深层导入内部文件、跨模块修改私有状态或绕过所属模块直接访问其存储。
- 修改数据、API、认证、AI、任务、删除恢复、附件、时间、渲染、导航、配置、日志或隐私契约前，必须按影响矩阵检查全部生产者、消费者、测试和文档。
- 公共契约和共享模块在并行任务中必须有唯一负责人；多个任务需要修改同一模块时应串行处理或先冻结兼容契约。
- 模块化重构默认保持行为不变。结构调整和功能变化应拆成可独立验证的任务，不在同一提交中混合。
- 新增、拆分、合并、重命名模块或改变模块职责时，必须同步维护模块化设计文件；临时兼容入口必须记录删除条件。
- 并行准入、共享契约写集及串行接入只见[协作协议](../SOP/multi-agent-orchestration.md)，不把旧版本的固定分工沿用为长期要求。
- 性能或容量验证按实际目标和影响选择；不因“数据库重构”默认压测，也不因“功能开发”排除必要性能验收。选择规则见[测试影响矩阵](test-impact-matrix.md)。

### 3.5 源码与接口文档规范

唯一正文见[源码与接口文档规范](source-documentation-rules.md)。本入口只规定工程修改必须引用该 detail，不复制其条款。

## 4. 诚实与验证

- 不编造文件路径、行号、提交哈希、API、库能力、部署状态或测试结果。
- 不以“diff 看起来正确”代替运行验证。
- Bug 修复优先先复现症状或建立失败断言，再修复根因；隐藏报错、扩大重试或吞掉异常不算修复。
- 测试范围随风险扩大：窄改动跑相关检查；共享行为、数据结构、认证、部署或用户主流程改动必须扩大回归。
- 测试无法运行时，必须说明未运行的项目、原因和剩余风险。
- 需求存在两种高影响解释且无法从项目事实判断时，先对齐；低风险细节采用最符合现有系统的方案继续推进。

代码变更的验证范围遵循唯一正文[测试影响矩阵](test-impact-matrix.md)，按写集、行为影响和候选阶段选择 `package.json` 中的专项、Journey Smoke、系统门或完整 Release 门；不对所有改动固定运行同一组全量命令。环境与证据要求也以测试影响矩阵为准。

### 4.1 用户旅程与真实依赖

- 功能切片开始时即从 `knowledge/user-journey-matrix.json` 标出受影响旅程；
  新增或改变用户任务时，在同一切片补齐旅程、业务结果、持久化、异常恢复和
  副作用断言。旅程验证不得推迟到主版本总集成后。
- 测试层级和发布前全局门仅引用[测试影响矩阵](test-impact-matrix.md)，不另设冻结后才验证的第二种顺序。
- 新接入第三方供应商时，首个接入切片必须同时建立不发请求的 plan-only
  检查、取得凭据与费用授权后的本地 live 冒烟，以及发布阶段的生产 live
  冒烟（仅在环境授权覆盖且确需验证时）；具体阶段与复用条件见[真实第三方验收](third-party-live-testing.md)，不得只用协议桩关闭真实可用性验收。

## 5. 提交与发布

本地提交见[提交规则](commit-and-release-rules.md)；发布操作见[发布 SOP](../SOP/release-and-observation.md)，权限见[发布自动授权策略](release-authorization-policy.md)。三者不互相授予权限或复制条款。

## 6. 沟通规则

- 直接说明正在确认什么、修改什么、验证结果和剩余风险，不寒暄、不奉承、不重复用户原话。
- 用户前提与代码事实冲突时先指出证据，再给出可执行替代方案。
- 完成声明必须对应已观察结果；部分完成应明确区分“已完成、未完成、被阻塞”。
- 交付总结聚焦行为变化、关键文件、验证和部署状态，不罗列无关过程。

## 7. 规则维护

- 规则篇幅、map-detail 及唯一维护位置遵循[项目约束维护](../PROJECT_RULES.md#约束维护)。
- 新规则应来自真实需求、重复摩擦或有复发风险的错误，不预先穷举。
- 每隔数周或规则明显膨胀时审查一次：合并重复项、删除已失效或已由自动检查替代的规则。
- 通用工程规则维护在本文档；具体产品口径维护在对应 `knowledge/` 文件；真实错误经验维护在 `one-mistake-one-rule.md`。
- 删除规则前确认其约束已不再需要，或已经由测试、lint、类型检查、权限和部署门禁可靠替代。
